# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## God Rule — Plain Language Always

**When explaining EVERYTHING to the user, write in plain language.** This applies to every user-facing message without exception: explanations, audit results, recommendations, status updates, bug reports, fix descriptions, end-of-turn summaries, questions back to the user — everything.

The user is not reading the code. They need to understand what's happening, not what it's called.

**Never:**
- Name functions, classes, files, components, hooks, variables, properties, fields, routes, endpoints, tables, or columns
- Quote line numbers or file paths
- Use technical jargon: "endpoint", "state", "props", "callback", "promise", "schema", "middleware", "render", "dispatch", "mount", "ref", "context", "response", "request", "payload", "API", "frontend", "backend", "server-side", "client-side"
- Reference framework or library names: React, Express, SQLite, JWT, hooks, etc.

**Always:**
- Describe the experience as a flow: "the user clicks here → this happens → then this shows up"
- For a bug: describe what the user expected to see vs. what actually happens
- For a fix: describe the new behavior the user will experience
- Use everyday words: "the screen", "the button", "the form", "the list", "the message", "the page", "saves", "shows", "remembers", "sends"

**Example — wrong (technical):**
> The `qaTemplateWarning` field is set on the response in `jobcard-mutations.js:157` but the form's submit handler doesn't consume it, so no toast fires.

**Example — right (plain):**
> When a job is created, if any quality forms fail to copy, the screen never shows a warning. So the user thinks everything worked when it didn't.

The only exception is code comments and commit messages, where technical terms are appropriate because the audience is a future reader of the code itself.

## Project Overview

DH Engineering Job Card System - A full-stack Electron/React/Express application for managing job cards, quotes, contacts, suppliers, and manufacturing operations. Designed for LAN-connected desktop use with a central server.

## Development Commands

All commands run from `/jobcard-system/`:

```bash
# Start full application (server + Electron client)
npm start

# Start server only (port 3000)
npm run server

# Start client only (Electron + Vite dev server)
npm run client

# Web-only mode (no Electron, port 5173)
cd client && npm run start:web

# Build production client
npm run build

# Build Electron distributable
cd client && npm run build:electron

# Server with auto-reload
cd server && npm run dev

# Seed mock data (wipes DB, creates test data) — run on Windows
seed.bat
```

## Architecture

### Stack
- **Frontend**: React 18 + React Router, Vite bundler, Electron 27, react-hot-toast (notifications), framer-motion (animations)
- **Backend**: Express 4, better-sqlite3 (synchronous SQLite), pino (logging), express-validator, express-rate-limit
- **Auth**: JWT (memory-only, no localStorage), bcryptjs password hashing, rate-limited login (5 failed attempts/15 min)
- **Font**: Pragmatica (bundled OTF, weights 300/400/700) with Google Sans fallback

### API Structure
Base URL: `/api` (relative; Vite dev server proxies to `http://localhost:3000`, production serves client statically from Express)

Main routes: `/auth`, `/jobcards`, `/contacts`, `/suppliers`, `/machines`, `/settings`, `/history`, `/qa-levels`, `/tags`, `/search`

Tag endpoints: `GET /tags` (authenticated, optional `?category=treatment`, optional `?includeArchived=true`), `GET /tags/categories` (authenticated), `GET /tags/:id` (admin), `POST /tags` (admin, `{ category, name }` — **idempotent create**: a name that maps to an existing option returns that option (200) instead of erroring, so "add on the spot" never makes a duplicate; a matching value that was archived is restored under the freshly typed name), `PUT /tags/:id` (admin, a value-changing rename is blocked for **any** category while job line items still use that value), `DELETE /tags/:id` (admin — **archives**, never hard-deletes; jobs reference options by value, so the row is kept and the `archived` flag is set), `POST /tags/:id/activate` (admin, restores an archived tag)

Settings endpoints: `GET /settings` (admin), `PUT /settings` (admin), `GET /settings/inactivity-timeout` (all users), `POST /settings/export-backup` (admin, creates ZIP at `outputPath` with database + job folder files), `POST /settings/import-backup` (admin, restores from ZIP at `inputPath`, requires `job_folders_base` configured). `PUT /settings` also accepts the **overtime configuration** (all validated server-side in `settings-overtime.js`, extracted beside `settings.js`): `timezone` (an IANA zone the overtime schedule/holidays are measured against — rejected unless `Intl.DateTimeFormat` recognises it), `labourSchedule` (a 7-day weekly schedule object; each day is a non-empty, strictly-increasing block list, each block `{ start: 'HH:MM', tier: 'normal'|'ot1'|'ot2' }` — a block runs until the next block's start, and each day is a **24-hour cycle**: the time before the earliest block wraps to the **last** block's tier, so blocks may start at any time with no forced `00:00` anchor), `labourDefaultRate` (the company-wide default base hourly rate, a number ≥ 0, stored as `labour_default_rate`), `labourOt1Multiplier` / `labourOt2Multiplier` / `labourHolidayMultiplier` (each a number ≥ 1), and `labourPublicHolidays` (array of `YYYY-MM-DD` local dates, de-duped and sorted). Managed on the admin **Labour Rates & Overtime** page (`/labour-rates`, `LabourRatesSettings.jsx` + `hooks/useLabourRates.js` + `components/settings/labour/` sub-cards); see the overtime tiers under Time entries.

Job card printout (per-job): `POST /jobcards/:id/print` (any authenticated user, in `jobcard-printout.js`) — **generates the job card as an HTML page** from the job's current data and returns `{ html }`. There is **no uploaded template and no saved file**: the card is drawn by `renderJobCardHtml` (`server/src/utils/jobCardHtml.js`) from friendly, pre-formatted data built by `buildJobCardView` (`jobcard-helpers.js`, which resolves tag values → names via `tagQueries.getByValue` and formats treatments/dates/priority). It lists exactly the job's parts (no blank rows) and flows onto extra pages for long jobs. The returned HTML is shown as the on-screen card preview in the paperwork hub (`previewCard` in `JobPaperworkHub.jsx`); **printing/saving the card always goes through the combined-packet route** (the same HTML is rendered to PDF server-side by `renderHtmlToPdf` — see the packet route below), so the desktop app and the web build print the identical card. Nothing is written to disk, so the on-screen job stays the single live record. Works whether or not job-folder storage is configured. Records a `jobCardPrinted` history entry. The printout is **not** a file category and is **never** part of the missing-attachment warning.

Combined packet printout (per-job): `POST /jobcards/:id/packet` (any authenticated user, in `jobcard-printout.js`) — welds the chosen job documents into **one combined PDF** for printing or saving. Body `{ items: [{category, filename}], includeJobCard?: boolean }` (card defaults in): the big file bytes never travel up — the client sends only the small list of files to include plus the `includeJobCard` flag, and the server reads each chosen file straight off disk **and renders the job card to PDF itself**, so the desktop app and the web build get the identical card-first packet. The card is rendered by `renderHtmlToPdf` (`server/src/utils/htmlToPdf.js`), which has two Chromium-based paths so the output is identical everywhere: when the server runs in-process inside the **packaged desktop app** (see `client/electron/main.js` `startServer`, production-only) it drives Electron's own off-screen `printToPDF` (bounded by a 30s timeout — `withTimeout` in `htmlToPdf.js` — so a wedged built-in browser can't hang the print forever; on timeout the hidden window is destroyed in the `finally`, which frees the stuck render, and the card is skipped-and-reported as a `'render'` failure like any other); otherwise (**dev — where `npm start` runs the server as a standalone Node process — or a background-only server**) it uses **Puppeteer's bundled headless Chromium** (`puppeteer` dependency in `server/package.json`; one cached browser instance is reused across requests and relaunched if it dies — `scripts/setup.js` `checkPdfBrowser` auto-downloads Puppeteer's Chrome on first setup so the standalone server can render). **Browser location is pinned into the project**: `server/.puppeteerrc.cjs` sets Puppeteer's `cacheDirectory` to `server/.chrome` (gitignored, OS-specific) instead of the default per-user `~/.cache/puppeteer`, so the standalone-server Chrome is tied to the app folder rather than one OS login — it survives a same-OS folder copy and can't be "found under the wrong user". **The engine is verified at startup**: `verifyPdfEngine` (`server/src/utils/pdfEngine.js`) warms the browser via `probeBrowser` (`htmlToPdf.js`) once after `app.listen` (fire-and-forget, never blocks boot); on failure it logs a loud, fixable message and flips a status. That status is surfaced on `GET /health` as `pdfEngine` (`ready` / `unavailable` / `electron` / `pending`). The check is **skipped inside the packaged desktop app** (`electron`), which renders with its own built-in browser. Both use A4 / backgrounds-on / zero-margins. If the card can't be rendered it's **skipped and reported**, never failing the whole packet — a render that failed because the engine couldn't start is reported with `reason: 'engine'` (vs `'render'`) so the paperwork hub shows a specific "couldn't start the PDF engine" message (`reportSkipped` in `usePacketPrint.js`). The packet itself is built by `buildPacketPdf` (`server/src/utils/pdfPacket.js`) with `pdf-lib`: the card goes first, then each file in order — PDFs are merged page-for-page (their own size/orientation preserved, so a landscape A3 drawing stays A3), images are normalised through `sharp` to PNG (every input format works; CMYK/progressive JPEGs that pdf-lib can't embed are handled) and placed one per A4 page scaled to fit. A file that can't be read/decoded is **skipped and reported** in `skipped`, never failing the whole packet; if **nothing** ends up combinable (every document unreadable and no card) the route returns 400 `None of the chosen documents could be combined` with the `skipped` list rather than a generic failure. Each requested filename is verified against the live folder listing (anti-traversal). Caps: ≤20 items, total input read into memory ≤600 MB (summed via `statSync` as files are read, bailing with 413 before crossing it), combined output ≤40 MB (else 413). The paperwork hub mirrors the item cap client-side (`MAX_PACKET_FILES`), disabling the print/save buttons with an "untick N" hint when more than 20 files are ticked. Records a `jobCardPacketPrinted` history entry.

History sub-routes: `GET /history` (recent, admin), `GET /history/user/:userId` (admin), `GET /history/entity/:entityType?page=1` (admin, type = `user`|`contact`|`supplier`|`machine`, returns `{ data, total, page, totalPages }` with 50 items/page)

Auth sub-routes: `PUT /auth/change-password` (all authenticated users, verifies current password)

Job card sub-routes: `/assignees`, `/time-entries`, `/costing`, `/files/:category`, `/history`, `/notes`

Job card file endpoints (disk-first; one folder per category per job — no DB rows): All routes accept `category` ∈ `{ job-files, qa-form-files, customer-property-files }`, mapped to on-disk subfolders `Job Files`, `QA Forms`, `Customer Property` under `[base]/[Company]/[JobNumber]/`. `GET /jobcards/:id/files/:category` (authenticated, lists files — each file also carries `displayName` (the tag stripped back to the human name), `itemId`, and `itemNumber` telling which part it belongs to, resolved by `resolveFileOwners` in `jobcard-files.js`; a job-level file comes back with `itemId: null`), `GET /jobcards/:id/files/:category/:filename` (authenticated, returns file as base64), `POST /jobcards/:id/files/:category/upload` (authenticated, saves base64 data; body: `{ filename, fileData, itemId? }` — used by both the file picker and camera capture), `POST /jobcards/:id/files/:category/:filename/assign` (authenticated, body `{ itemId?: string|null }` — **re-tags a stored file to a part or back to whole-job by renaming it**: strips the old `[…]` tag and re-writes it as `[p{code}]` for a part or `[{timestamp}]` for whole-job, so the paperwork hub's "For:" picker can move a file between parts and a file added job-level can be tied to a part; a given `itemId` must be a real line item on this job, else 400; records a `reassign_file` history entry). Filenames are validated against extension allowlist + path-traversal guards and made collision-free with a ` (n)` suffix. **Naming**: the identifying code rides at the END of the name in square brackets so the human-readable name leads. A file tied to a specific line item (optional `itemId`, the part's permanent `item:` id) is stored as `{name} [p{code}]` where `{code}` is the part's full id reduced to alphanumerics (`idSlug` in `folderCreation.js` — the whole id, not a truncation, so two parts can never collide on it), so the file stays matched to the part even after line items are re-numbered; job-level files (no `itemId`) get a 14-digit timestamp tag `{name} [{timestamp}]` instead. **Returned quality forms** are a special case of job-level files: any upload to the `qa-form-files` folder is renamed to a clean, predictable `Completed Form {N}` (N = one past the highest existing `Completed Form` number in that folder, via `nextQaFormNumber` in `jobcard-files.js`) — dropping whatever the scanner/camera called it — and still gets the timestamp tag appended, so a returned form lands as `Completed Form 1 [{timestamp}].pdf`. The detection of "a completed form came back" is unchanged (still the timestamp tag). The paperwork hub strips that trailing tag from QA-form names for display (`cleanQaName` in `JobPaperworkHub.jsx`), so the list reads `Completed Form 1.pdf`. The missing-file scan matches a part's files by the `[p{code}]` tag at the END of the base name (optionally followed by ` (n)`), before the extension — anchored, not an anywhere-in-name `includes`, so a file whose human-readable name merely contains another part's code can't masquerade as that part's attachment. Base64 uploads are capped at 30 MB (raw bytes); larger payloads are rejected with 400. Every upload is also validated **before any write** by `fileValidation.js`: `decodeBase64Strict` rejects a truncated/scrambled payload (Node's lenient base64 decode would otherwise silently save a broken file), and `assertMatchesExtension` checks the decoded leading bytes match the filename's extension signature — both surface a plain-English 400 so a corrupt upload can't masquerade as a part's attachment. QA template uploads (`POST /qa-levels/:id/templates`) run the same check.

Attachment-warnings endpoint: `POST /jobcards/attachment-warnings` (authenticated) — per-page check for the job list. Body `{ ids: [jobcardId, ...] }` is the ids of just the rows currently on screen; the scan checks only those (so the cost never grows with the total job count), de-duping and ignoring non-string ids. Returns `{ checked, flagged }` where `checked` is the full list of ids that were looked at (so the list can tell "checked, clean" apart from "not checked yet") and `flagged` carries one entry per checked job that declared a drawing / customer property / quality form but has no matching file on disk (`{ jobcardId, items: [{ itemNumber, missingDrawing, missingCustomerProperty }], missingQaForms }`). Missing or archived (invoiced) jobs are treated as checked-clean — included in `checked`, never in `flagged`. A "declared" value is any non-empty drawing/customer-property selection other than the explicit `N_A` ("N/A") answer; a job needs a quality form only if its QA level has a template attached **and** the level's `requires_returned_form` switch is on, and no returned form is in the QA Forms folder — a returned form is detected by the 14-digit timestamp tag the upload route stamps at the end of the name (`[{timestamp}]`, optionally ` (n)`), not by "any file that isn't a template name", so a stray/unrelated upload can't falsely clear the warning. Levels with the switch off are print-only: their templates are still copied/pre-filled on save, but the job never nags for a returned form. The same per-job warning data is also attached to single-job responses as `attachmentWarnings` (on `GET /jobcards/:id`, and on the `PUT /:id` / `PATCH /:id/status` responses). No-ops safely when job-folders storage isn't configured. Used by the job list to mark rows and by the job card screen to show per-part "Attach file" buttons. **The per-part "Attach file" button opens the paperwork hub** pointed at that part (via a `ref` handle `openForPart` on `JobPaperworkHub.jsx`), highlighting the matching folder and defaulting the next file added there to that part — it no longer opens a bare OS file dialog whose upload would land as a whole-job file that never clears the part's warning.

**Soft close-out checkpoint**: When `PUT /jobcards/:id` or `PATCH /jobcards/:id/status` would set status to `INVOICED` (which also archives) and any attachment gaps exist, the server returns 409 `{ error: 'MISSING_ATTACHMENTS', attachmentWarnings }` **before any write**. The client shows an "Invoice anyway?" confirm and resends with `confirmMissingAttachments: true` in the body to bypass the check. This is a soft nudge, not a hard block.

**Soft delete checkpoint**: `DELETE /jobcards/:id` (admin) never deletes on the first request — because deleting is permanent and the job number is never reused, the server always returns 409 `{ error: 'CONFIRM_DELETE', workWarning }` **before any write** unless the body carries `confirmDelete: true`. `workWarning` is `null` when the job has no recorded work (client shows a plain "are you sure"); when any time has been logged or a timer is running (both cascade away on delete) it carries `{ hasActive, activeWorkers, loggedHours, pastWorkers }` so the confirm can name who/what is being erased. The confirmation lives entirely in this one 409 round-trip — there is no separate client-side pre-confirm — so the admin only ever sees a single dialog. Resending with `confirmDelete: true` bypasses the gate. Mirrors the missing-attachments checkpoint.

QA level endpoints: `GET /qa-levels` (authenticated, non-admin sees active only), `GET /qa-levels/:id` (admin), `POST /qa-levels` (admin, accepts `requiresReturnedForm`), `PUT /qa-levels/:id` (admin, accepts `requiresReturnedForm`; omitting it leaves the existing value untouched so a name-only edit doesn't flip the switch), `DELETE /qa-levels/:id` (admin, blocked if used by jobs), `POST /qa-levels/:id/templates` (admin, upload PDF), `GET /qa-levels/:id/templates` (admin), `DELETE /qa-levels/:id/templates/:tid` (admin). Each level carries a `requires_returned_form` flag (default 0): on = a completed quality form must be scanned back before invoicing (drives the missing-quality-form warning); off = print-only.

**"Standard" is the baseline, not a real level**: "Standard" simply means *no special quality level* — it is **never** a row in `qa_levels` and is **not** in the seed data. A job on the baseline has `qa_level_id = NULL` and its `quality_level` label stored as `'STANDARD'`. The admin Quality Levels page therefore only lists the *extra* levels someone creates (e.g. Critical). On the job screen the quality-level picker shows a `Standard` option (value empty = no level) first as the default, followed by the saved levels; choosing Standard clears `qaLevelId` and labels the job `STANDARD`. The server is authoritative: on create/update, no `qaLevelId` ⇒ `quality_level = 'STANDARD'` and `qa_level_id = NULL`; a chosen level ⇒ that level's upper-cased name. A baseline job never has templates and never drives the missing-quality-form warning. The seed script feeds a `{ id: null, name: 'Standard' }` entry to the scenario builder so some seeded jobs sit on the baseline.

Timer endpoints: `GET /jobcards/active-timer` (authenticated), `POST /jobcards/:id/time-entries/start` (authenticated, body: `{ itemNumber, workerId? }` — `itemNumber` required, must match an existing line item; auto-assigns the timer's worker to the job if they aren't already an assignee, recorded as `self_assign`. Optional `workerId` lets an **admin start the timer for another worker** (e.g. setting someone up at a machine): admin-only (non-admins get 403), the worker is validated via `resolveWorkerId` and auto-assigned via `autoAssignWorker` (recorded as an admin assign, not `self_assign`), the running timer belongs to that worker (history names them under `worker`), and the client does **not** adopt it as the admin's own active timer), `POST /jobcards/:id/time-entries/:entryId/stop` (authenticated — **a run shorter than 15 seconds is treated as an accidental start/stop tap**: the block is deleted instead of logged, history records a `discard_timer` action, and the route returns `{ discarded: true }` so the client skips the stop form)

Notes endpoints: `GET /jobcards/:id/notes` (assignee/admin), `POST /jobcards/:id/notes` (assignee/admin), `DELETE /jobcards/:id/notes/:noteId` (admin only)

Assignee endpoints: `POST /jobcards/:id/assignees` (admin, full assignee replace), `DELETE /jobcards/:id/assignees/:userId` (admin), `POST /jobcards/:id/assignees/self` (authenticated, idempotent self-assign — uses `req.user.userId`, body ignored), `DELETE /jobcards/:id/assignees/self` (authenticated, idempotent self-unassign). Self routes log history with action `self_assign` / `self_unassign`.

Search endpoint: `GET /search` (authenticated, scoped). Query params: `scope` (all|jobs|people|activity|time), `q` (text query), `page`, `status`, `assigneeId`, `priority`, `jobType` (matches any item.job_type), `qaLevel`, `dateFrom`, `dateTo`, `dateField` (created|due), `includeArchived`, `peopleType` (both|contacts|suppliers), `userId`, `action`, `entityType`, `field` (search within changes JSON keys), `workerId`, `machineId`, `jobNumber`. Scopes `people` and `activity` are admin-only. `time` scope restricts non-admin to own entries. `all` scope returns grouped previews (top 5 per category with counts); other scopes return paginated results (25/page).

### Database Schema (SQLite)
Core tables: `users`, `contacts`, `suppliers`, `jobcards`, `job_items`, `job_assignees`, `time_entries`, `job_costings` (carries the labour overtime tiers — `labour_ot1_*` / `labour_ot2_*` / `labour_holiday_*` hours/override/total/multiplier columns; see Overtime labour tiers below), `qa_levels`, `qa_level_templates`, `history`, `settings`, `machines`, `job_notes`, `tags`, `supplier_service_tags`. Files are not stored in the database — they live on disk under the configured job-folders base (see "Files & QA workflow" below).

**Per-line-item treatments**: Each job item carries a `treatments` JSON column (array of `{ value, supplierId, supplierName }`). `value` is a treatment tag value; `supplierId` is **optional**. The UI is **one treatment + optional supplier per line item** (`tabs/LineItemTreatment.jsx`): the treatment field is a **type-or-create picker** (`common/CreatableTagSelect.jsx`) shown first — it lists **all** active treatments and lets the user add a brand-new one on the spot (dedup-safe: the idempotent `POST /tags` returns the existing option if the typed name already maps to one); the supplier dropdown appears only once a treatment is picked, lists **all** active suppliers (no longer filtered to "offers this treatment"), and can be left as "No supplier". There is **no "Other" free-text treatment** — creating a treatment on the spot replaces it. The `treatments` array holds 0 or 1 entry, but stays an array so costing/PDF-fill/history/export code that iterates it is unchanged. Validated server-side in `validateItemTreatments`: `value` must be a known treatment tag value; a supplier, when given, must exist and be active (the "supplier offers this treatment" check is gone). The same type-or-create picker drives the per-line-item **material** field (`tabs/ItemsTab.jsx`). Suppliers still carry `serviceTags` (managed on the supplier admin page) but they no longer gate the job-screen pickers. This replaces the previous `subcontracts` table — there is no separate subcontract entity, tab, or workflow.

**Per-line-item drawings & customer property**: Each job item also carries `drawings_type` and `customer_property` columns, each a comma-separated string of tag values (categories `drawings` / `customer_property`). Both are required per line item and edited via `tabs/LineItemTagSelect.jsx` (a multi-select tile picker reused for both); the `N_A` ("N/A") tag is mutually exclusive and serves as the explicit "no drawing" / "nothing supplied" answer. Validated server-side in `validateItemDrawings` / `validateItemCustomerProperty`. These used to live as single fields on the `jobcards` table; they now live on `job_items` so each part on a job records its own drawing and physical-reference state. QA-template PDF pre-fill aggregates (de-duped) the values across all items into the job-level `drawingsType` / `customerProperty` fill fields.

**Unified tags system**: The `tags` table stores all dynamic dropdown/multi-select options with columns: `id`, `category` (treatment/material/customer_property/drawings/job_type), `name`, `value`, `sort_order`, `archived`, `created_at`. The `supplier_service_tags` junction table links suppliers to treatment tags. Frontend uses the `useTags(category)` hook from `client/src/hooks/useTags.js` to fetch tags dynamically. Admin manages tags and equipment via the "Tags & Equipment" page (`/tags`, with a "Show archived" toggle and a restore button on archived rows). Equipment is managed through the existing `machines` table but shares the same admin UI.

**Archiving options (never delete)**: Options are archived, not deleted — a job stores the option's `value`, so removing the row would strand it on every job that used it. `getByCategory` returns active options only (drives the pickers); `getByCategoryIncludeArchived` returns everything (drives save-validation and display lookups). `useTags` fetches with archived included and exposes `tags` (active-only, for pickers), `labelOf(value)` (resolves any stored value — archived included — to its friendly name), plus `rawTags`/`loading`/`refresh`. A value saved on a job whose option was since archived shows in the field tagged "**(retired)**" in amber (CSS `retired-option` / `has-retired` / `lit-select-btn--retired`) so it stays visible and can be cleared, but retired options are never offered for new work. The same retired treatment shows for an archived **supplier** chosen on a job (job card loads suppliers with archived included). Server-side, `buildGrandfatheredValues` lets a job re-save a value it already held even if the option was archived/renamed away, so editing other fields on an old job never trips validation. Tag history actions are `archive` / `unarchive`.

**Contacts model** (company-primary): Each contact requires a `company_name` (NOT NULL, unique case-insensitive); `contact_name` is optional. Search autocomplete is on the Company field, with dropdown showing **Company (Contact)** format. Search filters by both `company_name` and `contact_name`. Job cards link to contacts via `contact_id` and **snapshot the customer's company/contact/phone/email onto the jobcard row at creation** (its own `company_name` / `contact_name` / `contact_phone` / `contact_email` columns). These frozen copies are read directly for all job display, search, and export — there is no live join back to `contacts` for display, and customer details are read-only once a job exists (the server strips contact fields on every update, for every role). **Customers are archived, never deleted** (track-and-trace): there is no contact-delete route — `POST /contacts/:id/archive` and `POST /contacts/:id/unarchive` (both admin) flip an `archived` flag. Archived customers are hidden from pickers, autocomplete, and search, but keep their record, the `contact_id` link on their jobs, and their files on disk; the admin Contacts page shows them via a "Show archived" toggle (`GET /contacts?includeArchived=true`). Because the link is never severed, a customer's files never strand.

All changes logged to `history` table for audit trail.

**Job card auto-numbering**: Job numbers are auto-generated from two settings: `job_number_prefix` (e.g. `"DH-"`) and `job_number_next` (e.g. `"00001"`). The format preserves leading zeros (width of `job_number_next` string). On each job card creation, the server generates `{prefix}{paddedNumber}`, validates uniqueness, inserts the record, then increments `job_number_next`. Deleted job numbers are never reused (counter only goes forward). The job number field is read-only in the create form. Admin configures prefix and starting number in Settings > Job Card Numbering. If not configured, job card creation is blocked with an error message.

**Automatic folder management**: When `job_folders_base` setting is configured, the system auto-creates `[base]/[Company] [code]/` on contact create/update and `[base]/[Company] [code]/[JobNumber]/Job Files/` + `QA Forms/` + `Customer Property/` on job card create. On job card deletion, the job card folder (`[base]/[Company] [code]/[JobNumber]/`) is recursively deleted but the parent company folder is preserved. **Folder identity is the code in the name, not the name itself**: each company folder carries the owning contact's full id (reduced to alphanumerics by `idSlug`) at the end of its name in square brackets (e.g. `Rio Tinto Iron Ore [550e8400e29b41d4a716446655440000]`), and the QA-level folders under `[base]/QA Levels/` do the same with the level id. The full id is used (not a truncation) so two folders can never collide on the code. Folder lookups (`findCompanyFolder` / `findQaLevelFolder` in `folderCreation.js`) match by that bracketed code, so renaming a customer/level just renames the folder and never strands its files — there is **no hidden marker file**. The code makes every folder name unique, so there is no same-name disambiguation. Company names are also enforced unique (case-insensitive) at create/update in `contacts.js`. Jobs with no linked contact fall back to a plain name-built folder (no code). Reading or listing files is **never** folder-creating — `resolveCategoryFolder` resolves read-only and the upload path creates the folder chain itself when a file is actually written, so browsing jobs never scatters empty folders on disk. Folder operations are fire-and-forget (errors logged, never block DB operations). Names are sanitized for cross-platform filesystem safety with path traversal protection.

**Work-driven automatic status**: A job's status follows the shop floor — it is recomputed from logged work on every work event (timer start/stop, time block added or deleted, finished quantity edited) by `syncStatusToWork` in `server/src/utils/jobStatusAuto.js`. Rule: every line at (or over) its ordered quantity ⇒ `DONE`; otherwise ⇒ `IN_PROGRESS`. Completion sums the good pieces (`qty`) from **finished** time blocks per line and compares to the line's quantity; a job with no lines, or any line whose quantity is missing/zero, is never complete. This **overrides** a manual status flip: if a manager moves a job elsewhere and a worker then logs work, it snaps back to match reality — to hold a finished job in another state the work itself must change. The only status it never touches is `INVOICED` (terminal); it also no-ops on archived jobs and when the status already matches. It does **not** write its own history row — it returns the `{ from, to }` change (or null) and the calling work route folds it into the history entry it already writes for that work event, so one action shows as one audit row carrying both the work change and the status move. Auto-status failures never break the work action. This is why **quantity is now required and must be a positive whole number** on every line item — it is the completion target. Enforced client-side (`jobCardValidation.js`, number input in `ItemsTab.jsx`) and server-side (`validateItemQuantities` in `validation.js`) on create and update.

**Auto-archive on INVOICED**: When a job card's status transitions to `INVOICED` (via `PUT /:id` or `PATCH /:id/status`), the server automatically sets `archived = 1` and stamps `invoicedDate` with the current timestamp. Only admins can set status to INVOICED. **Invoicing is an update-only transition**: a job is never *created* as INVOICED — the create route (`POST /`) rejects a `status` of `INVOICED` with 400, because only the update/status paths run the auto-archive + missing-files check, so allowing it at creation would strand a job in the invoiced-but-still-open limbo the status-lock exists to prevent. The status picker on the job screen mirrors this (INVOICED is offered only when editing an existing job, never while creating one). There is no manual archive endpoint; unarchive (`POST /:id/unarchive`, admin-only) is the only way to reverse it. **An archived (invoiced/filed-away) job is status-locked**: both status-changing paths refuse any status change while `archived === 1` (returns 409 **before any write**) — `PATCH /:id/status` blocks every status change, and `PUT /:id` blocks a status change while still allowing edits to other fields — so even an admin can't recreate the filed-away-but-OPEN limbo by editing. The lock keys off the `archived` flag alone (invoicing always files a job away; unarchive always clears it). **Unarchive also resets `status` to `OPEN`** (in the same `unarchive` query) so a re-opened job returns as a normal working job rather than a back-in-the-list-but-still-INVOICED contradiction; the reset is recorded in history alongside the `archived`/`invoicedDate` changes.

**Job card printout vs quality forms (two separate features)**: These are deliberately split. (1) The **job card printout** is **generated on demand as an HTML page** from the job's current data (`renderJobCardHtml` + `buildJobCardView`) and printed directly — there is no template to upload and **no saved file**; it lists exactly the job's parts and is never part of the missing-attachment warning. (2) **Quality forms** are per-QA-level inspection PDF templates that are printed, hand-filled, and (for levels with `requires_returned_form` on) scanned back; only those levels drive the missing-quality-form warning, and they still use `fillPdfTemplate`. See the printout endpoint above and the QA workflow below.

**Files & QA workflow**: All job card files live on disk, not in the database. Three category folders per job: `Job Files`, `QA Forms`, `Customer Property` (the job card printout is generated as HTML and printed on demand — it is not a file and is not stored). The QA level system is the only producer of templated content:
1. **Admin creates QA levels** (e.g. "Standard", "Critical") and uploads PDF template forms to each level. Templates stored at `[job_folders_base]/QA Levels/[LevelName]/`.
2. **Job card creation/update with a QA level** copies that level's template PDFs into `[base]/[Company]/[JobNumber]/QA Forms/`, auto-filling fillable form fields with job data via `pdf-lib` (`server/src/utils/pdfFiller.js`). PDFs without fillable fields are copied as-is (blank templates for handwriting). No DB rows are created — the files on disk are the only record. Implemented in `copyQaTemplatesForJob` in `jobcard-helpers.js`.
3. **Workers print** the pre-filled PDFs, fill inspection results by hand, then bring the completed forms back in via the paperwork hub in the JobCardModal header (each folder section has its own Add file / Camera buttons → file written under the matching folder). Whether a returned form is *required before invoicing* depends on the level's `requires_returned_form` switch (off = print-only, no nag).
4. **All file uploads** (file picker, camera) go through the unified `/jobcards/:id/files/:category/upload` route — same endpoint regardless of source, same disk layout regardless of category.
5. **The paperwork hub** (`JobPaperworkHub.jsx`, opened from a single **Files** button in the JobCardModal header, available to **all** users): one panel listing the generated job card on top plus the three folders (job files, QA forms, customer property), each with thumbnails, per-row View (lightbox for images, inline for PDFs) and Print-this-one, and per-folder Add file / Camera. Each file row is drawn by `HubFileRow.jsx`. In the **Job Files** and **Customer Property** sections each row also carries a **"For:"** picker (Whole job / Part N) that ties the file to a part — changing it calls the assign route to re-tag the file, which is what clears that part's missing-drawing / missing-customer-property warning (QA forms and the pinned job card have no picker). Only saved parts (with an `item:` id) are offered. Files uploaded via the hub's Add/Camera default to whole-job, unless the hub was opened from a part's Attach button (`openForPart`), in which case that section is highlighted and the next file added there defaults to that part. Everything is pre-ticked; a **Print packet** / **Save as PDF** welds the ticked items (card first) into one combined PDF via `POST /jobcards/:id/packet` (see above). Reuses `useJobFiles` (list/upload/view/thumbnails/`assignFile`) + `useCamera`; the build/print/save flow lives in `usePacketPrint.js`. This single hub **replaces** the former header Files menu and the admin-only Files tab (both removed).

Supported PDF field names for templates are defined by `FIELD_MAPPINGS` in `server/src/utils/pdfFiller.js`. The `qualityLevel` column stores the level name; `qa_level_id` is the FK to `qa_levels`.

**Time entries**: Core fields only — item#, machine#, qty, scrap (bin + recycle), description, start/end time. **Scrap pieces**: Scrap is split into two destinations — `scrap_bin_qty` and `scrap_recycle_qty` (both integers, default 0) recording pieces binned vs sent to recycling; the line's total scrap and scrap rate sum the two. They are entered by the worker in the stop-timer form (two number fields) and by admins in the manual time-entry form (which carries both Scrap — Bin and Scrap — Recycle for adding and editing). The server clamps each to ≥ 0, treating blank/garbage as 0, and preserves the existing value if an update omits a field. **Critical-job inspection checklist**: Job cards on the **Critical** quality level (the job's `quality_level` label is `'CRITICAL'`) ask the worker an extra inspection checklist when they finish, stored on the time entry: `first_off_inspection`, `in_process_validation`, `measuring_equipment_verification`, `equipment_checks` (each 1 = yes / 0 = no / NULL = not applicable, i.e. the job wasn't Critical) plus a free-text `equipment_checks_comments`. On a Critical job all four Yes/No answers are **required before a finished block can be saved** — enforced client-side (the stop-timer Submit button stays disabled until all four are answered) and server-side in `checkCriticalInspection` (`jobcard-time-entries.js`) on both the add and edit routes, which 400s a completed block missing any answer. Non-Critical jobs never show the checklist and store NULLs. The admin manual time-entry form also shows the checklist when the job is Critical (so an admin can record/correct the answers), and each finished entry's card displays the answers as Yes/No chips with the equipment comment. (The schema's legacy-drop list deliberately excludes `first_off_inspection` / `in_process_validation` — they are live again for this feature.) **Crediting work**: The admin manual time-entry form requires picking the worker who actually did the work (a `workerId` select), so hours land under that person, not the admin filling in the form. The server validates the chosen worker is a real, active account, auto-assigns them to the job (mirroring what a self-started timer does), and records the worker in history. On edit, only an admin can re-credit a block to a *different* worker (a regular worker editing their own block keeps it under themselves); leaving the owner unchanged is always allowed, so an old block owned by a since-deactivated worker can still have its other fields corrected. The machines field on a time entry is a multi-select (`CheckboxDropdown`) stored as one comma-joined string (e.g. `"5, 9"`), matching the stop-timer form. The per-item Progress section shows scrap total + scrap rate (scrap / good pieces completed; can exceed 100%; hidden when no good pieces completed yet). **Per-item timers**: Each line item has its own Start/Stop button (`LineItemTimerButton.jsx`); starting a timer requires picking an item, and the active timer is bound to that `itemNumber` (server validates the item exists on the job card, returns 409 if a timer is already running on another job/item with the conflicting timer's `jobcardId` + `itemNumber` for "stop & switch" prompts). **Special labour**: Special labour is a **manually-entered costing line**, not a per-time-entry flag. An admin types the special-labour hours and rate directly on the Costing tab (`labour_special_hours` / `labour_special_rate` on `job_costings`); the special total is `hours × rate`. Regular labour hours are auto-calculated server-side from completed time entries (`getHoursByJobcard`), but the admin can **override** that figure by typing their own hours in the Costing tab's Hours box: the auto-tally is always kept in `labour_hours` (returned as `labourHoursCalculated`) while an optional `labour_hours_override` on `job_costings` holds the hand-typed number (NULL = use the live tally). The labour total uses the override when set, otherwise the tally. A reference line under the field shows the logged-time figure with a "Reset to logged" link that clears the override, and a manual entry survives a timer refresh (a timer tick only re-fills the box when no override is in place). The override is tracked in the audit trail (the auto-tally itself is not, so an automatic recalculation isn't attributed to whoever saved). Special hours are **not** derived from time entries — time blocks can no longer be marked "special". A one-time startup conversion (`init.js`, guarded by the `special_labour_manual_reset_at` settings flag) zeroes any special hours that were previously auto-tallied so the manual line starts clean; the seed scripts stamp that flag so freshly-seeded manual figures aren't wiped. **Overtime labour tiers**: Logged time is split by *when* each minute was worked into four tiers — normal, Overtime 1, Overtime 2, and public holiday — against the admin's weekly schedule + public-holiday list (the Labour Rates & Overtime settings above). The split is done a minute at a time in local wall-clock (via `Intl`, so DST and midnight-spanning blocks fall out naturally) by `splitHours` (`server/src/utils/overtimeSplit.js`; each day is a cycle — a minute before the day's earliest block takes the last block's tier, so a late block carries over past midnight); all costing values are then worked out in **one place** — `computeLiveCosting` (`server/src/utils/costingCompute.js`), used by the costing GET/PUT routes. Each tier charges `hours × base labourRate × that tier's multiplier` (multipliers come from settings — normal is always ×1). **Per-job overtime multipliers**: the two overtime tiers' multipliers are hand-overridable per job exactly like the hours — on the Costing tab each OT row's ×N chip is a small editable box; typing marks it hand-edited (amber cue + row dot) and saves to `labour_ot1_multiplier_override` / `labour_ot2_multiplier_override` on `job_costings` (NULL = follow this job's own captured baseline multiplier; values are floored at 1 server-side), with a "standard ×N" snap-back link under the box and the footer's reset-all covering multipliers too. The effective multiplier (override ?? this job's captured baseline) is what's stored in `labour_*_multiplier` and used for the tier's charge; a job that never touched its multipliers keeps following its own captured baseline (see Per-job rule ownership below), so recomputing always reproduces the billed figure. The holiday multiplier is settings-only (not per-job). Overrides are tracked in the audit trail. **Base rate default (new-jobs-only)**: the base labour rate has a company-wide default (`labour_default_rate` in settings, a number ≥ 0, set on the Labour Rates & Overtime page). The default **only seeds new jobs**: when a job card is created, its costing row is seeded with `labour_rate` = the current company default (`persistCosting(computeLiveCosting(id, { labourRate: default }))` in the create route, inside the create transaction). From then on the job **owns** its rate — changing the company default later never moves any already-created job. The base rate is editable per job on the Costing tab (a "use company default ($X)" convenience link fills it with the current default, but it's a plain value set — nothing "follows" the default afterwards). A job with no costing row yet (only old pre-feature jobs, since new jobs are seeded at creation) falls back to the current default as a starting suggestion until first saved. `labour_rate` is owned per job, so it never moves once the job is created. Each tier's auto-split hours are hand-**overridable** exactly like normal labour: `labour_ot1_override` / `labour_ot2_override` / `labour_holiday_override` on `job_costings` (NULL = use the auto split), with `labour_*_hours` holding the tally and `labour_*_total` the charge; the tier multipliers are also copied onto the row (`labour_*_multiplier`) so the exact rate each tier was charged at is recorded. On the Costing tab each tier shows a "From logged time" reference with a "Reset to logged" link. An invoiced job's sheet stays **fully editable** — there is no locked/frozen state; saving just asks for an on-screen confirm first, then recalculates from the job's own rules — see Per-job rule ownership below. **Per-job rule ownership (no invoice-time freeze)**: every job captures its own copy of the overtime rules (schedule, holidays, timezone, base multipliers) into `job_costings` — `labour_schedule` / `labour_public_holidays` / `labour_timezone` / `labour_base_ot1_multiplier` / `labour_base_ot2_multiplier` / `labour_base_holiday_multiplier` — the first time its costing is computed (seeded at creation), exactly how `labour_rate` is already owned per job. `computeLiveCosting` reads the overtime rules from that captured copy (live settings only as the fallback for a not-yet-captured row) and writes them back, so the rules are **write-once** and a later change to the company overtime rules never moves an already-created job. Invoicing therefore takes **no** costing snapshot and there is **no lock**: recomputing an invoiced job always reproduces the billed number, and `GET /:id/costing` recomputes on the spot for open **and** invoiced jobs (every job's PUT is allowed, gated only by an on-screen "change an invoiced job?" confirm on the client). For jobs created *before* this feature (whose rules were never recorded), a one-time startup conversion (`init.js`, guarded by the `overtime_ownership_at` flag) stamps every un-captured costing row with today's rules as its own copy — best available, since the originals are unrecoverable — so from then on they too own their rules and recalculate like any other job. The client still flushes any unsaved pricing edits **before** invoicing so nothing is lost when the job is filed away. A one-time startup conversion (`init.js`, guarded by the `labour_hours_override_reset_at` settings flag) clears stale whole-job labour-hours overrides on non-invoiced jobs (the override now means *normal-tier only*, so an old whole-job override would double-count once overtime windows exist); the seed scripts stamp that flag. Hand-entered time blocks longer than ~31 days are rejected at entry (`checkEntryDuration`) and the minute-walk is safety-capped at 60 days so a bad legacy row can't stall a costing read. **Active timer protection**: Server blocks DELETE on entries with no `end_time` (returns 400). The per-item Progress section shows only a Stop button for active entries (no Edit/Delete until stopped). `useTimer` polls every 5s while a timer is active; if an admin stops it externally, the employee sees a toast notification and the time entries list refreshes automatically. **Stop timer form** (`StopTimerForm.jsx`): When a worker stops their timer, a focused card appears for the single item that was being worked on, asking for good pieces completed, scrap (binned + recycled), machines used, and description — plus the four-item Critical inspection sign-off when the job is on the Critical quality level. Good/scrap counts use a stepper (−/+ buttons either side of a typeable number; the buttons are skipped by Tab so keyboard flows field-to-field), a live scrap rate shows once any good pieces are entered, the description offers one-tap preset chips, and a long equipment list gets a filter box and a capped scrolling area (picked machines pinned on top). The header shows how long the run logged (start → end clock times). Submitting fills those fields on the existing time entry (the row created at start); a description is always required, and on a Critical job all four inspection answers are required too (good pieces, both scrap counts, and machines stay optional). Clicking X resumes the timer by clearing `end_time` on the original entry (preserves original `startTime` and `itemNumber`). A run under 15 seconds never reaches this form — the stop route discards it (see Timer endpoints) and the worker just sees a "Timer discarded — under 15 seconds" toast. On a finished entry's card (`TimeEntryCard.jsx`) the Critical inspection answers are collapsed behind a one-line "passed / flagged" summary that expands to the full Yes/No chips.

### Authentication
- Three roles: `admin` (full access), `manager` (everything an admin can do **except money** — see below) and `user` (limited)
- Management (admin **or** manager) — everywhere this file says "admin" for these areas, read "admin or manager": user management, supplier management, equipment management, QA level management, tags, contacts, settings, activity log, **contact/customer info**, **job card creation/deletion/invoicing**, **note deletion**, manual time entries and time-entry corrections
- Admin-only (never manager): **job costing** (the Costing tab and both `/jobcards/:id/costing` routes), the **Labour Rates & Overtime** page (`/labour-rates`; the labour/overtime settings keys are stripped from `GET /settings` and rejected on `PUT /settings` for managers — key lists exported as `OVERTIME_BODY_KEYS`/`OVERTIME_DB_KEYS` from `settings-overtime.js`), **data backup export/import** (a backup carries the whole database, pricing included), the **job-folders base path** (the `job_folders_base` setting — it decides where every job's files and backups are written, so a manager can't repoint it to a personal/removable drive; the Job Folders card is admin-only in the Settings UI and a manager's `PUT /settings` carrying `jobFoldersBase` is rejected 403 alongside the overtime keys), the **Excel job-card export's pricing sheet** (the export button is management-visible, but the Costing sheet — labour/overtime/materials/grand total — is only built for admins; the costing fetch is admin-only server-side anyway, so a manager's export simply omits the sheet), the **activity trail** (the global Activity Log page + `GET /history` + `GET /history/user` + the per-job Activity tab + `GET /jobcards/:id/history` + the search **activity** scope are all admin-only, because the trail records costing edits with dollar from/to; managers keep entity history — user/contact/supplier/machine via `GET /history/entity` — which carries no pricing), and **admin accounts** (a manager can never create, promote, edit or archive an admin — otherwise they could grant themselves the costing access managers are barred from; enforced server-side in the user routes and mirrored in the Users page UI)
- Role checks: server-side `requireManagement` / `isManagement(role)` from `middleware/auth.js` (`requireAdmin` remains for the money routes); client-side `isManagement(user)` from `client/src/utils/roles.js`. Convention: props/variables carrying management semantics are named `canManage` (not `isAdmin`), and list-column/search-scope metadata uses `managementOnly`
- **Employee (user) role**: Read-only job card view (Details tab renders as styled text, not inputs) except status dropdown (employees can change job status via `PATCH /:id/status`, but cannot set status to INVOICED — management-only). Employees see no tab strip — only the Details content renders, with line items + per-item Progress inlined. Managers see no tab strip either — the strip only appears for true admins (Details + Costing + Activity); the Costing and Activity tabs and their data loads are gated on true admin, and the per-job Activity trail carries pricing changes so it stays admin-only. The paperwork hub is reachable by all users (read+write — anyone assigned to a job can upload to its folders). The Costing tab is pricing-only (rates, totals); all time-entry CRUD lives in the Details tab via per-item Progress (`LineItemProgress.jsx` inside `ItemsTab.jsx`). Employees use Start/Stop timer for time tracking (one active timer at a time, enforced server-side). Can add notes but not delete them. **Paperwork hub**: a single **Files** button in the JobCardModal header opens the hub (`JobPaperworkHub.jsx`) — the one place to view/upload/print a job's documents (job card + Job Files / QA Forms / Customer Property), with per-folder Add file / Camera and combined-packet print/save. Uploads go to the matching folder via `/jobcards/:id/files/:category/upload`. Active timers show a pulsing green indicator on job card rows for all users.
- **Job card visibility**: All authenticated users can see and access all job cards (same visibility as admin). Non-admin users remain read-only with limited actions (status change, timer, notes, self-assign). Non-admins can add/remove **only themselves** via the Assigned-To column popover (`POST`/`DELETE /jobcards/:id/assignees/self`); admins still manage the full assignee list via the modal.
- **Settings page**: Employees see only Appearance (dark mode) and Change PIN. Admins and managers see all cards (App Info, Current User, Printers, Security Settings, Job Folders, Server Connection) — except Data Backup, which stays admin-only. Labour rates & overtime live on their own admin-only page (`/labour-rates`), not on the Settings page.
- Default credentials: `admin` / `1234`
- **No token persistence**: JWT stored in memory only (not localStorage). Users must log in every time they open/refresh the app. Designed for shared workstation security.
- **Inactivity timeout**: Users auto-logout after configurable period of inactivity (default 5 min). Warning modal appears 30 seconds before logout. Activity = mouse, keyboard, touch, scroll. Timer continues when tab is hidden (security for shared workstations).
- **Contact info hidden from non-admin**: All customer/contact data (name, company, phone, email) is stripped from API responses for non-admin users. Server nulls out contact fields in `formatJobcard()`, deletes contact fields from POST/PUT request bodies, and all `/contacts` endpoints require admin. Client hides Customer column in tables, hides Contact section in DetailsTab, and skips contact creation logic in JobCardModal submit.

## Key Patterns

- **Direct API**: All components use `api.js` to communicate directly with the Express server. Components load data on mount and refresh after mutations.
- **JobCardModal**: Modular tab-based UI with custom hooks for each tab's logic (`useCosting.js`, `useTimeEntries.js`, `useTimer.js`, `useJobNotes.js`, `useCamera.js`, `useJobCardForm.js`, `useContactSearch.js`, `useJobFiles.js`, `useActivityLog.js`)
- **Prepared statements**: Database queries use better-sqlite3 prepared statements defined in `database.js`
- **History tracking**: Use `recordHistory()` for server-side data mutations to maintain audit trail
- **Input validation**: Use `express-validator` middleware from `validation.js` for request validation
- **Structured logging**: Use `logger` from `utils/logger.js` instead of `console.error()` for server-side logging
- **Toast notifications**: Use `react-hot-toast` for user feedback instead of `alert()`
- **Modal accessibility**: Use `role="alertdialog"`, `aria-modal="true"`, `aria-labelledby`/`aria-describedby`, focus trap (prevent Tab from leaving), and Escape key handler
- **Auto-formatting on blur**: Name and text fields auto-format when the user leaves the field (`onBlur`). Utilities are in `client/src/utils/formatters.js`:
  - `toTitleCase` — for name fields (person names, company names, display names, tag/label names). Produces "John Snow" style.
  - `capitalizeFirst` — for text fields (descriptions, notes, addresses). Capitalizes only the first letter.
  - Skip formatting for: phone, email, passwords, usernames, reference numbers, dates, numbers, search inputs, file paths.
  - Pattern: `onBlur={(e) => { const f = fn(e.target.value); if (f !== e.target.value) setState(...); }}`

## Architectural Guidelines

### Backward Compatibility via Startup Conversions
- **When a schema or value format changes, ship a one-time startup conversion that folds existing data into the new shape.** This is the single, consistent way we keep existing databases working across changes. Put the conversion in `runMigrations()` (`server/src/db/init.js`) — it runs on every boot, and must be idempotent (a second run finds nothing to convert and is a no-op).
- **Keep runtime code single-path — no backward-compatibility logic in live code** (old-value fallbacks, renamed aliases, dual read paths, etc.). The startup conversion is the *only* place that knows about the old shape; once it has run, every other part of the app only ever sees the new shape.
- **Actively remove legacy code** when replacing a system — delete old files, routes, queries, tables, imports, and exports. Do not leave orphaned code "for reference" or "just in case." The conversion migrates the *data*; the old *code* still goes.
- **Update the seed scripts to the new shape too**, so fresh installs and re-seeds produce new-shape data directly (only existing databases need the conversion).
- Example: removing the `TREATMENT`/`ON_HOLD` job statuses folded them into `AWAITING_MATERIAL` via a startup conversion in `init.js`, while every status list, picker, sort map, and validator was updated to the new set and the old statuses were deleted from the code.

### File Size Limits
- **Maximum 600 lines per file** - Refactor when approaching this limit
- Extract custom hooks when domain logic exceeds ~150 lines
- Split into tab/section components when UI grows complex
- CSS files are exempt (styling can be large)

### Separation of Concerns
- **Custom hooks** (`use*.js`): Encapsulate domain logic (state, handlers, API calls)
- **Constants** (`constants.js`): Enum-like values, dropdown options, form templates
- **Tab/Section components**: Presentational, receive all data via props, minimal logic
- **Orchestrator components**: Coordinate child components, manage shared state

### Naming Conventions
| Type | Convention | Example |
|------|------------|---------|
| Components | PascalCase.jsx | `JobCardList.jsx` |
| Hooks | use*.js | `useTimeEntries.js` |
| Utilities | camelCase.js | `mappers.js` |
| Route files | kebab-case.js | `jobcard-time-entries.js` |
| DB fields | snake_case | `contact_id`, `due_date` |
| All JavaScript code | camelCase | `contactId`, `dueDate` |
| Constants | UPPER_SNAKE_CASE | `JOB_TYPES` |

### Data Flow Convention

**Standard API flow:**
```
User Action → API Request → Express Server → SQLite Database
     ↑                                              ↓
Component ← JSON Response ← Express Response ←──────┘
```

- **Database**: snake_case (SQL convention) - `contact_id`, `due_date`
- **All JavaScript** (API, frontend, form state): camelCase - `contactId`, `dueDate`
- Convert at API boundary (server routes) only

### CRITICAL: Unified camelCase in JavaScript

**ALL JavaScript code uses camelCase - no exceptions:**
```javascript
// API responses
card.jobNumber
card.dueDate
card.contactName

// Form state
formData.jobNumber
formData.dueDate
formData.contactName

// Form field names in JSX
<input name="dueDate" value={formData.dueDate} />
<input name="contactName" value={formData.contactName} />
```

**Server-side: Convert at API boundaries only:**
```javascript
// In route handlers - convert DB snake_case to API camelCase
return {
  jobNumber: row.job_number,    // DB → API
  dueDate: row.due_date,
  contactId: row.contact_id
};

// When saving - API camelCase to DB snake_case
db.run(data.jobNumber, data.dueDate, data.contactId);
```

**Summary:**
| Location | Convention | Example |
|----------|------------|---------|
| Database columns | snake_case | `contact_id`, `due_date` |
| Everything else (JS) | camelCase | `contactId`, `dueDate` |

### Required Patterns
- **Direct API calls**: Use `api.js` methods for all server communication
- **Audit trail**: Call `recordHistory(entityType, entityId, action, userId, userName, changes, snapshot)` for all server-side data mutations. **Action names use present tense**: `'create'`, `'update'`, `'delete'` (not past tense). **IMPORTANT: `changes` must always use `{ field: { from: oldVal, to: newVal } }` format** — this applies to ALL actions including creates, notes, timers, etc. The activity log UI (`formatChanges`) iterates `Object.entries(changes)` and renders `from → to` for each field. If you pass flat data or `null` for changes, nothing will display in the activity log. Only use `snapshot` (7th param) for supplementary context that doesn't need from/to display. Use `req.user.userId` (not `req.user.id`) for the userId parameter.
- **Prepared statements**: Use queries defined in `database.js`, never inline SQL
- **Server error handling**: Try-catch with `logger.error()` from `utils/logger.js`
- **Client error handling**: Use `toast.error()` from `react-hot-toast` (not `alert()`)
- **Input validation**: Use validators from `middleware/validation.js` for new routes
- **Form state**: Single state object + unified `handleChange` handler
- **Data refresh**: Call load function after each mutation to refresh UI
- **React hooks**: Use `useCallback` for functions passed to useEffect dependencies or child components

## Security Features

- **Rate limiting**: Login (first 5 **failed** attempts normal, then 30-second cooldown between attempts; successful login clears failure count; resets after 15 min inactivity) and user creation (10 attempts/15 min) per IP
- **Password policy**: Exactly 4 numeric digits (PIN). Enforced on create user, update user password, and change own password. Not enforced on login.
- **Input validation**: All API inputs validated with express-validator
- **JWT authentication**: Memory-only token storage (no localStorage), role-based access control. Session ends on app close/refresh.
- **Inactivity auto-logout**: Configurable timeout (1-60 min, default 5 min) with 30-second warning modal. Admin configures in Settings. Handles system sleep/wake via visibility API.
- **Audit trail**: All data mutations logged to history table (including failed login attempts)
- **Prepared statements**: All database queries use prepared statements (SQL injection protection)
- **Auto-generated JWT secret**: On first run, a random 256-bit secret is generated via `crypto.randomBytes(32)` and persisted to `data/config.json`. Env var `JWT_SECRET` overrides if set.
- **Secure serving (production HTTPS, self-minted local CA)**: LAN clients (browsers on other PCs) need a *secure context* for the in-app camera (`getUserMedia`) and to avoid "insecure download" blocks on the combined packet — plain `http://<lan-ip>` is neither. So in production (`NODE_ENV=production`, i.e. the packaged app) the server serves **HTTPS**. On first boot `server/src/utils/certs.js` `ensureCertificates(dataDir)` mints a local **certificate authority** (`ca.crt`/`ca.key`, ~10-yr) and a **leaf** signed by it (`server.crt`/`server.key`, ~2-yr, SAN = `localhost` + `127.0.0.1` + every non-internal IPv4 + `os.hostname()`), all under `DATA_DIR` beside `config.json`. Uses `node-forge` (pure JS, no native build). The **CA is minted once and reused forever**; the **leaf is re-minted** only when missing/unreadable or its SAN no longer covers a current LAN IP (IP drift) — the CA never changes, so trust installed on a client keeps holding. Private keys are written `0o600` and **never served** by any route. The HTTPS listener binds `HTTPS_PORT` (443); plain-HTTP **redirect-only** listeners on `80` and `3000` (`config.redirectPorts`) 301 old `http://…:port` links to `https://<host>/…` (no app data on these — a blocked redirect port logs a warning and is non-fatal; the HTTPS listener failing stays fatal). **Dev is unchanged** — plain HTTP on 3000, since Vite's `localhost` is already a secure context. The **packaged app's own window** loads `https://localhost` and trusts our leaf via `session.setCertificateVerifyProc` (scoped to `localhost` + certs chaining to our CA only — not a blanket trust) plus a health poll over HTTPS pinned to our `ca.crt`. **Other PCs must install `ca.crt` once** to clear the browser warning (the planned "Set up this PC" trust step); until then they see a normal cert warning. `client/src/services/api.js` uses a relative `/api` base, so the client inherits HTTPS automatically with no change.
- **Electron server lifecycle**: In production builds, Electron loads the Express server in-process (via `require()`) and uses `Promise.race` between the server startup promise and `/health` polling to detect readiness or failure. `ELECTRON_MODE` env var prevents the server from calling `process.exit()` on failure, letting Electron show an error dialog instead. In dev mode, the server is started separately via `npm start`. **Single-instance lock**: `app.requestSingleInstanceLock()` guards startup — a second launch focuses the existing window and quits instead of starting a duplicate in-process server (which would fail with `EADDRINUSE` on the shared port); the duplicate's `whenReady` also early-returns. An `EADDRINUSE` failure shows a plain "already running / restart the PC" dialog. **No-console safety**: a packaged GUI app has no attached console, so writing to stdout/stderr throws `EBADF` and crashes the process — `client/electron/main.js` wraps `process.stdout/stderr.write` to swallow that (covers `console.*` and the in-process server's plain logs), and `server/src/utils/logger.js` writes JSON logs to a **file** (`[DATA_DIR]/logs/server.log`, `pino.destination` with `sync: true`) in production instead of stdout. The menu bar is hidden (`autoHideMenuBar`, drops down on Alt); Developer Tools are dev-only (no menu item or shortcut in the packaged app).
- **Windows packaging**: `client/package.json` `build` sets `win.signAndEditExecutable: false` (no signing certificate, so the inner exe is neither signed nor rcedit-branded — this also avoids the winCodeSign toolchain). `afterPack` (`client/scripts/rebuild-native.js`) swaps the bundled `better-sqlite3` for Electron's ABI by running `prebuild-install -r electron -t <electronVersion>` (downloads the matching prebuilt binary — no local C++ toolchain needed) rather than compiling via node-gyp.
