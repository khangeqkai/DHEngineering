# Files, printouts and the quality-form workflow

> Detail split out of CLAUDE.md. Read before touching job documents, folders on disk, printing, or quality levels/forms.

## How files are stored on disk

Job card file endpoints (disk-first; one folder per category per job — no DB rows): All routes accept `category` ∈ `{ job-files, qa-form-files, customer-property-files }`, mapped to on-disk subfolders `Job Files`, `QA Forms`, `Customer Property` under `[base]/[Company]/[JobNumber]/`. `GET /jobcards/:id/files/:category` (authenticated, lists files — each file also carries `displayName` (the tag stripped back to the human name), `itemId`, and `itemNumber` telling which part it belongs to, resolved by `resolveFileOwners` in `jobcard-files.js`; a job-level file comes back with `itemId: null`), `GET /jobcards/:id/files/:category/:filename` (authenticated, returns file as base64), `POST /jobcards/:id/files/:category/upload` (authenticated, saves base64 data; body: `{ filename, fileData, itemId? }` — used by both the file picker and camera capture), `POST /jobcards/:id/files/:category/:filename/assign` (authenticated, body `{ itemId?: string|null }` — **re-tags a stored file to a part or back to whole-job by renaming it**: strips the old `[…]` tag and re-writes it as `[p{code}]` for a part or `[{timestamp}]` for whole-job, so the paperwork hub's "For:" picker can move a file between parts and a file added job-level can be tied to a part; a given `itemId` must be a real line item on this job, else 400; records a `reassign_file` history entry. **"Already tagged for this chosen owner" is decided before any rename is attempted** — `currentFileTag(filename) === partFileCode(itemId)` (both read the same trailing `[…]` bracket) — rather than by building the new name and comparing it to the old one: the file already exists on disk under its current name, so asking `buildStorageFilename` to reproduce that same tag always finds a clash (itself) and appends a `(n)`, making a "same owner" case look changed and rename the file plus write a needless `reassign_file` entry every time it was picked), `DELETE /jobcards/:id/files/:category/:filename` (**management** — uploading is open to everyone, but removing a file is not: a file is the job's evidence and deleting one can silently re-open a part's missing-attachment warning, so it follows the same rule as deleting a note. Removes the file from disk and records a `delete_file` history entry carrying its clean display name; 404 when the file isn't there). In the paperwork hub the delete sits as a bin icon on each file row and asks for confirmation inline on the row (`hub-del-confirm`), so the file being removed stays in view while the person answers; the bin is hidden entirely for non-management. Filenames are validated against extension allowlist + path-traversal guards and made collision-free with a ` (n)` suffix. **Naming**: the identifying code rides at the END of the name in square brackets so the human-readable name leads. A file tied to a specific line item (optional `itemId`, the part's permanent `item:` id) is stored as `{name} [p{code}]` where `{code}` is the part's full id reduced to alphanumerics (`idSlug` in `folderCreation.js` — the whole id, not a truncation, so two parts can never collide on it), so the file stays matched to the part even after line items are re-numbered; job-level files (no `itemId`) get a 14-digit timestamp tag `{name} [{timestamp}]` instead. **Returned quality forms** are a special case of job-level files: any upload to the `qa-form-files` folder is renamed to a clean, predictable `Completed Form {N}` (N = one past the highest existing `Completed Form` number in that folder, via `nextQaFormNumber` in `jobcard-files.js`) — dropping whatever the scanner/camera called it — and still gets the timestamp tag appended, so a returned form lands as `Completed Form 1 [{timestamp}].pdf`. The detection of "a completed form came back" is unchanged (still the timestamp tag). The paperwork hub strips that trailing tag from QA-form names for display (`cleanQaName` in `JobPaperworkHub.jsx`), so the list reads `Completed Form 1.pdf`. The missing-file scan matches a part's files by the `[p{code}]` tag at the END of the base name (optionally followed by ` (n)`), before the extension — anchored, not an anywhere-in-name `includes`, so a file whose human-readable name merely contains another part's code can't masquerade as that part's attachment. Base64 uploads are capped at 30 MB (raw bytes); larger payloads are rejected with 400. Every upload is also validated **before any write** by `fileValidation.js`: `decodeBase64Strict` rejects a truncated/scrambled payload (Node's lenient base64 decode would otherwise silently save a broken file), and `assertMatchesExtension` checks the decoded leading bytes match the filename's extension signature — both surface a plain-English 400 so a corrupt upload can't masquerade as a part's attachment. QA template uploads (`POST /qa-levels/:id/templates`) run the same check.

**Automatic folder management**: When `job_folders_base` setting is configured, the system auto-creates `[base]/[Company] [code]/` on company create/update and `[base]/[Company] [code]/[JobNumber]/Job Files/` + `QA Forms/` + `Customer Property/` on job card create. On job card deletion, the job card folder (`[base]/[Company] [code]/[JobNumber]/`) is recursively deleted but the parent company folder is preserved. **Folder identity is the code in the name, not the name itself**: each company folder carries the owning company's full id (reduced to alphanumerics by `idSlug`) at the end of its name in square brackets (e.g. `Rio Tinto Iron Ore [550e8400e29b41d4a716446655440000]`), and the QA-level folders under `[base]/QA Levels/` do the same with the level id. The full id is used (not a truncation) so two folders can never collide on the code. Folder lookups (`findCompanyFolder` / `findQaLevelFolder` in `folderCreation.js`) match by that bracketed code, so renaming a customer/level just renames the folder and never strands its files — there is **no hidden marker file**. For speed, `resolveCompanyFolder` first probes the computed `"Name [code]"` path directly (the usual case, since a rename renames the folder) and only scans the base by code when that path doesn't exist; the probed name always embeds the right code, so the shortcut can never resolve to another customer's folder, and a name that has drifted simply falls through to the code scan. The code makes every folder name unique, so there is no same-name disambiguation. Company names are enforced unique (case-insensitive) at create/update in `companies.js`. Jobs with no linked company fall back to a plain name-built folder (no code). The folder is keyed by **company** id, never the contact person's — the people at a customer change, and a person-keyed folder would split one customer's files in half when they did. Reading or listing files is **never** folder-creating — `resolveCategoryFolder` resolves read-only and the upload path creates the folder chain itself when a file is actually written, so browsing jobs never scatters empty folders on disk. Folder operations are fire-and-forget (errors logged, never block DB operations). Names are sanitized for cross-platform filesystem safety with path traversal protection.

## Printing

Job card printout (per-job): `POST /jobcards/:id/print` (any authenticated user, in `jobcard-printout.js`) — **generates the job card as an HTML page** from the job's current data and returns `{ html }`. There is **no uploaded template and no saved file**: the card is drawn by `renderJobCardHtml` (`server/src/utils/jobCardHtml.js`) from friendly, pre-formatted data built by `buildJobCardView` (`jobcard-helpers.js`, which resolves tag values → names via `tagQueries.getByValue` and formats treatments/dates/priority). It lists exactly the job's parts (no blank rows) and flows onto extra pages for long jobs. The returned HTML is shown as the on-screen card preview in the paperwork hub (`previewCard` in `JobPaperworkHub.jsx`); **printing/saving the card always goes through the combined-packet route** (the same HTML is rendered to PDF server-side by `renderHtmlToPdf` — see the packet route below), so the desktop app and the web build print the identical card. Nothing is written to disk, so the on-screen job stays the single live record. Works whether or not job-folder storage is configured. Records a `jobCardPreviewed` history entry — **this route only builds the on-screen preview, so it is never treated as a real print** (it used to record `jobCardPrinted`, which wrongly told the trail a preview was a print; see the packet route below for what actually counts). The printout is **not** a file category and is **never** part of the missing-attachment warning.

Combined packet printout (per-job): `POST /jobcards/:id/packet` (any authenticated user, in `jobcard-printout.js`) — welds the chosen job documents into **one combined PDF** for printing or saving. Body `{ items: [{category, filename}], includeJobCard?: boolean }` (card defaults in): the big file bytes never travel up — the client sends only the small list of files to include plus the `includeJobCard` flag, and the server reads each chosen file straight off disk **and renders the job card to PDF itself**, so the desktop app and the web build get the identical card-first packet. **Building a packet is neither printing nor saving it, so this route records nothing at all and never stamps `printed_at`.** Both are unfinished when the response is sent: a print still has to reach a viewer, and a save still has to land on disk — on the desktop the user gets a "where do you want to save it?" window *after* the build and can cancel it, so logging a save at build time recorded saves that never happened. It returns `cardIncluded` — true only when the job card is *in the finished document*, which `buildPacketPdf` reports directly (a card that rendered but then failed to merge is skipped-and-reported and comes back `false`, so a job can never be ticked as printed while its card is missing from the bundle). The client confirms the real outcome through one of the two routes below.

Print and save confirmation (two routes, same reason): `POST /jobcards/:id/printed` (any authenticated user, same file) — body `{ cardIncluded?: boolean }`. **Only the client knows whether a built packet ever reached a viewer**, which is why this is a second call: on the desktop the built-in viewer can fail to open, and on the web a blocked pop-up turns the print into a download (a save, not a print). `printPacket` (`usePacketPrint.js`) calls this **only after a viewer actually opened** — `window.electronAPI.openPdf` returned without `success === false`, or `showPdfInBrowser` returned `true` (it now returns whether the tab opened; the pop-up-blocked fallback returns `false` and says so in its toast). Passing `cardIncluded: true` stamps `jobcards.printed_at` with the current UTC ISO moment (`markPrinted` in `db/queries/jobcard.js` — deliberately does not touch `updated_at`, so a print never re-sorts the job list), records a `jobCardPrinted` entry carrying `{ from: previousPrintedAt, to: newMoment }`, and returns it as `printedAt` so the job list can update that row without a re-fetch. Passing `false` (printing with the job card unticked, or a packet whose card was dropped) records an `attachmentsPrinted` entry and returns `printedAt: null`. `POST /jobcards/:id/saved` is its twin for a save: `savePacket` calls it **only once a file really landed** (the desktop save dialog returned un-cancelled, or the browser download fired), and it records a `packetSaved` entry and stamps nothing — a save is not a print and must never tick the Print column. A cancelled save dialog therefore records nothing, which is the point of the split.

The trail entries are deliberately distinct — `jobCardPreviewed` (on-screen preview), `jobCardPrinted`, `attachmentsPrinted`, `packetSaved` — so the trail never calls a non-print a print. **Pre-existing entries are renamed by a startup conversion** (`renameLegacyPrintTrail`, `db/init.js`): the old `jobCardPrinted` was written by the *preview* route and the old `jobCardPacketPrinted` by merely *building* a bundle, so they are rewritten in place to `jobCardPreviewed` and `packetBuilt` respectively. **It is bounded by a cutover moment, not guarded by a done-once flag** — the flag was the bug: after the first boot on this code a `jobCardPrinted` entry is a genuine print, and a flag can go missing (a pass that threw, or a restore that wipes `settings`), so an unbounded second pass silently demoted real prints to previews while the job kept its green tick. The cutover (`print_naming_cutover_at`) is the moment this install first ran the new naming — stored on first use and never recomputed. Unlike `job_folders_base` it belongs to the **data**, not to the machine: a restore keeps **the earlier of ours and the backup's own marker**, because a machine rebuilt today would otherwise rename every genuine print carried by an older install's backup into a preview — the audit record destroyed while the job keeps its tick, the exact disagreement the cutover exists to prevent. Earlier only ever renames fewer rows, the safe direction. If the marker is ever missing it is **not reconstructed from the trail**: the rename stamps new names onto old rows while keeping their original dates, so the earliest new-name entry is the oldest legacy preview, not the cutover. Instead, a trail that already carries a live-written `jobCardPreviewed` (the one new name the rename never produces — `packetBuilt` it does) is left alone and the gap is logged; with no such entry there is nothing to lose (a first run here, or a restored pre-change backup) and the cutover is stamped now. Only entries `created_at` *before* the cutover are rewritten, and an undated row is left alone — mislabelling one costs a word, renaming a genuine print costs the audit record. Bounded this way the pass is idempotent by construction, so it runs on **every boot and at the end of a backup restore** (alongside `normalizeStoredTimestamps` and `foldGoodPiecesToWhole`) — a pre-change backup can't leave the trail calling previews prints until someone next restarts, which on an always-on machine can be days. **A save is only recorded once the file really landed** — on the desktop that means the save window wasn't cancelled; in the browser, that the download wasn't refused (it is handed over after the packet is built, so it is no longer inside the user's click and a strict browser can silently refuse it — the user is told either way, and a refused download records nothing). **Neither confirmation is fire-and-forget:** if the call fails the user is told the print/save wasn't recorded (the packet is open or the file is on disk, so the act itself didn't fail, but nothing was written down and reloading the list won't conjure it). **The print warning names the missing tick only when `cardIncluded` is true** — an attachments-only print never stamps `printed_at`, so promising a tick there sends the user hunting for one that was never due; it says the print wasn't written into the job's activity instead. Neither is ever re-sent — both write a history entry and the print also stamps the job, so a retry would record the same act twice (see the no-automatic-write-retry rule in `docs/notes/client-patterns.md`). This is what the job list's **Print** column reads (`printedAt` on each job, via `formatJobcard`): a green tick once printed, a red cross otherwise, and it never flips back on a later edit. It is **deliberately never backfilled** — older prints predate the field and can't be told apart from a save or an attachments-only print, so every pre-existing job starts with a red cross. The card is rendered by `renderHtmlToPdf` (`server/src/utils/htmlToPdf.js`), which has two Chromium-based paths so the output is identical everywhere: when the server runs in-process inside the **packaged desktop app** (see `client/electron/main.js` `startServer`, production-only) it drives Electron's own off-screen `printToPDF` (bounded by a 30s timeout — `withTimeout` in `htmlToPdf.js` — so a wedged built-in browser can't hang the print forever; on timeout the hidden window is destroyed in the `finally`, which frees the stuck render, and the card is skipped-and-reported as a `'render'` failure like any other); otherwise (**dev — where `npm start` runs the server as a standalone Node process — or a background-only server**) it uses **Puppeteer's bundled headless Chromium** (`puppeteer` dependency in `server/package.json`; one cached browser instance is reused across requests and relaunched if it dies — `scripts/setup.js` `checkPdfBrowser` auto-downloads Puppeteer's Chrome on first setup so the standalone server can render). **Browser location is pinned into the project**: `server/.puppeteerrc.cjs` sets Puppeteer's `cacheDirectory` to `server/.chrome` (gitignored, OS-specific) instead of the default per-user `~/.cache/puppeteer`, so the standalone-server Chrome is tied to the app folder rather than one OS login — it survives a same-OS folder copy and can't be "found under the wrong user". **The engine is verified at startup**: `verifyPdfEngine` (`server/src/utils/pdfEngine.js`) warms the browser via `probeBrowser` (`htmlToPdf.js`) once after `app.listen` (fire-and-forget, never blocks boot); on failure it logs a loud, fixable message and flips a status. That status is surfaced on `GET /health` as `pdfEngine` (`ready` / `unavailable` / `electron` / `pending`). The check is **skipped inside the packaged desktop app** (`electron`), which renders with its own built-in browser. Both use A4 / backgrounds-on / zero-margins. If the card can't be rendered it's **skipped and reported**, never failing the whole packet — a render that failed because the engine couldn't start is reported with `reason: 'engine'` (vs `'render'`) so the paperwork hub shows a specific "couldn't start the PDF engine" message (`reportSkipped` in `usePacketPrint.js`). The packet itself is built by `buildPacketPdf` (`server/src/utils/pdfPacket.js`) with `pdf-lib`: the card goes first, then each file in order — PDFs are merged page-for-page (their own size/orientation preserved, so a landscape A3 drawing stays A3), images are normalised through `sharp` to PNG (every input format works; CMYK/progressive JPEGs that pdf-lib can't embed are handled) and placed one per A4 page scaled to fit. A file that can't be read/decoded is **skipped and reported** in `skipped`, never failing the whole packet; if **nothing** ends up combinable (every document unreadable and no card) the route returns 400 `None of the chosen documents could be combined` with the `skipped` list rather than a generic failure. Each requested filename is verified against the live folder listing (anti-traversal). Caps: ≤20 items, total input read into memory ≤600 MB (summed via `statSync` as files are read, bailing with 413 before crossing it), combined output ≤40 MB (else 413). The paperwork hub mirrors the item cap client-side (`MAX_PACKET_FILES`), disabling the print/save buttons with an "untick N" hint when more than 20 files are ticked.

**Job card printout vs quality forms (two separate features)**: These are deliberately split. (1) The **job card printout** is **generated on demand as an HTML page** from the job's current data (`renderJobCardHtml` + `buildJobCardView`) and printed directly — there is no template to upload and **no saved file**; it lists exactly the job's parts and is never part of the missing-attachment warning. (2) **Quality forms** are per-QA-level inspection PDF templates that are printed, hand-filled, and (for levels with `requires_returned_form` on) scanned back; only those levels drive the missing-quality-form warning, and they still use `fillPdfTemplate`. See the printout endpoint above and the QA workflow below.

## Quality levels and forms

QA level endpoints: `GET /qa-levels` (authenticated, non-admin sees active only), `GET /qa-levels/:id` (admin), `POST /qa-levels` (admin, accepts `requiresReturnedForm`), `PUT /qa-levels/:id` (admin, accepts `requiresReturnedForm`; omitting it leaves the existing value untouched so a name-only edit doesn't flip the switch), `DELETE /qa-levels/:id` (admin, blocked if used by jobs), `POST /qa-levels/:id/templates` (admin, upload PDF — **disk-first, like job files**: the PDF must actually land under `[base]/QA Levels/[Level]/` before the `qa_level_templates` row is added; no `job_folders_base` → 400, folder can't be made or the write fails → 500 with a plain message and **no row**, because a row with no file behind it makes every later job on that level fail `verifyQaTemplatesAvailable`'s pre-save check), `GET /qa-levels/:id/templates` (admin), `DELETE /qa-levels/:id/templates/:tid` (admin). **One name, one form per level**: the file on disk *is* the form, so a second upload under the same sanitized filename is refused with 409 **before any write** — it would overwrite the file and leave two records sharing it, and removing either would take the file away and make every job on that level fail its pre-save check. A one-time startup conversion drops any such duplicate pairs an existing database already holds, keeping the newest of each. Each level carries a `requires_returned_form` flag (default 0): on = a completed quality form must be scanned back before invoicing (drives the missing-quality-form warning); off = print-only.

**"Standard" is the baseline, not a real level**: "Standard" simply means *no special quality level* — it is **never** a row in `qa_levels` and is **not** in the seed data. A job on the baseline has `qa_level_id = NULL` and its `quality_level` label stored as `'STANDARD'`. The admin Quality Levels page therefore only lists the *extra* levels someone creates (e.g. Critical). On the job screen the quality-level picker shows a `Standard` option (value empty = no level) first as the default, followed by the saved levels; choosing Standard clears `qaLevelId` and labels the job `STANDARD`. The server is authoritative: on create/update, no `qaLevelId` ⇒ `quality_level = 'STANDARD'` and `qa_level_id = NULL`; a chosen level ⇒ that level's upper-cased name. A baseline job never has templates and never drives the missing-quality-form warning. The seed script feeds a `{ id: null, name: 'Standard' }` entry to the scenario builder so some seeded jobs sit on the baseline.

**Files & QA workflow**: All job card files live on disk, not in the database. Three category folders per job: `Job Files`, `QA Forms`, `Customer Property` (the job card printout is generated as HTML and printed on demand — it is not a file and is not stored). The QA level system is the only producer of templated content:
1. **Admin creates QA levels** (e.g. "Standard", "Critical") and uploads PDF template forms to each level. Templates stored at `[job_folders_base]/QA Levels/[LevelName]/`.
2. **Job card creation/update with a QA level** copies that level's template PDFs into `[base]/[Company]/[JobNumber]/QA Forms/`, auto-filling fillable form fields with job data via `pdf-lib` (`server/src/utils/pdfFiller.js`). PDFs without fillable fields are copied as-is (blank templates for handwriting). No DB rows are created — the files on disk are the only record. Implemented in `copyQaTemplatesForJob` in `server/src/utils/qaTemplateProvisioning.js` (moved out of `jobcard-helpers.js`, which was getting long; `verifyQaTemplatesAvailable`, the matching pre-save check, lives there too).
3. **Workers print** the pre-filled PDFs, fill inspection results by hand, then bring the completed forms back in via the paperwork hub in the JobCardModal header (each folder section has its own Add file / Camera buttons → file written under the matching folder). Whether a returned form is *required before invoicing* depends on the level's `requires_returned_form` switch (off = print-only, no nag).
4. **All file uploads** (file picker, camera) go through the unified `/jobcards/:id/files/:category/upload` route — same endpoint regardless of source, same disk layout regardless of category.
5. **The paperwork hub** (`JobPaperworkHub.jsx`, opened from a single **Files** button in the JobCardModal header, available to **all** users): one panel listing the generated job card on top plus the three folders (job files, QA forms, customer property), each with thumbnails, per-row View (lightbox for images, inline for PDFs), Print-this-one and (management only) Delete, and per-folder Add file / Camera. Each file row is drawn by `HubFileRow.jsx`. In the **Job Files** and **Customer Property** sections each row also carries a **"For:"** picker (Whole job / Part N) that ties the file to a part — changing it calls the assign route to re-tag the file, which is what clears that part's missing-drawing / missing-customer-property warning (QA forms and the pinned job card have no picker). Only saved parts (with an `item:` id) are offered. Opening the camera always starts with **zero** shots (`openCamera` clears `camera.photos`), so shots from a session abandoned with Back/Escape can't be saved into the next folder opened. Files uploaded via the hub's Add/Camera default to whole-job, unless the hub was opened from a part's Attach button (`openForPart`), in which case that section is highlighted and the next file added there defaults to that part. Everything is pre-ticked; a **Print packet** / **Save as PDF** welds the ticked items (card first) into one combined PDF via `POST /jobcards/:id/packet` (see above). Reuses `useJobFiles` (list/upload/view/thumbnails/`assignFile`/`deleteFile`) + `useCamera`; the build/print/save flow lives in `usePacketPrint.js`. This single hub **replaces** the former header Files menu and the admin-only Files tab (both removed).

Supported PDF field names for templates are defined by `FIELD_MAPPINGS` in `server/src/utils/pdfFiller.js`. The `qualityLevel` column stores the level name; `qa_level_id` is the FK to `qa_levels`.

## Missing-attachment warnings

Attachment-warnings endpoint: `POST /jobcards/attachment-warnings` (authenticated) — per-page check for the job list. Body `{ ids: [jobcardId, ...] }` is the ids of just the rows currently on screen; the scan checks only those (so the cost never grows with the total job count), de-duping and ignoring non-string ids. Returns `{ checked, flagged }` where `checked` is the full list of ids that were looked at (so the list can tell "checked, clean" apart from "not checked yet") and `flagged` carries one entry per checked job that declared a drawing / customer property / quality form but has no matching file on disk (`{ jobcardId, items: [{ itemNumber, position, missingDrawing, missingCustomerProperty }], missingQaForms }`). `position` is the part's 1-based place in this job's own ordered list (item_number ascending) — stated here because this is the one place a caller (the job list) can't work it out for itself: it only ever receives this flagged subset, never each job's full ordered parts, so the server states the number the parts list itself would show instead of leaving the tooltip to name the part by its stored, possibly-gapped `item_number`. Every other place a part is returned (a job card's `items`, the per-part item routes' replies) carries the same `position` field for the same reason — see `docs/notes/jobs-and-status.md`. Missing or archived (invoiced) jobs are treated as checked-clean — included in `checked`, never in `flagged`. A "declared" value is any non-empty drawing/customer-property selection other than the explicit `N_A` ("N/A") answer; a job needs a quality form only if its QA level has a template attached **and** the level's `requires_returned_form` switch is on, and no returned form is in the QA Forms folder — a returned form is detected by the 14-digit timestamp tag the upload route stamps at the end of the name (`[{timestamp}]`, optionally ` (n)`), not by "any file that isn't a template name", so a stray/unrelated upload can't falsely clear the warning. Levels with the switch off are print-only: their templates are still copied/pre-filled on save, but the job never nags for a returned form. The same per-job warning data is also attached to single-job responses as `attachmentWarnings` (on `GET /jobcards/:id`, and on the `PUT /:id` / `PATCH /:id/status` responses). No-ops safely when job-folders storage isn't configured. Used by the job list to mark rows and by the job card screen to show per-part "Attach file" buttons. **The per-part "Attach file" button opens the paperwork hub** pointed at that part (via a `ref` handle `openForPart` on `JobPaperworkHub.jsx`), highlighting the matching folder and defaulting the next file added there to that part — it no longer opens a bare OS file dialog whose upload would land as a whole-job file that never clears the part's warning.
