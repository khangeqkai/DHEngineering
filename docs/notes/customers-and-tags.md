# Customers, contacts and the tag/option system

> Detail split out of CLAUDE.md. Read before touching customers, contact people, dropdown options or per-line-item fields.

## Customer model (a company holds many people)

**Customer model** (a company holds many people): A customer is a **company** (`companies`: `id`, `name` NOT NULL unique case-insensitive, `address`, `notes`, `archived`) and the **contact people** who work there (`contacts`: `id`, `company_id` FK, `contact_name`, `phone`, `email`, `archived` — nothing unique, so Jane can be replaced by Bob without a second Acme). The company owns the customer identity and the folder on disk; a person is only ever read alongside their company, so `contactQueries` all JOIN `companies` and emit `company_name` / `company_archived` (shaped by `toContactApi` in `routes/customer-format.js`, shared with `routes/companies.js` and the search route).

Routes: `/companies` (management) — `GET /` (`?includeArchived=true`, `?withPeople=true` nests each company's people), `POST /`, `PUT /:id`, `POST /:id/archive`, `POST /:id/unarchive`. A person is **only ever read as part of their company** (that one nested call feeds both the Customers page and the job screen's picker), so `/contacts` (management) carries only the writes: `POST /` (requires `companyId`), `PUT /:id` (name/phone/email only — **which company a person belongs to never changes**, since moving them would move who past jobs were taken for; a person who moves firms starts a new record at the new company), `POST /:id/archive` ("retire"), `POST /:id/unarchive`. An existing database is folded into the new shape by the startup conversion `splitCustomersIntoCompanies` (`db/splitCustomers.js`, run from `schema.js` before the contacts indexes and the prepared statements that read the new columns): each old customer row becomes one company plus one person, and the **company keeps the old row's id**, so every job folder on disk still matches by its code and nothing is renamed or moved. It rebuilds the contacts table (SQLite can't drop the old `UNIQUE` company-name column in place, so foreign keys are off for the rebuild), backfills `jobcards.company_id` from `contact_id`, and is idempotent (once `company_name` is gone the block is skipped). Unlike the other conversions it **throws** on failure rather than logging and carrying on — the queries built moments later read columns it creates, so continuing would kill the app with a confusing SQL error instead of the real reason. A backup taken before the split gets the same treatment on import via `splitCustomersInBackup` (same file) — the company again keeps the old row's id, so the company folders inside the same backup still match by their code.

Job cards carry **both**: `company_id` (which folder the job's files live in) and `contact_id` (the person it was taken for), plus the usual **snapshot of company/contact/phone/email onto the jobcard row at creation** (`company_name` / `contact_name` / `contact_phone` / `contact_email`). The snapshot is what all job display, search, and export read — there is no live join back for display — and it is frozen: the server strips `companyId`/`contactId`/`contactName`/`companyName`/`contactPhone`/`contactEmail` on **every** update, for every role. On create the server is authoritative for the company name (it takes `companies.name`, never what was typed) and validates that a named contact actually works at the chosen company; the person's name/phone/email are taken from the request, so a job can record a one-off correction without touching the saved record. The one place a job reads the *live* company is folder resolution (`jobcard-files.js` prefers `companies.name` over the frozen copy), so a renamed customer's files still resolve.

**Editing a customer while creating a job** (`jobCardContact.jsx` + `useContactSearch.js`): the picker is company-first — type the company (autocomplete over the loaded list), pick it, then pick which person there from a dropdown (a company with exactly one person picks them automatically). Their phone and email fill in and **stay editable**. On save: a company that was typed but never picked is offered as a new customer (confirm → `POST /companies`); a person's name typed with nobody picked is added under that company; and if a *picked* person's name, phone or email was changed, a three-way prompt lists each change old → new and offers **Update contact** / **Add as new person** (a second person under the same company — this is the Jane-replaced-by-Bob case) / **Just this job** (the job keeps the typed details, the record is untouched). The third button comes from `showConfirm({ altLabel })` in `useConfirmDialog`, which resolves `'alt'`; every other caller still gets a plain yes/no.

**Customers are archived, never deleted** (track-and-trace): there is no delete route for either a company or a person. Archived companies are hidden from pickers and search but keep their record, their jobs' links, and their files on disk; retired people stop being offered on new jobs while the jobs already taken for them keep their name. The Customers page (`ContactManagement.jsx` + `contacts/CompanyPeople.jsx`) lists companies, and opening one shows its people with add / edit / retire / restore. Its activity log asks for `company,contact` — `GET /history/entity/:entityType` accepts a comma-separated list so the two halves of a customer read as one trail.

## Tags (all dynamic dropdown options)

**Unified tags system**: The `tags` table stores all dynamic dropdown/multi-select options with columns: `id`, `category` (treatment/material/customer_property/drawings/job_type), `name`, `value`, `sort_order`, `archived`, `created_at`. The `supplier_service_tags` junction table links suppliers to treatment tags. Frontend uses the `useTags(category)` hook from `client/src/hooks/useTags.js` to fetch tags dynamically. Admin manages tags and equipment via the "Tags & Equipment" page (`/tags`, with a "Show archived" toggle and a restore button on archived rows). Equipment is managed through the existing `machines` table but shares the same admin UI.

**Archiving options (never delete)**: Options are archived, not deleted — a job stores the option's `value`, so removing the row would strand it on every job that used it. `getByCategory` returns active options only (drives the pickers); `getByCategoryIncludeArchived` returns everything (drives save-validation and display lookups). `useTags` fetches with archived included and exposes `tags` (active-only, for pickers), `labelOf(value)` (resolves any stored value — archived included — to its friendly name), plus `rawTags`/`loading`/`refresh`. A value saved on a job whose option was since archived shows in the field tagged "**(retired)**" in amber (CSS `retired-option` / `has-retired` / `lit-select-btn--retired`) so it stays visible and can be cleared, but retired options are never offered for new work. The same retired treatment shows for an archived **supplier** chosen on a job (job card loads suppliers with archived included). Server-side, `buildGrandfatheredValues` lets a job re-save a value it already held even if the option was archived/renamed away, so editing other fields on an old job never trips validation. Tag history actions are `archive` / `unarchive`.

Tag endpoints: `GET /tags` (authenticated, optional `?category=treatment`, optional `?includeArchived=true`), `GET /tags/categories` (authenticated), `GET /tags/:id` (admin), `POST /tags` (admin, `{ category, name }` — **idempotent create**: a name that maps to an existing option returns that option (200) instead of erroring, so "add on the spot" never makes a duplicate; a matching value that was archived is restored under the freshly typed name), `PUT /tags/:id` (admin, a value-changing rename is blocked for **any** category while job line items still use that value), `DELETE /tags/:id` (admin — **archives**, never hard-deletes; jobs reference options by value, so the row is kept and the `archived` flag is set), `POST /tags/:id/activate` (admin, restores an archived tag)

## Per-line-item fields

**Per-line-item treatments**: Each job item carries a `treatments` JSON column (array of `{ value, supplierId, supplierName }`). `value` is a treatment tag value; `supplierId` is **optional**. The UI is **one treatment + optional supplier per line item** (`tabs/LineItemTreatment.jsx`): the treatment field is a **type-or-create picker** (`common/CreatableTagSelect.jsx`) shown first — it lists **all** active treatments and lets the user add a brand-new one on the spot (dedup-safe: the idempotent `POST /tags` returns the existing option if the typed name already maps to one); the supplier dropdown appears only once a treatment is picked, lists **all** active suppliers (no longer filtered to "offers this treatment"), and can be left as "No supplier". There is **no "Other" free-text treatment** — creating a treatment on the spot replaces it. The `treatments` array holds 0 or 1 entry, but stays an array so costing/PDF-fill/history/export code that iterates it is unchanged. Validated server-side in `validateItemTreatments`: `value` must be a known treatment tag value; a supplier, when given, must exist and be active (the "supplier offers this treatment" check is gone). The same type-or-create picker drives the per-line-item **material** field (`tabs/ItemsTab.jsx`). Suppliers still carry `serviceTags` (managed on the supplier admin page) but they no longer gate the job-screen pickers. This replaces the previous `subcontracts` table — there is no separate subcontract entity, tab, or workflow.

**Per-line-item drawings & customer property**: Each job item also carries `drawings_type` and `customer_property` columns, each a comma-separated string of tag values (categories `drawings` / `customer_property`). Both are required per line item and edited via `tabs/LineItemTagSelect.jsx` (a multi-select tile picker reused for both); the `N_A` ("N/A") tag is mutually exclusive and serves as the explicit "no drawing" / "nothing supplied" answer. Validated server-side in `validateItemDrawings` / `validateItemCustomerProperty`. These used to live as single fields on the `jobcards` table; they now live on `job_items` so each part on a job records its own drawing and physical-reference state. QA-template PDF pre-fill aggregates (de-duped) the values across all items into the job-level `drawingsType` / `customerProperty` fill fields.

**Per-line-item descriptions**: a saved line's description cannot be blanked — the form blocks the save (`jobCardValidation.mjs`) instead of silently dropping the line from the payload, which the server's replace-on-update semantics would treat as a delete of that part (`jobcard-mutations.js` deletes saved parts missing from the save payload; only time-logged lines are guarded). Client-side only — the server does not validate item descriptions. Pinned by `client/scripts/check-jobCardValidation.mjs`.
