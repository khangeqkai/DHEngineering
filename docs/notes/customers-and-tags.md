# Customers, contacts and the tag/option system

> Detail split out of CLAUDE.md. Read before touching customers, contact people, dropdown options or per-line-item fields.

## Customer model (a company holds many people)

**Customer model** (a company holds many people): A customer is a **company** (`companies`: `id`, `name` NOT NULL unique case-insensitive, `address`, `notes`, `archived`) and the **contact people** who work there (`contacts`: `id`, `company_id` FK, `contact_name`, `phone`, `email`, `archived` — nothing unique, so Jane can be replaced by Bob without a second Acme). The company owns the customer identity and the folder on disk; a person is only ever read alongside their company, so `contactQueries` all JOIN `companies` and emit `company_name` / `company_archived` (shaped by `toContactApi` in `routes/customer-format.js`, shared with `routes/companies.js` and the search route).

Routes: `/companies` (management) — `GET /` (`?includeArchived=true`, `?withPeople=true` nests each company's people), `POST /`, `PUT /:id`, `POST /:id/archive`, `POST /:id/unarchive`. A person is **only ever read as part of their company** (that one nested call feeds both the Customers page and the job screen's picker), so `/contacts` (management) carries only the writes: `POST /` (requires `companyId`), `PUT /:id` (name/phone/email only — **which company a person belongs to never changes**, since moving them would move who past jobs were taken for; a person who moves firms starts a new record at the new company), `POST /:id/archive` ("retire"), `POST /:id/unarchive`. A person must carry at least one of name, phone or email — a front desk with only a phone number is fine, a person with none of the three is refused on both create and edit with 400 naming `contactName` ("Enter a name, phone or email"); rows saved before this rule stay and show as "Unnamed". An existing database is folded into the new shape by the startup conversion `splitCustomersIntoCompanies` (`db/splitCustomers.js`, run from `schema.js` before the contacts indexes and the prepared statements that read the new columns): each old customer row becomes one company plus one person, and the **company keeps the old row's id**, so every job folder on disk still matches by its code and nothing is renamed or moved. It rebuilds the contacts table (SQLite can't drop the old `UNIQUE` company-name column in place, so foreign keys are off for the rebuild), backfills `jobcards.company_id` from `contact_id`, and is idempotent (once `company_name` is gone the block is skipped). Unlike the other conversions it **throws** on failure rather than logging and carrying on — the queries built moments later read columns it creates, so continuing would kill the app with a confusing SQL error instead of the real reason. A backup taken before the split gets the same treatment on import via `splitCustomersInBackup` (same file) — the company again keeps the old row's id, so the company folders inside the same backup still match by their code.

Job cards carry **both**: `company_id` (which folder the job's files live in) and `contact_id` (the person it was taken for), plus the usual **snapshot of company/contact/phone/email onto the jobcard row at creation** (`company_name` / `contact_name` / `contact_phone` / `contact_email`). The snapshot is what all job display, search, and export read — there is no live join back for display — and it is frozen: the server strips `companyId`/`contactId`/`contactName`/`companyName`/`contactPhone`/`contactEmail` on **every** update, for every role. On create the server is authoritative for the company name (it takes `companies.name`, never what was typed) and validates that a named contact actually works at the chosen company; the person's name/phone/email are taken from the request, so a job can record a one-off correction without touching the saved record. The one place a job reads the *live* company is folder resolution (`jobcard-files.js` prefers `companies.name` over the frozen copy), so a renamed customer's files still resolve.

**Editing a customer while creating a job** (`jobCardContact.jsx` + `useContactSearch.js`): the picker is company-first — type the company (autocomplete over the loaded list), pick it, then pick which person there from a dropdown (a company with exactly one person picks them automatically). Their phone and email fill in and **stay editable**. A company name typed out exactly as an existing customer's (ignoring capitals and spacing — the shared `sameName` rule in `server/src/shared/names.js`, the same one the server's duplicate check uses) counts as picking that customer — on leaving the box that customer is adopted (its only person is filled in, as a click would, only when the person boxes are empty — details typed by hand are kept, never replaced or blanked), the "Not on the list" hint never shows for it, and the save falls back to the same match — because the server refuses a new customer by that same name rule. On save: a company that was typed but never picked (and matches no customer exactly) is offered as a new customer (confirm → `POST /companies`); a person's name typed with nobody picked is added under that company; and if a *picked* person's name, phone or email was changed, a three-way prompt lists each change old → new and offers **Update contact** / **Add as new person** (a second person under the same company — this is the Jane-replaced-by-Bob case) / **Just this job** (the job keeps the typed details, the record is untouched). The third button comes from `showConfirm({ altLabel })` in `useConfirmDialog`, which resolves `'alt'`; every other caller still gets a plain yes/no.

**Customers are archived, never deleted** (track-and-trace): there is no delete route for either a company or a person. Archived companies are hidden from pickers and search but keep their record, their jobs' links, and their files on disk; retired people stop being offered on new jobs while the jobs already taken for them keep their name. **A person can't be added under an archived company**: `POST /contacts` refuses with `409 { error: "That customer is archived. Restore it before adding people." }` when the target company is archived (matching the wording of the archived-customer refusal on job creation). Which company a person belongs to never changes on `PUT /contacts/:id` (see below), so there is no "move a person into an archived company" path to guard there. The Customers page (`ContactManagement.jsx` + `contacts/CompanyPeople.jsx`) lists companies, and opening one shows its people with add / edit / retire / restore. Its activity log asks for `company,contact` — `GET /history/entity/:entityType` accepts a comma-separated list so the two halves of a customer read as one trail.

## Tags (all dynamic dropdown options)

**Unified tags system**: The `tags` table stores all dynamic dropdown/multi-select options with columns: `id`, `category` (treatment/material/customer_property/drawings/job_type), `name`, `value`, `sort_order`, `archived`, `created_at`. A tag's `value` (the code a job actually saves) is derived from its typed `name` by the one shared `nameToValue` in `server/src/utils/tagSlug.js` — both the live tags route (a new/renamed option) and the seed script read it, so a tag created on the spot and a seeded one always land on the same value shape. The `supplier_service_tags` junction table links suppliers to treatment tags. Frontend uses the `useTags(category)` hook from `client/src/hooks/useTags.js` to fetch tags dynamically. Admin manages tags and equipment via the "Tags & Equipment" page (`/tags`, with a "Show archived" toggle and a restore button on archived rows). Like the other management pages it has an Export (the open tab exactly as listed — one option category, or the machines) and an Activity Log reading `tag,machine` as one trail; every tag trail entry carries a `{ name, category }` snapshot so the log can name the option and its category. **Every save on the page confirms with "… updated"** — adding a new machine or option included ("Machine updated", "Tag updated"). This is the chosen wording, not a slip; don't "fix" an add to say created/saved. Equipment is managed through the existing `machines` table but shares the same admin UI. A machine number may not contain a comma — logged work stores several machines as one comma-joined string, so "CNC,01" would read back as two machines; the machine checks (`validateCreateMachine`/`validateUpdateMachine`) and the Equipment form read the separator from `shared/machineList.js`, and start-up only logs any pre-existing one (logged work is never rewritten). Machine numbers are never reused in this workshop (owner decision), so Workshop Statistics crediting logged hours by machine number rather than by machine record is intended, not a bug. The Equipment form edits the description too; a machine update that leaves `description` out keeps the stored one.

**Changing a tag refreshes every list showing it, without the caller having to ask.** `useTags.js` keeps a subscriber set per category: each mounted `useTags(category)` instance registers itself on mount and unregisters on unmount. The four writes — create, update, archive, restore — are exported as `tagActions` (`useTags.js`), each calling the matching `api` method, then dropping that category's cache and notifying its subscribers, then returning the api result (failures propagate to the caller unchanged, so it keeps its own toast). Every caller that changes a tag — `TagManagement.jsx` (create/update/archive/restore), `common/CreatableTagSelect.jsx` (create on the spot), `SupplierManagement.jsx` (add custom service, archive service) — goes through `tagActions` rather than calling `api.createTag`/`updateTag`/`archiveTag`/`activateTag` directly; those four api methods are called from `useTags.js` only. This replaces the old `invalidateTagCache`, which only dropped the cache — a list already on screen kept showing the stale options until it happened to re-render for some other reason. A screen's own local list update (e.g. `SupplierManagement`'s `setServiceTags`) can still run alongside `tagActions`, for the one screen that changed the tag; the subscriber notification is what catches up every *other* screen showing the same category.

**Archiving options (never delete)**: Options are archived, not deleted — a job stores the option's `value`, so removing the row would strand it on every job that used it. `getByCategory` returns active options only (drives the pickers); `getByCategoryIncludeArchived` returns everything (drives save-validation and display lookups). `useTags` fetches with archived included and exposes `tags` (active-only, for pickers), `labelOf(value)` (resolves any stored value — archived included — to its friendly name), plus `rawTags`/`loading`/`refresh`. A value saved on a job whose option was since archived shows in the field tagged "**(retired)**" in amber (CSS `retired-option` / `has-retired` / `lit-select-btn--retired`) so it stays visible and can be cleared, but retired options are never offered for new work. The same retired treatment shows for an archived **supplier** chosen on a job (job card loads suppliers with archived included). Server-side, `buildGrandfatheredValues` lets a job re-save a value it already held even if the option was archived/renamed away, so editing other fields on an old job never trips validation. Tag history actions are `archive` / `unarchive`.

Tag endpoints: `GET /tags` (authenticated, optional `?category=treatment`, optional `?includeArchived=true`), `GET /tags/categories` (authenticated), `GET /tags/:id` (admin), `POST /tags` (admin, `{ category, name }` — **idempotent create**: the same name (capitals and spacing ignored, `sameName`) as an existing option returns that option (200) instead of erroring, so "add on the spot" never makes a duplicate; a matching value that was archived is restored under the freshly typed name. The code drops decimal points, fractions, accents and symbols, so two different names can share one code — "M6 x 1.0" / "M6 x 10", "Plate ½" / "Plate ¼" — and a name that shares an option's code **without** being the same name is refused with a message naming that option, never handed the other option), `PUT /tags/:id` (admin, a rename is blocked for **any** category while job line items still use that value when it changes the value **or** really changes the name (anything beyond capitals/spacing) — a same-code rename relabels every job using it; a name sharing another option's code is refused naming it), `DELETE /tags/:id` (admin — **archives**, never hard-deletes; jobs reference options by value, so the row is kept and the `archived` flag is set), `POST /tags/:id/activate` (admin, restores an archived tag)

**One archive/restore action for every archived entity.** Companies, contacts, machines, suppliers, tags and users all archive/restore through the same `setArchived` helper (`server/src/utils/archiveToggle.js`): missing row → 404; already in the target state → the success reply is sent as-is, with nothing written and no trail entry (this is the one place the behaviour was tightened — a repeat archive/restore call used to still write a duplicate `archive`/`unarchive` trail entry on some of these entities); otherwise the write happens and one `recordHistory(..., 'archive' | 'unarchive', ...)` entry is left with `{ status: { from, to } }`. That change alone doesn't say *which* record, so every caller must pass a `snapshot` naming it (the helper throws without one): the customer's name, the customer + person name for a contact, the option's name, the supplier's name, the machine, the user. Route-specific refusals (the last-admin/self-archive/admin-account guards on users, the "another active machine now has this number" restore refusal on machines) stay in the route, checked before the shared action runs.

## Suppliers

**Suppliers are validated and de-duplicated like customers.** `POST /suppliers` and `PUT /suppliers/:id` (`server/src/routes/suppliers.js`) run `validateCreateSupplier` / `validateUpdateSupplier` (`middleware/validation.js`) — name required and non-blank (trimmed; on an edit it may be left out, see "Edits send only what changed" below), plus `optionalEmail('contactEmail')` / `optionalPhone('contactPhone')` — before touching the database, mirroring `validateCreateContact`/`validateUpdateContact`. Supplier names — like customer names and quality-level names — are matched by the shared `sameName` rule (`server/src/shared/names.js`: capitals, surrounding and repeated spaces ignored, so "acme  coatings" clashes with "Acme Coatings"; found by `findNameClash` in `routes/name-conflict.js`, a scan because SQL can't collapse spaces, and on an edit only checked when the name really changes) and a clash returns 409, archived-aware just like companies: `'A supplier with this name already exists'`, or `'…in the archive. Restore it from the archived list instead.'` when the clashing row is inactive (`active = 0`). The same shared reply (`nameConflictOr409`) is used by `POST /auth/users` for a username clash (`'A user with this username already exists'`, or the archive/restore wording when the matching account is archived); every such 409 also carries `fields: [{ field, message }]` (`name`, or `username` for users) — the validation step's shape — so the form marks the name box rather than popping the message up. There is **no** database `UNIQUE` constraint on the name — only the route-level check — since an existing database may already hold duplicates from before this rule.

**A refusal about one box names that box.** Every single-box refusal on these management routes — the name clashes above, and the dropdown-option refusals in `routes/tags.js` (blank or symbol-only name, a code clash, "already has this name", a retired option holding it, "Cannot rename: N job part(s)…") and the machine-number ones in `routes/machines.js` (already in use, renumbering a machine with logged work) — goes through `refuseField` in `routes/name-conflict.js`, which sends `{ error, fields: [{ field, message }] }` (`name`, or `machineNumber`). The forms mark the box; the job screen's own option picker, which has no form box, still pops the message up. The job screen's part supplier picker judges a typed name with the same shared `sameName` rule against every supplier, archived ones included: an archived match shows a "restore it on the Suppliers page" hint instead of offering "Create …".

**Edits send only what changed.** The management edit forms — Users, the Customers company form, a customer's person, Suppliers and Equipment — remember what they opened with and send only the boxes the person changed (`client/src/utils/changedFields.js`); a whole-form send from a copy opened earlier used to put back whatever someone else changed meanwhile (on Users, a role). So `PUT /auth/users/:id`, `PUT /companies/:id`, `PUT /contacts/:id`, `PUT /suppliers/:id` and `PUT /machines/:id` all keep any field left out of the request; a sent field, blank included, replaces it (a name or machine number can't be sent blank).

## Per-line-item fields

**Per-line-item treatments**: Each job item carries a `treatments` JSON column (array of `{ value, supplierId, supplierName }`). `value` is a treatment tag value; `supplierId` is **optional**. The UI is **one treatment + optional supplier per line item** (`tabs/LineItemTreatment.jsx`): the treatment field is a **type-or-create picker** (`common/CreatableTagSelect.jsx`) shown first — it lists **all** active treatments and lets the user add a brand-new one on the spot (dedup-safe: the idempotent `POST /tags` returns the existing option if the typed name already maps to one); the supplier dropdown appears only once a treatment is picked (`tabs/LineItemSupplierPicker.jsx`): an empty box lists the suppliers tagged for the part's treatment, typing searches all active suppliers, any supplier may be chosen either way, and it can be left as "No supplier". There is **no "Other" free-text treatment** — creating a treatment on the spot replaces it. The `treatments` array holds 0 or 1 entry, but stays an array so costing/PDF-fill/history/export code that iterates it is unchanged. Validated server-side in `validateItemTreatments`: `value` must be a known treatment tag value; a supplier, when given, must exist and be active (the "supplier offers this treatment" check is gone). The same type-or-create picker drives the per-line-item **material** field (`tabs/ItemsTab.jsx`). Suppliers still carry `serviceTags` (managed on the supplier admin page), which set the empty box's default list above; typing past that list and picking a supplier that doesn't yet carry the treatment tags it onto that supplier, so future filtering learns it. That link goes through its own narrow action, `POST /suppliers/:id/service-tags` with `{ tagId }` (management-only, idempotent), which adds the one service and touches nothing else — it used to re-send the whole supplier through `PUT /suppliers/:id` from the job screen's long-lived (and, for a worker, contact-blanked) copy, reverting other people's edits to the supplier. This replaces the previous `subcontracts` table — there is no separate subcontract entity, tab, or workflow.

**Per-line-item drawings & customer property**: Each job item also carries `drawings_type` and `customer_property` columns, each a comma-separated string of tag values (categories `drawings` / `customer_property`). Both are required per line item and edited via `tabs/LineItemTagSelect.jsx` (a multi-select tile picker reused for both); the `N_A` ("N/A") tag is mutually exclusive and serves as the explicit "no drawing" / "nothing supplied" answer. Validated server-side in `validateItemDrawings` / `validateItemCustomerProperty`. These used to live as single fields on the `jobcards` table; they now live on `job_items` so each part on a job records its own drawing and physical-reference state.

**Per-line-item descriptions**: a saved line's description cannot be blanked — the form blocks the save (`jobCardValidation.mjs`) instead of silently dropping the line from the payload, which the server's replace-on-update semantics would treat as a delete of that part (`jobcard-mutations.js` deletes saved parts missing from the save payload; only time-logged lines are guarded). Client-side only — the server does not validate item descriptions. Pinned by `client/scripts/check-jobCardValidation.mjs`.

**A new job's typed-in contact is checked; a picked person's own saved details are not re-checked.** `POST /jobcards` runs `validateJobcardContactFields` (`middleware/validation.js`) — a plain chain (`contactName` length, `optionalEmail('contactEmail')`, `optionalPhone('contactPhone')`) that checks only whatever the body actually carries. **Picking a saved person copies their stored phone/email as-is**: `buildJobcardPayload` (client) sends `contactName`/`contactPhone`/`contactEmail` only for the ones that differ from the picked person (`detailChanges`) and leaves the rest out of the body; on the server, `jobcard-mutations.js` fills each field the body left out (`undefined`) straight from the saved contact row (`contact.contact_name` / `contact.phone` / `contact.email`) rather than validating it, so a person saved before the phone/email rules existed — or holding a number/address the rule would now refuse — is never blocked from being picked for a new job. A field that IS sent — typed for a walk-in with no `contactId`, or changed from the picked person's own value — is validated as usual, and the screen marks the box instead of a pop-up when it fails. This replaces the old `isPickedContactsOwnPhone` exact-match skip, which only ever covered the phone field and only when the typed value matched the saved one byte-for-byte.
