# Sign-in, sessions and security

> Detail split out of CLAUDE.md. The role/permission *policy* stays in CLAUDE.md; this file carries how it is enforced and the traps around sessions.

## Roles are read live, never from the pass

- **Role is read live, never from the token**: the JWT carries identity only (`userId`/`username`/`name`/`sessionToken`) — **no `role` claim**. `authenticate` reads `role` from the DB row it already fetches for the session/active check (`userQueries.getAuthState`, extended to select `role`) and builds `req.user` explicitly from named fields, so a token can never supply a stale access level. A role change therefore applies on the **very next request** instead of at next sign-in — no forced sign-out. The client follows within one poll tick (~5s): `AuthContext`'s session poll compares the role from `GET /auth/me` against the one it holds and calls `applyRole` (role-only on purpose — blanket-adopting the fresh profile would clobber an in-flight `updatePreferences` save) plus a plain-language toast. Everything downstream is derived in render, so it self-corrects: the route guards in `App.jsx` navigate a demoted admin off `/labour-rates` or `/activity`, nav/columns/tabs re-gate, and the inactivity timer re-arms for someone dropped out of admin. Three spots need explicit handling because they don't re-derive on their own — `JobCardModal` clamps `activeTab` back to Details when admin access is lost mid-modal (its tab-reset effect only runs on open); `useSearch` takes the role as an argument and, on any change, calls `changeScope('all')` + bumps `refreshKey` (the scope tabs re-gate by themselves, but already-fetched rows would otherwise linger on screen carrying costing/contact data the new role can't see, since the fetch effect keys off query/filters/page only — the `refreshKey` bump also advances `requestId`, so an in-flight reply to the old role's query can't paint over the cleared results); and `UserManagement.handleSubmit` short-circuits after a **self** role change **only when the new role drops out of management** (the page sits behind `ManagementRoute`, so an admin→manager self-demotion stays put and must still reload the list, or it keeps showing them as an admin on a row `isAdmin` now renders unclickable).

## What each role sees

- **Employee (user) role**: Read-only job card view (Details tab renders as styled text, not inputs) except status dropdown (employees can change job status via `PATCH /:id/status`, but cannot set status to INVOICED — management-only). Employees see no tab strip — only the Details content renders, with line items + per-item Progress inlined. Managers see no tab strip either — the strip only appears for true admins (Details + Costing + Activity); the Costing and Activity tabs and their data loads are gated on true admin, and the per-job Activity trail carries pricing changes so it stays admin-only. The paperwork hub is reachable by all users (read+write — anyone assigned to a job can upload to its folders). The Costing tab is pricing-only (rates, totals); all time-entry CRUD lives in the Details tab via per-item Progress (`LineItemProgress.jsx` inside `ItemsTab.jsx`). Employees use Start/Stop timer for time tracking (one active timer at a time, enforced server-side). Can add notes but not delete them. **Paperwork hub**: a single **Files** button in the JobCardModal header opens the hub (`JobPaperworkHub.jsx`) — the one place to view/upload/print a job's documents (job card + Job Files / QA Forms / Customer Property), with per-folder Add file / Camera and combined-packet print/save. Uploads go to the matching folder via `/jobcards/:id/files/:category/upload`. Active timers show a pulsing green indicator on job card rows for all users.

- **Job card visibility**: All authenticated users can see and access all job cards (same visibility as admin). Non-admin users remain read-only with limited actions (status change, timer, notes, self-assign). Non-admins can add/remove **only themselves** via the Assigned-To column popover (`POST`/`DELETE /jobcards/:id/assignees/self`); admins still manage the full assignee list via the modal.

- **Settings page**: Employees see only Appearance (dark mode) and Change PIN. Admins and managers see all cards (App Info, Current User, Printers, Security Settings, Home Access, Server Connection) — except Job Folders and Data Backup, which stay admin-only. Labour rates & overtime live on their own admin-only page (`/labour-rates`), not on the Settings page.

## Sessions and signing out

Auth sub-routes: `PUT /auth/change-password` (all authenticated users, verifies current password — **the only way to change your own PIN**: `PUT /auth/users/:id` refuses a `password` for the caller's own account with 403, so someone who walks up to a signed-in session can't set a new PIN without knowing the old one and lock the owner out; resetting *someone else's* PIN there is still management's job), `POST /auth/logout` (all authenticated users — **clears `users.session_token`**, so the JWT the person was holding is rejected by `authenticate` from the very next request instead of staying valid until it expires; records a `logout` history entry)

- **Signing out ends the session on the server, not just on the screen**: signing out is **two beats**, because the moment the server tears the session marker up anything still in flight is refused — and one of the `registerBeforeLogout` callbacks puts a half-stopped timer *back on the clock* (`useTimer.js`), so cancelling first silently loses the worker's run. `api.beginLogout()` forgets the in-memory token **immediately** and returns the server-side cancel as a function; `logout` in `AuthContext` fires the before-logout callbacks first, collects whatever promises they hand back, and only calls that function once they settle (capped by `BEFORE_LOGOUT_GRACE_MS`, 3s, so an unanswering server can't hold the sign-out open). The cancel `POST`s `/auth/logout` with the token it captured, wiping the marker server-side (`updateSessionToken.run(null, ...)`), so the JWT the person was holding is rejected by `authenticate` from the very next request. Two details are load-bearing: the captured token means signing **back in** inside the grace window can't cancel the *new* session, and the cancel is sent with a **plain `fetch`, not `_send`** — routed through the shared sender its 401 (the marker has since been replaced by that new sign-in) would reach the forced-sign-out handler and sign the new person straight out. `beginLogout` also sets `sessionInvalidated` so a request that was already in flight can't come back as the "signed in from another device" toast; the flag is re-armed by `setToken` on the next sign-in. `api.logout()` remains as the fire-it-now form. Nothing blocks the local sign-out — a server that isn't answering still signs the person out here. `maintenanceGuard` lets `/auth/logout` through during a restore alongside `/auth/login`: it touches only that person's own session marker, which a restore replaces wholesale anyway, and refusing it would leave them looking signed out while the server still honoured their pass.

- **A page restored by the Back button is signed out**: a browser can keep a whole page alive when you navigate away and hand it back — JavaScript memory included — on Back, which on a shared workstation restored the previous person still signed in (the in-memory token survives, and the inactivity timer is frozen while the page is parked, so it never fires). `AuthProvider` listens for `pageshow` and signs out whenever `event.persisted` is true, with a plain-language toast. A normal Sign Out was already safe: the route guards render `<Navigate to="/login" replace />`, so Back can't re-enter (and `replace` keeps a redirect from stacking history entries).

- **Inactivity timeout**: Users auto-logout after configurable period of inactivity (default 5 min). Warning modal appears 30 seconds before logout. Activity = mouse, keyboard, touch, scroll. Timer continues when tab is hidden (security for shared workstations). **Admins are exempt** — the timer is disabled entirely for `role === 'admin'` (no countdown, no warning modal), since the timeout targets shared shop-floor workstations; managers and employees are still timed out.

- **Every dead-pass 401 carries a code, and the client signs the person out on it**: `authenticate` answers `TOKEN_EXPIRED` / `TOKEN_INVALID` alongside the existing `SESSION_REPLACED` / `ACCOUNT_DEACTIVATED`, and `SIGNED_OUT_MESSAGES` in `client/src/services/api.js` is the single list of those codes and the plain-English wording each one shows (shared with `AuthContext`, so the toast and any thrown `err.message` can never disagree). A 401 whose code is in that list triggers the forced sign-out. Without `TOKEN_EXPIRED` there, an admin — who is exempt from the inactivity timeout — could sit on a session past its expiry and watch every action fail silently instead of being told to sign in again.

- **JWT authentication**: Memory-only token storage (no localStorage), role-based access control. The token carries **identity only** — the role is looked up from the database on every request, so changing someone's role takes effect immediately rather than at their next sign-in (see the roles section of `CLAUDE.md`). Session ends on app close/refresh.

- **Auto-generated JWT secret**: On first run, a random 256-bit secret is generated via `crypto.randomBytes(32)` and persisted to `data/config.json`. Env var `JWT_SECRET` overrides if set.

## Login throttling

- **Rate limiting**: Login (first 5 **failed** attempts normal, then 30-second cooldown between attempts; successful login clears failure count; resets after 15 min inactivity). The attempt is **counted up front, before the password comparison** — that comparison yields, so counting the failure afterwards left a window in which a whole burst of guesses passed the check together and one cooldown wait bought unlimited tries; a successful sign-in clears the count as before. Plus user creation (10 attempts/15 min) per IP. The server sets `trust proxy` to `loopback` (`server/index.js`), so a request forwarded by a Cloudflare Tunnel (`cloudflared` runs on the host and hands visitors to `localhost`) is keyed on the real home user via `X-Forwarded-For` instead of every home user sharing the loopback address; the header is only honoured from this machine, so a LAN client can't fake it. The login throttle itself is keyed on `clientIp(req)` (`utils/homeAccess.js`): the **rightmost** untrusted forwarded entry, i.e. the one Cloudflare appended, because Cloudflare appends the real visitor to any `X-Forwarded-For` the visitor sent and Express's `req.ip` would take the leftmost — a visitor could otherwise dodge the throttle by faking a fresh header each try

## Contact details are hidden from non-management

- **Contact info hidden from non-admin**: All customer/contact data (name, company, phone, email) is stripped from API responses for non-admin users. Server nulls out contact fields in `formatJobcard()`, deletes contact fields from POST/PUT request bodies, and all `/contacts` endpoints require admin. Client hides Customer column in tables, hides Contact section in DetailsTab, and skips contact creation logic in JobCardModal submit.

## Other protections

- **Inactivity auto-logout**: Configurable timeout (1-60 min, default 5 min) with 30-second warning modal. Admin configures in Settings. Handles system sleep/wake via visibility API. Does not apply to admin accounts (see the roles section of `CLAUDE.md`).

- **Signed-in replies are never stored by the browser**: a small middleware sets `Cache-Control: no-store` on everything under `/api` (mounted in `server/index.js` before the API routers). Express sends no cache headers of its own, so a browser was free to keep authenticated JSON on disk under heuristic freshness and hand it back on a shared machine after the next person signed in.

## Home access (reaching the app from outside the office)

- **Home access (Cloudflare Tunnel, customer's own domain)**: the app can be reached from outside the office through a named Cloudflare Tunnel (`cloudflared`) installed as a Windows service on the host, forwarding `https://jobs.<domain>` → `https://localhost:443` with *No TLS Verify* on (our leaf is self-minted). The full one-time setup is in `jobcard-system/HOME-ACCESS.md` (the workshop-day checklist is at the bottom of `instruction.md`); `jobcard-system/setup-home-access.bat` self-elevates, downloads `cloudflared`, prompts for the tunnel key and installs the service in one go. Nothing is opened on the router and nothing is installed on home PCs. App side: `server/src/utils/homeAccess.js` `isViaTunnel(req)` (`req.ips.length > 0`, which with `trust proxy = loopback` is only true for a proxy on this machine) tells a tunnel visitor apart from an office one; `/health` carries `viaTunnel` so the login screen shows a third **Home access code** box only to tunnel visitors. **The code is the real lock**: `PUT /settings` `homeAccessCode` (admin-only, 8 chars to 72 bytes — bcrypt reads no further, stored bcrypt-hashed as `home_access_code`, blank = off; the hash is stripped from `GET /settings`, which returns `homeAccessCodeSet` instead) and `POST /auth/login` from the tunnel refuses with 403 when no code is set and 401 (counted as a login failure) when the code is wrong — checked **before** the PIN is looked at. Office/LAN sign-ins never see or need it. `homeAddress` (`home_address`, admin-only, display-only text) is the address staff type from home, shown on the **Home Access** card in Settings (`settings/HomeAccessCard.jsx`; any manager can read it, only an admin can set it or the code). The validation/view helpers live in `routes/settings-home-access.js` (`HOME_ACCESS_BODY_KEYS` gates managers with 403, `HOME_ACCESS_SECRET_KEYS` strips secrets, `collectHomeAccessUpdates`, `homeAccessView`).
