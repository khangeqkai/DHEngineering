# Sign-in, sessions and security

> Detail split out of CLAUDE.md. The role/permission *policy* stays in CLAUDE.md; this file carries how it is enforced and the traps around sessions.

## Roles are read live, never from the pass

- **Role is read live, never from the token**: the JWT carries identity only (`userId`/`username`/`name`/`sessionToken`) — **no `role` claim**. `authenticate` reads `role` from the DB row it already fetches for the session/active check (`userQueries.getAuthState`, extended to select `role`) and builds `req.user` explicitly from named fields, so a token can never supply a stale access level. The **display name** (and username) on `req.user` come from that same row too, not from the token's `name`, so a person renamed while signed in writes comments and trail entries under the new name on their very next request (the user rename only folds *existing* comments onto the new name — anything written afterwards under a token-held old name would have stayed stale for good). A role change therefore applies on the **very next request** instead of at next sign-in — no forced sign-out. The client follows within one poll tick (~5s): `AuthContext`'s session poll compares the role and display name from `GET /auth/me` against the ones it holds and calls `applyIdentity` (role and name only, on purpose — blanket-adopting the fresh profile would clobber an in-flight `updatePreferences` save), plus a plain-language toast when the role changed (a rename alone just updates the name on screen); `UserManagement`'s own-account save adopts the same two fields through it. Everything downstream is derived in render, so it self-corrects: the route guards in `App.jsx` navigate a demoted admin off `/labour-rates` or `/activity`, nav/columns/tabs re-gate, and the inactivity timer re-arms for someone dropped out of admin. Three spots need explicit handling because they don't re-derive on their own — `JobCardModal` clamps `activeTab` back to Details when admin access is lost mid-modal (its tab-reset effect only runs on open); `useSearch` takes the role as an argument and, on any change, calls `changeScope('all')` + bumps `refreshKey` (the scope tabs re-gate by themselves, but already-fetched rows would otherwise linger on screen carrying costing/contact data the new role can't see, since the fetch effect keys off query/filters/page only — the `refreshKey` bump also advances `requestId`, so an in-flight reply to the old role's query can't paint over the cleared results); and `UserManagement.handleSubmit` short-circuits after a **self** role change **only when the new role drops out of management** (the page sits behind `ManagementRoute`, so an admin→manager self-demotion stays put and must still reload the list, or it keeps showing them as an admin on a row `canManageAdmins` now renders unclickable).

## The last admin can't be demoted

- **`PUT /auth/users/:id` refuses to demote the only admin**: when the target account is currently `admin`, the request is setting a different `role`, and no *other* active admin exists (`userQueries.countOtherActiveAdmins`, active admins excluding the target id), the server returns 400 `{ error: 'This is the only admin account. Make another person an admin first.' }` **before any write** — checked whether the caller is demoting themselves or someone else. With nobody else in the role, there would be no one left who could grant it back — costing, backups, the job-folders path and every other admin-only surface would become permanently unreachable. The deactivate route already can't archive yourself and only an admin can archive an admin account, so it needed no equivalent guard.

## What each role sees

- **Employee (user) role**: Read-only job card view (Details tab renders as styled text, not inputs) except status dropdown (employees can change job status via `PATCH /:id/status` — the only status-changing route a non-management user can reach at all, since `PUT /:id` is management-only end to end — but only **to** `IN_PROGRESS`/`AWAITING_MATERIAL` and only **from** `OPEN`/`IN_PROGRESS`/`AWAITING_MATERIAL` — everything else, including INVOICED, is management-only; see `canSetStatus` in `docs/notes/jobs-and-status.md`). Employees see no tab strip — only the Details content renders, with line items + per-item Progress inlined. Managers see no tab strip either — the strip only appears for true admins (Details + Costing + Activity); the Costing and Activity tabs and their data loads are gated on true admin, and the per-job Activity trail carries pricing changes so it stays admin-only. The paperwork hub is reachable by all users (read+write — anyone assigned to a job can upload to its folders). The Costing tab is pricing-only (rates, totals); all time-entry CRUD lives in the Details tab via per-item Progress (`LineItemProgress.jsx` inside `ItemsTab.jsx`). Employees use Start/Stop timer for time tracking (one active timer at a time, enforced server-side). Can add notes but not delete them. **Paperwork hub**: a single **Files** button in the JobCardModal header opens the hub (`JobPaperworkHub.jsx`) — the one place to view/upload/print a job's documents (job card + Job Files / QA Forms / Customer Property), with per-folder Add file / Camera and combined-packet print/save. Uploads go to the matching folder via `/jobcards/:id/files/:category/upload`. Active timers show a pulsing green indicator on job card rows for all users.

- **Job card visibility**: All authenticated users can see and access all job cards (same visibility as admin). Non-admin users remain read-only with limited actions (status change, timer, notes, self-assign). Non-admins can add/remove **only themselves** via the Assigned-To column popover (`POST`/`DELETE /jobcards/:id/assignees/self`); admins still manage the full assignee list via the modal.

- **Settings page**: Employees see only Appearance (dark mode) and Change PIN. Admins and managers see all cards (App Info, Current User, Printers, Security Settings, Home Access, Server Connection) — except Job Folders and Data Backup, which stay behind the `systemData` permission. Labour rates & overtime live on their own `pricing`-permission page (`/labour-rates`), not on the Settings page. **`GET /settings` (`routes/settings.js`) strips both the money and the job-folders keys when the caller lacks the matching permission** (a manager passes `requireManagement` to reach the route at all, but reads it as if those keys were never set): the overtime/labour-rate keys (`OVERTIME_DB_KEYS`, from `settings-overtime.js`) are dropped for anyone without `pricing`, and `job_folders_base` for anyone without `systemData` — both `can(role, permission)` checks from `middleware/auth.js`, each `delete`d from the settings object before it's converted to camelCase and sent — so a manager's session never even receives the job-folders path, not just gets a UI that hides it. `PUT /settings` rejects both the same way (403) if a manager's body carries them.

## Editing an account

- **`PUT /auth/users/:id` is management-only, full stop** — `requireManagement` gates the whole route, so a non-management caller gets 403 before the handler even runs, including for their own account. There used to be a self branch that let anyone rename or re-email their own account here (the only fields it let self through for, since self-password is refused below and self-role-change was already blocked) — that was the bug: a worker could rename or re-email themselves. Once name/email are off-limits to self too, nothing useful was left for a non-management caller on this route, so it went management-only rather than keeping a self branch with nothing left to do. Everything management could already do — edit anyone's name/email/role, reset a password, the admin-only and last-admin guards below — is unchanged.
- **Field checks on update mirror create**: `validateUpdateUser` (`middleware/validation.js`, beside `validateCreateUser`, reusing its helpers) checks `name` (optional, same length cap) and `email` (optional, valid format, lower-cased only — never `normalizeEmail()`, so a typed address is never silently rewritten) before the route's own inline password (exactly 4 digits — the one shared `isValidPin`/`PIN_MESSAGE` in `server/src/shared/pin.js`, read by `middleware/validation.js` for create/update and by the client's own pre-save check in `client/src/utils/formatters.js`) and role (`admin`/`manager`/`user`) checks run.

## Sessions and signing out

Auth sub-routes: `PUT /auth/change-password` (all authenticated users, verifies current password — throttled like sign-in, see "Login throttling" below — **the only way to change your own PIN**: `PUT /auth/users/:id` refuses a `password` for the caller's own account with 403, so someone who walks up to a signed-in session can't set a new PIN without knowing the old one and lock the owner out; resetting *someone else's* PIN there is still management's job), `POST /auth/logout` (all authenticated users — **clears `users.session_token`**, so the JWT the person was holding is rejected by `authenticate` from the very next request instead of staying valid until it expires; records a `logout` history entry)

- **Signing out ends the session on the server, not just on the screen**: signing out is **two beats**, because the moment the server tears the session marker up anything still in flight is refused — and one of the `registerBeforeLogout` callbacks puts a half-stopped timer *back on the clock* (`useTimer.js`), so cancelling first silently loses the worker's run. `api.beginLogout()` forgets the in-memory token **immediately** and returns the server-side cancel as a function; `logout` in `AuthContext` fires the before-logout callbacks first, collects whatever promises they hand back, and only calls that function once they settle (capped by `BEFORE_LOGOUT_GRACE_MS`, 3s, so an unanswering server can't hold the sign-out open). The cancel `POST`s `/auth/logout` with the token it captured, wiping the marker server-side (`updateSessionToken.run(null, ...)`), so the JWT the person was holding is rejected by `authenticate` from the very next request. Two details are load-bearing: the captured token means signing **back in** inside the grace window can't cancel the *new* session, and the cancel is sent with a **plain `fetch`, not `_send`** — routed through the shared sender its 401 (the marker has since been replaced by that new sign-in) would reach the forced-sign-out handler and sign the new person straight out. `beginLogout` also sets `sessionInvalidated` so a request that was already in flight can't come back as the "signed in from another device" toast; the flag is re-armed by `setToken` on the next sign-in. `api.logout()` remains as the fire-it-now form. Nothing blocks the local sign-out — a server that isn't answering still signs the person out here. `maintenanceGuard` lets `/auth/logout` through during a restore alongside `/auth/login`: it touches only that person's own session marker, which a restore replaces wholesale anyway, and refusing it would leave them looking signed out while the server still honoured their pass.

- **A page restored by the Back button is signed out**: a browser can keep a whole page alive when you navigate away and hand it back — JavaScript memory included — on Back, which on a shared workstation restored the previous person still signed in (the in-memory token survives, and the inactivity timer is frozen while the page is parked, so it never fires). `AuthProvider` listens for `pageshow` and signs out whenever `event.persisted` is true, with a plain-language toast. A normal Sign Out was already safe: the route guards render `<Navigate to="/login" replace />`, so Back can't re-enter (and `replace` keeps a redirect from stacking history entries).

- **Inactivity timeout**: Users auto-logout after configurable period of inactivity (default 5 min). Warning modal appears 30 seconds before logout. Activity = mouse, keyboard, touch, scroll. Timer continues when tab is hidden (security for shared workstations). **Whoever carries the `stayLoggedIn` permission is exempt** — the timer is disabled entirely (no countdown, no warning modal) for `can(user, 'stayLoggedIn')`, today only `admin`, since the timeout targets shared shop-floor workstations; managers and employees are still timed out.

- **Every dead-pass 401 carries a code, and the client signs the person out on it**: `authenticate` answers `TOKEN_EXPIRED` / `TOKEN_INVALID` alongside `SESSION_REPLACED` (the session marker was replaced — someone signed in to this account elsewhere, or the PIN was changed from another PC), `SESSION_ENDED` (the marker was cleared here — a management PIN reset, archiving the account, a backup restore — so the person is told their PIN or access may have changed rather than falsely told another device signed in) and `ACCOUNT_DEACTIVATED`, and `SIGNED_OUT_MESSAGES` in `client/src/services/api.js` is the single list of those codes and the plain-English wording each one shows (shared with `AuthContext`, so the toast and any thrown `err.message` can never disagree). A 401 whose code is in that list triggers the forced sign-out. Without `TOKEN_EXPIRED` there, an admin — who is exempt from the inactivity timeout — could sit on a session past its expiry and watch every action fail silently instead of being told to sign in again.

- **JWT authentication**: Memory-only token storage (no localStorage), role-based access control. The token carries **identity only** — the role is looked up from the database on every request, so changing someone's role takes effect immediately rather than at their next sign-in (see the roles section of `CLAUDE.md`). Session ends on app close/refresh.

- **Auto-generated JWT secret**: On first run, a random 256-bit secret is generated via `crypto.randomBytes(32)` and persisted to `data/config.json`. Env var `JWT_SECRET` overrides if set.

## Login throttling

- **Rate limiting**: Login (first 5 **failed** attempts normal, then an escalating cooldown — 30s, 1m, 2m, capped at 5m; resets after 15 min with no new failure). **One throttle for every PIN check**: the counting, cooldown and sweep live once in `server/src/utils/pinAttempts.js` (`createPinAttemptLimiter`), used by sign-in and by `PUT /auth/change-password`. **Each failure remembers the account it was aimed at**, and a correct PIN forgives only the failures aimed at that account (`forgive(key, target)`): someone who mistypes their own PIN and then gets it right is fully cleared, but signing in correctly to your own account no longer wipes the guesses made from the same computer at someone else's — which used to let a worker make 4 guesses at the admin, sign in as themselves, and repeat forever with no wait. Sign-in keys the record on the computer (below) with the typed username (lower-cased — usernames match ignoring case) as the target. **Change PIN is throttled too**: the current PIN is the lock that stops someone at a session left signed in (an admin's never times out) from finding the real PIN and setting their own, so a wrong current PIN counts exactly like a failed sign-in — counted before the comparison, 429 with the wait once the free attempts are used, and a `pin_change_failed` trail entry (`reason: { from: null, to: 'invalid_current_password' }`) each time. That throttle is keyed on the account itself, which only its own session can reach, so no coworker can be slowed down by it. **Sign-in boxes carry size caps** (`validateLogin`: username at the same 100-character cap account creation uses, PIN 64, home access code 72) and the sign-in route has its own 10 KB body limit mounted ahead of the app-wide photo-sized one, so an oversize attempt is refused before the throttle, the trail or the log are touched — sign-in is the one write anyone can reach before signing in. The attempt is **counted up front, before the password comparison** — that comparison yields, so counting the failure afterwards left a window in which a whole burst of guesses passed the check together and one cooldown wait bought unlimited tries; a successful sign-in forgives its own account's failures as above. Plus user creation (10 attempts/15 min) per IP. The server sets `trust proxy` to `loopback` (`server/index.js`), so a request forwarded by a Cloudflare Tunnel (`cloudflared` runs on the host and hands visitors to `localhost`) is keyed on the real home user via `X-Forwarded-For` instead of every home user sharing the loopback address; the header is only honoured from this machine, so a LAN client can't fake it. The login throttle itself is keyed on `clientIp(req)` (`utils/homeAccess.js`): the **rightmost** untrusted forwarded entry, i.e. the one Cloudflare appended, because Cloudflare appends the real visitor to any `X-Forwarded-For` the visitor sent and Express's `req.ip` would take the leftmost — a visitor could otherwise dodge the throttle by faking a fresh header each try. **The failure map is swept, not just read**: each limiter's in-memory `Map` is never trimmed by the checks above on their own — a key that fails once and never comes back would sit in it forever on a long-running server. A `setInterval` in `pinAttempts.js` (every 15 minutes, `.unref()`'d so it can never hold the process open on its own) deletes any entry that has gone a full 15-minute window with no new failure, using the exact same expiry test (`isExpired`) the check itself uses. A record whose current cooldown has passed but is still inside its window is kept, so the sweep can never reset someone's escalating wait.

## Contact details are hidden from non-management

- **Contact info hidden from non-admin**: All customer/contact data (name, company, phone, email) is stripped from API responses for non-admin users. One step, `customerFields(row, canManage)` in `jobcard-helpers.js`, decides this for every reader of a job's customer fields — `formatJobcard()` spreads it for the live job card, `search.js`'s job results take `companyName`/`contactName` from it, and the printout's `buildJobCardView` takes its `company` field from it — so the hiding rule can't drift between them; it also deletes contact fields from POST/PUT request bodies, and all `/contacts` endpoints require admin. A supplier's contact phone/email are hidden from non-management the same way, through the shared `supplierContactFields(row, canManage)` in `supplier-helpers.js` — used by `suppliers.js`'s `toApiFormat` and (for supplier search results) `search.js`'s own `formatSupplier`. Client hides Customer column in tables, hides Contact section in DetailsTab, and skips contact creation logic in JobCardModal submit.

## Other protections

- **Inactivity auto-logout**: Configurable timeout (1-60 min, default 5 min) with 30-second warning modal. Admin configures in Settings. Handles system sleep/wake via visibility API. Does not apply to admin accounts (see the roles section of `CLAUDE.md`). The range and default (`INACTIVITY_MINUTES`) and the "is this a valid number of minutes" check (`isInactivityMinutes`) live once in `server/src/shared/settingsRules.js` — `routes/settings.js` (save validation, and the fallback in `GET /settings/inactivity-timeout`), `hooks/useSettings.js` (the on-screen check, marking the field via `useFieldErrors` rather than a pop-up), `context/AuthContext.jsx` and `hooks/useInactivityTimer.js` (the client's own fallback default) all read it instead of carrying their own copy of the numbers.

- **Signed-in replies are never stored by the browser**: a small middleware sets `Cache-Control: no-store` on everything under `/api` (mounted in `server/index.js` before the API routers). Express sends no cache headers of its own, so a browser was free to keep authenticated JSON on disk under heuristic freshness and hand it back on a shared machine after the next person signed in.

## Home access (reaching the app from outside the office)

- **Home access (Cloudflare Tunnel, customer's own domain)**: the app can be reached from outside the office through a named Cloudflare Tunnel (`cloudflared`) installed as a Windows service on the host, forwarding `https://jobs.<domain>` → `https://localhost:443` with *No TLS Verify* on (our leaf is self-minted). The full one-time setup is in `jobcard-system/HOME-ACCESS.md` (the workshop-day checklist is at the bottom of `instruction.md`); `jobcard-system/setup-home-access.bat` self-elevates, downloads `cloudflared`, prompts for the tunnel key and installs the service in one go. Nothing is opened on the router and nothing is installed on home PCs. App side: `server/src/utils/homeAccess.js` `isViaTunnel(req)` (`req.ips.length > 0`, which with `trust proxy = loopback` is only true for a proxy on this machine) tells a tunnel visitor apart from an office one; `/health` carries `viaTunnel` so the login screen shows a third **Home access code** box only to tunnel visitors. **The code is the real lock**: `PUT /settings` `homeAccessCode` (admin-only, 8 chars to 72 bytes — bcrypt reads no further, stored bcrypt-hashed as `home_access_code`, blank = off; the hash is stripped from `GET /settings`, which returns `homeAccessCodeSet` instead) and `POST /auth/login` from the tunnel refuses with 403 when no code is set and 401 (counted as a login failure) when the code is wrong — checked **before** the PIN is looked at. Office/LAN sign-ins never see or need it. `homeAddress` (`home_address`, admin-only, display-only text) is the address staff type from home, shown on the **Home Access** card in Settings (`settings/HomeAccessCard.jsx`; any manager can read it, only an admin can set it or the code). The validation/view helpers live in `routes/settings-home-access.js` (`HOME_ACCESS_BODY_KEYS` gates managers with 403, `HOME_ACCESS_SECRET_KEYS` strips secrets, `collectHomeAccessUpdates`, `homeAccessView`).
