# Dates, times and time zones

> Detail split out of CLAUDE.md. Read this before touching anything that stores, reads, compares or displays a date or a time.

## Stored timestamps

**Stored timestamps are always ISO-8601 UTC**: every column holding a *moment* (`created_at`, `updated_at`, `assigned_at`, `uploaded_at`, `invoiced_date`, `start_time`, `end_time`) stores `YYYY-MM-DDTHH:MM:SS.sssZ` — the same shape as JavaScript's `toISOString()`. SQL writes use `strftime('%Y-%m-%dT%H:%M:%fZ','now')`; **never** `datetime('now')` or `CURRENT_TIMESTAMP`, which produce `YYYY-MM-DD HH:MM:SS` in UTC with no time-zone marker — JavaScript reads that shape as *local* time, so every displayed time shifted by the machine's UTC offset (a 09:40 comment in Melbourne showed as 23:40). `db/normalizeTimestamps.js` folds any value still in an old shape into the new one, in two passes. (1) The bare `YYYY-MM-DD HH:MM:SS` shape is already UTC, so it only gains the `T` and the `Z`. (2) `time_entries.start_time` / `end_time` are the one moment never written by SQL — they come from the person's own clock — and a hand-typed time saved before the write path was unified was stored as a **zone-less local wall-clock reading** (`YYYY-MM-DDTHH:MM`, sometimes with seconds); those can't just be stamped `Z`, so they are read against the office's own time zone (the `timezone` setting the overtime schedule uses, falling back to the machine's zone) via an `Intl` offset lookup that is DST-correct at the stored instant. A block with one end in that shape and the other in UTC measured hours wrong by the office's offset, which is what labour cost is billed on. Both passes are naturally idempotent (a converted value is 24 characters, so it matches neither the 19-character bare shape nor the 16/19-character zone-less shape) and therefore need no run-once flag. It is called at the **start** of `initializeDatabase()` on every boot — **before** `runLegacyMigrations()` (`db/legacyMigrations.js`), because some one-time conversions in there *read* stored moments and persist a figure derived from them (the archived-job costing backfill splits work blocks into overtime tiers, and a job owns its costing for good once written, so converting afterwards would leave a permanently wrong labour total) — **and** at the end of the backup-import transaction, so restoring a backup taken before the change can't bring the wrong times back. It runs before the default settings are seeded, which is safe: `officeTimeZone()` falls back to this machine's own zone, exactly what the `timezone` default is seeded to, and a database fresh enough to be missing that setting has nothing to convert. The seed script calls it too, because several of its inserts leave the timestamp to the column default and `CREATE TABLE IF NOT EXISTS` can't update that default on a database that already exists. Bare calendar dates (`due_date`) are a day, not a moment, and stay `YYYY-MM-DD`; the client's `parseDateValue` reads those as local midnight so they can't slip to the day before. **"Is this a real calendar day?"** is checked in exactly one place, shared by both sides — `server/src/shared/calendarDate.js`'s `isCalendarDate(value)` (built with `Date.UTC` and read back, so `2026-02-30` is false and `2028-02-29` is true; a bare regex or `Date.parse` check both let a rolled-over day like `2026-02-30` through) — used server-side by `routes/settings-overtime.js` (public holidays) and `routes/statistics-helpers.js` (a custom statistics range), and client-side (via the Vite plugin in `client/vite.config.js` that turns its shared-rule-file CommonJS into an ES module) by `Statistics.jsx` and `hooks/useLabourRates.js`, next to `todayIsoDate` in `client/src/utils/formatters.js`. The same file's `formatDayAu(isoDay)` turns a stored `'YYYY-MM-DD'` into the printed `'DD/MM/YYYY'` by rearranging the string — never through a `Date`, which would read the day in the server process's own zone rather than the office's. The job card printout (`buildJobCardView`) and the quality-form pre-fill (`qaFillDataForJob`, both in `jobcard-helpers.js`), plus the quality form's own "date" field (`qaTemplateProvisioning.js`), follow the office's day for a created moment — `formatDayAu(officeDateString(new Date(created_at)))` — and pass a due date straight through `formatDayAu(due_date)` with no `Date` object at all, since it's already a bare calendar day. On the client, "today" as a calendar day comes from `todayIsoDate()` in `utils/formatters.js` (built off the local clock, **never** `toISOString()`, whose UTC day is still yesterday all morning in Australia) — it drives the overdue comparison in the job list, the list table's red rows and the job screen's overdue badge (all now plain `YYYY-MM-DD` string compares, so the three can never disagree) plus the export filename stamp. Overdue is computed client-side from the already-loaded list; the old `GET /jobcards/overdue` route and its `getOverdue` query are gone.

## Office wall clock vs stored instants

**Crossing between stored instants and the office's wall clock** goes through one place — `server/src/utils/officeTime.js`. It also exports `isValidTimeZone(zone)` — the one "is this a real IANA time zone" check (tries to construct an `Intl.DateTimeFormat` against it and reports whether that throws); `officeTimeZone()` uses it for its own fallback, and `routes/settings-overtime.js` imports it to validate a saved `timezone` rather than carrying its own copy of the same try/catch. It exports `officeTimeZone()` (the `timezone` setting the overtime schedule uses, falling back to this machine's zone — read through the ordinary `getSettings()` lookup in `db/database.js`, the same one every other setting goes through, not a one-off query), `makeOfficeFormatter(tz)` (an `Intl` formatter that reads an instant down to the minute with its weekday attached, UTC-fallback on a missing or bad zone — `utils/overtimeSplit.js` and `routes/statistics-helpers.js` used to each carry their own byte-identical copy of this; both now import it from here), `officeDateString(moment, fmt = makeOfficeFormatter(officeTimeZone()))` (`'YYYY-MM-DD'` of a moment, read on the office clock — an optional pre-built formatter can be passed so a loop doesn't rebuild one per row; this used to be `routes/statistics-helpers.js`'s own `getLocalDateString`, now deleted, with every caller in `routes/statistics.js` / `routes/statistics-helpers.js` moved over), `wallClockToIso(value, tz)` (a zone-less local reading → the instant it names, DST-correct via an `Intl` offset lookup that carries milliseconds through, so a bound can't land a fraction short), and `officeDayStart(date)` / `officeDayEnd(date)` (the instants a picked calendar day begins and ends at on the office clock — exactly contiguous, so consecutive days neither gap nor overlap across a DST change). `db/normalizeTimestamps.js` uses it for the legacy wall-clock pass; `routes/search.js` uses it for **every date-range filter over a stored moment** (`pushMomentRange` → jobs by created, activity, time entries). Comparing the picked date as a plain string against a UTC instant would shift the whole window by the office's offset — in Melbourne "6 August" silently returned 6 Aug 10am → 7 Aug 10am, dropping that morning's work and pulling in the next morning's. The one date filter that does **not** go through it is jobs filtered by **due date**: a due date is a calendar day, so it compares straight against the picked day. `utils/overtimeSplit.js` keeps its own separate, segment-based offset walk (`zoneOffsetAt`/`offsetSegments`) for splitting a logged block minute-by-minute into overtime tiers — that one is a deliberate performance optimisation over calling `Intl` per minute (see the comment at the top of that file) and stays put; only the formatter construction was duplicated and is now shared.
