# Time tracking, overtime and job costing

> Detail split out of CLAUDE.md. This is the largest and most trap-laden area in the app — read it before touching timers, logged work, overtime tiers or pricing.

## Timer endpoints

Timer endpoints: `GET /jobcards/active-timer` (authenticated), `POST /jobcards/:id/time-entries/start` (authenticated, body: `{ itemId, workerId? }` — `itemId` required, must be the permanent id of an existing line item on this job card (never its `item_number`, which is only a sort order the server owns and may have gaps); auto-assigns the timer's worker to the job if they aren't already an assignee, recorded as `self_assign`. Optional `workerId` lets **management start the timer for another worker** (e.g. setting someone up at a machine): management-only (everyone else gets 403), the worker is validated via `resolveWorkerId`; **both** start paths assign through the one `autoAssignWorker` helper, which takes the history action to record (`self_assign` for your own timer, `assign` for one set up for someone else), the running timer belongs to that worker (history names them under `worker`), and the client does **not** adopt it as the caller's own active timer), `POST /jobcards/:id/time-entries/:entryId/stop` (authenticated — **a run shorter than 15 seconds is treated as an accidental start/stop tap**: the block is deleted instead of logged, history records a `discard_timer` action, and the route returns `{ discarded: true }` so the client skips the stop form. **The discard also undoes what the Start did** — `server/src/utils/startTimerUndo.js` puts back the status move and the auto-assignment that Start made, so an accidental tap can't leave the job reading In Progress with the worker assigned and no work to show for it. **Nothing is remembered between the two taps**: both facts are read back out of the database, so a restart in between changes nothing and no second copy of them exists. The status move comes from the Start's own `start_timer` history entry, found by the block's start time (`historyQueries.getStartTimer`, a `json_extract(changes,'$.timer.to')` match — Start writes that same value into the block and into the entry), and the auto-assignment from `job_assignees.assigned_at` being no older than the block (anyone assigned before it was already meant to be there, so they stay). The status is only put back if nothing else moved it since **and no other timer is still running on the job** — a colleague's still-running work earned that status honestly and an accidental tap from someone else must not undo it out from under them; the reply carries `unassignedUserId` so an open job screen unticks that worker too, or the next Save would re-assign them. A negative run — a block whose start is still ahead of the server clock — is discarded the same way, because saving it would record a finish before its start. It can only come from clock drift: `validateManualTimeEntry` (`middleware/validation.js`) rejects a hand-added/edited block's start time more than 15 minutes in the future, a leeway sized for an office PC whose clock runs ahead of the server's (the Add Time form fills its start from the PC clock). A hand-entered finish gets the same rule — a finish further ahead is a mistyped hour or day, and would be billed and counted toward Done at once. It deliberately does **not** call `syncStatusToWork` — that would just re-assert In Progress. Pinned by `server/scripts/check-startTimerUndo.js`, a standalone self-check against a throwaway database)

## Time entries, overtime tiers and the costing sheet

**Time entries**: Core fields only — item#, machine#, qty, scrap (bin + recycle), description, start/end time. A block stores **only** the part's permanent `item_id` (resolved when the block is created — inline in the timer-start route, via `resolveItemId` in the manual add/edit routes). **A part is required on a new block**, hand-added ones included: the job screen lists work only under its part, so a part-less block could never be seen, edited, deleted or (if open) stopped, yet would count toward labour and block invoicing. The only blank `resolveItemId` accepts is a management edit of an old block that already has no part, so its other fields stay correctable. **The manual edit form sends only what changed** since it opened (the start and finish always go, as they are judged as a pair), and the edit route keeps the stored pieces, machines, notes, part, scrap and inspection answers for anything left out — so a worker's stop-form save made while a manager had the edit form open isn't overwritten by the copy taken at Edit. A manual add, edit or delete also raises the job list's reload-on-close flag, because the server may have moved the job's status or put the worker on it. There is **no** `item_number` column on `time_entries`: the displayed number is derived at read time by joining the part's **current** position (`LEFT JOIN job_items` in `getByJobcard` / `getById` / `getActiveByUser`). The API returns both (`itemId` / `itemNumber`), and anything matching a block back to a part must key off `itemId` — the number only says where the part currently sits on screen. **Blocks logged before 2026-06-10** (when work switched from position number to stable id, commit `26dc957`) have `item_id` NULL and were never backfilled; a database upgraded across that change still carries the old `item_number` column, so those blocks show up in the "What this job used" panel under "Work on a deleted part". A fresh or re-seeded database has neither the column nor any such rows. **Good pieces are whole numbers**: `qty` on a work block is stored as a whole number or NULL — `wholeQty` in `timeEntryHelpers.js` coerces it on both the add and edit/stop routes (`"2.5"` → `"2"`, blank → NULL) and hands it back as **text**, because the column is text — a JS number bound into it is written as `"12.0"`, which the edit form's whole-number check then refuses. A part's own quantity (`job_items.qty`, also text) is bound as text for the same reason (`partQtyText` in `jobcard-helpers.js`), and both entry boxes (the stop-timer stepper and the admin manual form via `handleTimeEntryChange`) accept digits only. This is what keeps the three readers in step: `syncStatusToWork` and statistics sum with `parseInt`, the part's progress bar with `parseFloat` — a fractional count made the part read Done while the job stayed In Progress. A one-time startup conversion in `runLegacyMigrations` (`db/legacyMigrations.js`) folds any fractional text already stored down to its whole number (idempotent, no flag needed). **Scrap pieces**: Scrap is split into two destinations — `scrap_bin_qty` and `scrap_recycle_qty` (both integers, default 0) recording pieces binned vs sent to recycling; the line's total scrap and scrap rate sum the two. They are entered by the worker in the stop-timer form (two number fields) and by admins in the manual time-entry form (which carries both Scrap — Bin and Scrap — Recycle for adding and editing). The server requires each to be a plain non-negative whole number when sent at all (`wholeNonNegative` in `middleware/validation.js` rejects "-3", "2.5", "3 pcs" and the like with a 400, rather than the route silently coercing them), treats blank/absent as 0, and preserves the existing value if an update omits a field. The same rule applies to the good-pieces count (`qty`). **Critical-job inspection checklist**: A run whose job was on the **Critical** quality level *the moment it finished* asks the worker an extra inspection checklist, stored on the time entry: `first_off_inspection`, `in_process_validation`, `measuring_equipment_verification`, `equipment_checks` (each 1 = yes / 0 = no / NULL = not applicable, i.e. the run didn't need the sign-off) plus a free-text `equipment_checks_comments`. Whether a given run needed it at all is its own stored fact, not today's job level: `time_entries.critical_at_finish` (1/0/NULL) is decided once, at the moment a run first gets a finish time, and never re-decided after — see `docs/notes/files-and-qa.md`'s Critical sign-off note for the full rule, the decision helper (`criticalAtFinishForWrite`), the existing-data backfill, and the invoicing checkpoint. On a run needing the sign-off, all four Yes/No answers are **required before a finished block can be saved** — enforced client-side (the stop-timer Submit button stays disabled until all four are answered) and server-side in `checkCriticalInspection` (`jobcard-time-entries.js`, reading the run's own decided `critical_at_finish`) on both the add and edit routes, which 400s a completed block missing any answer. A run that never needed it shows no checklist and stores NULLs. The admin manual time-entry form shows the checklist for the same reason the job screen's forms do (see `docs/notes/files-and-qa.md`), and each finished entry's card displays the answers as Yes/No chips with the equipment comment, plus a "Sign-off missing" mark when the run needed the sign-off and any answer is still null. (The schema's legacy-drop list deliberately excludes `first_off_inspection` / `in_process_validation` — they are live again for this feature.) **Crediting work**: The admin manual time-entry form requires picking the worker who actually did the work (a `workerId` select), so hours land under that person, not the admin filling in the form. The server validates the chosen worker is a real, active account, auto-assigns them to the job (mirroring what a self-started timer does), and records the worker in history. On edit, only an admin can re-credit a block to a *different* worker (a regular worker editing their own block keeps it under themselves); leaving the owner unchanged is always allowed, so an old block owned by a since-deactivated worker can still have its other fields corrected. The part a block is credited to is management-only in the same way: a worker's save of their own block always keeps the stored part, whatever part it sends or leaves out, so it can neither move the block to another part nor detach it. The machines field on a time entry is a multi-select (`CheckboxDropdown`) stored as one comma-joined string (e.g. `"5, 9"`), matching the stop-timer form. The per-item Progress section shows scrap total + scrap rate (scrap / every piece made, i.e. good + scrap — the same formula the stop-timer form and the statistics page use, so it can never exceed 100%; hidden until any piece is recorded). **Per-item timers**: Each line item has its own Start/Stop button (`LineItemTimerButton.jsx`); starting a timer requires picking an item, and the active timer is bound to that item's permanent id (server validates the id belongs to the job card, returns 409 if a timer is already running on another job/item with the conflicting timer's `jobcardId` + `itemId`/`itemNumber` for "stop & switch" prompts — the client resolves the part it names back to a position in its own list rather than showing the raw stored number). **Special labour**: Special labour is a **manually-entered costing line**, not a per-time-entry flag. An admin types the special-labour hours and rate directly on the Costing tab (`labour_special_hours` / `labour_special_rate` on `job_costings`); the special total is `hours × rate`. **Cost-line notes**: each of the three manual cost lines (special labour, materials, subcontractor) carries a free-text note saying what the cost covers — `labour_special_description` / `materials_description` / `subcontractor_description` on `job_costings`, trimmed and capped at 300 characters server-side and stored NULL when blank. It renders as a "What this covers" box on its own row under that line's figures on the Costing tab (auto-capitalised on blur like every other text field), is tracked in the audit trail as text, and is exported in the Excel Costing sheet. **"What this job used" info panel**: an info icon beside the "Job costing" title in the sticky header toggles a read-only panel (`tabs/CostingBreakdown.jsx`, `.cost-brief` / `.cb-*` styles) that folds out between the header and the Labour block. It is the supporting evidence for the pricing boxes below it, and it is **one table**, read left to right: **part · material · treatment & supplier · machine · who · hours**. A part's item cell, material and treatment cells are `rowSpan`-merged down its machine rows, so however many runs a part took it still reads as one horizontal band and nothing about it is looked up in two places (an earlier split into two tables — hours and bought-in — was rejected for exactly that reason). Deliberately **six columns, not eight**: the supplier is stacked under its treatment (one fact — who is doing what to this part) and the part's own total sits under its name rather than in a column of its own; both were costing width that every other column paid for as an ellipsis. Each hours cell shows the decimal (the form the Hours boxes take) with the h/m reading under it, right-aligned in tabular mono; the job total closes the column in the `tfoot`. Machine **codes only** (`CNC-01`, `CNC-01 + MILL-01`) — carrying the make and model as well truncated the material and the worker's name to pay for it — and a treatment with no supplier is called out in the caution colour because it can't be priced. It is built entirely from data the job screen already holds (`formHook.lineItems` + `timeEntries`, passed as props — it needs no machines list), so it adds **no** new route and no saving; option names come from the shared cached tag lists (`useTags`), the same ones the job screen already loads. Only **finished** blocks are counted (running timers are called out in a note but excluded, matching how costing tallies hours); a block logged on several machines at once is kept as one combined row rather than split, since its span can't be divided between them without inventing figures; and blocks are matched to a part by the part's **permanent id** (`itemId` on the time entry — `item_id` is emitted by `toCamelCase` in `server/src/utils/timeEntryHelpers.js` and carried through `mapTimeEntryFromApi`), never by `itemNumber` — the number is only a display position that shifts as parts are added or removed — with blocks whose part has since been deleted falling into a "Work on a deleted part" group so the totals still add up. Tag values are named via each category's `rawTags` (not `useTags`'s `labelOf`, whose identity changes every render and would rebuild the table on the job screen's one-second timer re-render). The table **never wraps** — a wrapping table narrows itself by stacking words, which pushed the hours off the right edge instead of scrolling to them; cells ellipsis and `.cb-scroll` scrolls sideways below its `min-width`. **Grand total placement**: the grand total lives in the Costing tab's header bar, which sticks to the top of the scrolling panel (`position: sticky` — hence no `overflow` clipping on `.costing-sheet`), so the figure stays readable while the sheet is scrolled; there is no second grand-total block at the bottom. **The Costing tab saves itself — there is no Save button.** Every edit calls `markEdited` (bumps an edit counter, sets `costingDirty`, shows `pending`), but **nothing saves while the cursor is still in a box** — a save fires on leaving a box, on Enter, on pressing a reset/put-back link, on leaving the Costing tab and on closing the job, all through a `saveNowRef` so no per-render function identity can re-fire them on the job screen's one-second timer re-render. So all the typing inside one box lands as **one** save and one audit entry. There used to be a 1 s idle countdown as well (removed 2026-09-27): a save it fired while the person was clearing a box to retype came back and refilled the box mid-edit, so "55" became "556". Refreshing or closing the window with pricing unsaved already asks first, and admins — the only role that sees pricing — are exempt from the inactivity sign-out, so the countdown was guarding nothing the other exits don't. **Every box on the sheet holds a draft, not a coerced figure, while it's being typed in** (root-caused 2026-09-27, replacing the blank-restore/clamp patches below). `useCosting` (composed from `useCostingDrafts.js` — drafts and commits — and `useCostingSave.js` — the save queue, flush and leave guard) keeps two things: the **committed** form (numbers and flags — the only thing a save ever sends) and a `drafts` map of exactly the text in any box currently being typed in, keyed by field name. What the sheet shows in a box is the draft if one exists, else the committed value — a half-typed `"1-"` or a box mid-clear is never parsed into a number on a keystroke, because nothing at all happens on a keystroke beyond recording it (`handleCostingChange` just writes to `drafts`). `commitBox` is the single place a draft becomes a figure: called by a box's blur (Tab, click-away, Escape-then-close, switching tab — blur bubbles in React, so `CostingTab` still puts one `onBlur` on the `.costing-sheet` div rather than one per box) **and** by Enter, which commits and saves but leaves the cursor in place. Blank commits to a sensible default and saves (0 for a plain box, the calculated/logged figure for an override box, dropping its override flag); text that isn't a plain number, a number too long to be a real figure (over ~309 digits reads as infinity — "Enter a smaller number."), or a number under the field's floor, is refused outright — the draft is kept, the field is marked with `hooks/useFieldErrors.js` / `common/FieldError.jsx` (never a pop-up for this), and nothing is sent until it's fixed. A valid figure that didn't actually change just drops its draft — no save, sheet not dirtied. `commitBox` requests its save through `requestImmediateSave` the same one-render-later way the link presses do (see below) — its own tidying (the cost notes' capitalise-first, now run inside `commitBox` itself rather than a separate per-box `onBlur`) is still a queued state update while the blur handler runs, so saving on the spot would send the untidied wording. It does **not** lift `autoSavePaused` the way `flushCosting` does — after a failed save, tabbing across the sheet would otherwise fire one doomed retry per box, so the pause still lifts only on the next real edit or the "try again" link. Live totals (`calculateCostingTotals`, called with no argument) read the committed figures overlaid with every current draft, parsed the same way commitBox would judge it (blank plain → 0, blank override → its calculated figure, unparseable → 0 for display only) — so the sheet's running numbers, and the header's grand total, update on every keystroke without sending anything. Each line is rounded to whole cents and the grand total is added up from those rounded lines, exactly as `computeLiveCosting` does on the server, so the figure on screen is the figure a save stores. **A save sends only the figures this screen changed** — so two admins pricing the same job don't overwrite each other's figures with an out-of-date copy — `runSave` compares the committed form against `loadedRef` (the figures the server last stored and handed back — moved on by **every** successful save reply for this opening, even one not adopted into the boxes because something was typed meanwhile; otherwise a figure put back to its old value while an earlier save was in flight would be judged unchanged and never sent) and sends just the ones that differ (an override box as its override: the typed figure, or null for "follow the logged/company figure"; notes compared trimmed, as the server stores them). Sending the whole sheet let a second admin's out-of-date copy of a figure they never touched overwrite the first admin's saved one; now the server keeps its stored value for anything left out, and the reply — adopted as before — brings the other admin's figures onto this screen. No totals are sent: the server works every one out itself. A save's reply is only ever merged into fields with no draft currently sitting on top of them — the three notes and any box someone is mid-typing in survive a reply that lands underneath them.

A red box changes what closing the job, leaving the Costing tab, or invoicing can do: `costingHook.costingInvalid` is true while any field is marked, `firstInvalidCostingField` names the first one, and `guardLeaveCosting(showConfirm)` — used by both the close guard and (via a `JobCardModal.jsx` tab-switch guard) leaving the tab — commits every open draft first (exactly like leaving every box at once) and, if one stays red, asks "This pricing figure isn't saved — fix it or discard it?": Fix returns to the box, Discard drops every draft and error (`discardCostingDrafts`) and lets the job close/the tab switch proceed. Invoicing (`JobIdentityStrip.jsx`) refuses outright with no discard option — the job is never billed on a figure the admin didn't mean — and sends the person back to the Pricing tab with the box in view. `costingSaveState` (the status line beside the grand total) reads `'invalid'` whenever any box is red, overriding the ordinary idle/pending/saving/saved/error progression, since there's nothing to report about the rest of the sheet's save state while one figure on it isn't even a valid number yet. **A figure changed by pressing a link saves straight away too** — a tier's "reset to logged", an overtime multiplier's "standard ×N", "use company default", "put it back" and "Reset all to auto" have no box to leave, so the blur path never fires for them. They go through `requestImmediateSave` (`useCostingSave.js`), which bumps a counter that an effect turns into a `saveNow` **one render later**: the new value is still a queued state update inside the click handler, so saving there would send the figure the press just replaced. Several bumps in one click (Reset all to auto resets six things) batch into one render and so into one save. `revertField` exists for the same reason — "put it back" sets the committed value directly (dropping that box's draft and error, if any) rather than going through `handleCostingChange`, because typing into that same box must **not** save immediately. Enter commits exactly the box the cursor is in (`commitBox`, same as its blur) and leaves the cursor where it was. `flushCosting()` commits every box still holding a draft — leaving the tab and closing the job both reach it (the close guard, `useJobCardCloseGuard.js`, runs it and **waits for the answer** before asking the unsaved-work question: a pricing save that fails is named there as "your pricing hasn't been saved", so the admin can keep editing and retry — that wait is capped at the same few seconds as the job saves' own, so a save hung on a dead network can't hold the window open for good; past the limit it keeps running in the background, and because it may still store, the admin is asked a separate "Still saving" question instead — "Your pricing is still being saved and may still go through — close anyway?" (Close anyway / Wait) — which never calls the pricing lost and drops nothing; only a save that actually **failed** gets "close it and lose it", where answering Discard drops the unstored figures via `dropUnsavedCosting` so the save-on-close effect — now only a backstop for a close that never reaches the guard — doesn't send them anyway. There is no "your pricing changes are saved either way" line any more: it was said on an assumption, even straight after a failed save) — and only then decides whether to save: a box that stays red (invalid) makes it return `{ ok: false, invalid: true, field }` **without sending anything**, naming which field; otherwise it saves if the committed form is dirty, reusing an in-flight or already-requested save rather than sending the same figures twice (leaving the sheet with the cursor still in a box fires the blur commit a moment first, and the sheet reads as dirty until that reply lands). `guardLeaveCosting(showConfirm)` wraps the same commit-everything step with the fix-or-discard question for a caller that can still cancel what it was about to do (the close guard, and a `JobCardModal.jsx` tab-switch guard). `handleSaveCosting()` is a plain `saveNow()` — no commit step — and stays for **`JobIdentityStrip` only**, which checks `costingInvalid` itself before ever calling it. A `costingSaveState` of `idle | pending | saving | saved | error | invalid` drives the status line that replaced the button (`error` offers "try again"; `invalid` — "Not saved — fix the red box", in `--danger-ink` — overrides every other value while any box is red). Four guards make auto-save safe. (1) Saves are **serialised, not deduplicated**: `saveNow` chains a second caller *behind* the in-flight save (`inFlight.current.then(runNext, runNext)`, with `runNext` reading a `runSaveRef` so the queued attempt sends the figures as they are when it finally runs) rather than handing back the in-flight promise — that promise is bound to `costingForm` as it was when it started, so returning it would tell an invoicing or closing caller "saved" about keystrokes that were never sent, and file the job away billing the older number. (2) A save only clears `costingDirty` when the **edit counter is unchanged**, so typing during an in-flight save isn't marked saved (it goes out with the next blur, Enter or flush). (3) A failed save sets `autoSavePaused` so a down server gets one attempt per edit, not one per box tabbed across. (4) **A save is refused while `loadedRef` is null** — i.e. the job's stored costing never arrived, because the `GET` failed or hasn't finished. The form would still be `getDefaultCostingForm()` (every figure 0, every note blank) and `computeLiveCosting` takes every field from `incoming` when `incoming` is truthy, so one keystroke on that empty sheet would otherwise write zeros over the job's real rate, tier overrides, materials, subcontractor figures and notes. The Costing tab never shows that sheet either: `CostingTab` takes `loaded` / `loadFailed` / `onRetryLoad` and renders a plain "Loading pricing…" or "couldn't be loaded" placeholder (`.costing-placeholder`) with a Try again button instead — `showBreakdown`'s `useState` sits **above** that early return so the hook order is stable. **The on-open `GET` is guarded the same way**: `useJobCardCosting` keeps a `loadSeq` counter, bumped in an effect **cleanup** keyed on `[isOpen, jobCardId]` (i.e. on close and on job switch — **not** in `resetCosting`, whose call from the modal's open effect lands *after* the load effect has already fired for a tab left on Costing, so a bump there discarded the new job's own reply and stuck the tab on "Loading pricing…"), and `loadCosting` drops a reply whose counter has moved — the fetch walks every logged minute, so a reply for a job closed seconds ago can land after the next job has opened and would otherwise paint (and, on the next keystroke, save) that job's figures onto the new one. `resetCosting` in `useCosting` also bumps `editSeq`, so a close-time save that resolves after the same job is reopened fails the "nothing typed since" check instead of being adopted onto the freshly blanked form. **Three things protect a figure that was typed by hand.** (1) **A mouse wheel can't change a money box** — Chrome otherwise scrolls a focused number box's value, and this sheet would save that a second later. This used to be an `onWheel={blurOnWheel}` prop on each of the sheet's ten number inputs; it is now enforced app-wide by `utils/wheelValueGuard.js` (one capturing, passive `wheel` listener installed from `main.jsx`, blurring the focused control when the pointer is over it), because the per-box version had been forgotten on the parts list's quantity box. The prop and the local `blurOnWheel` helper are gone from `CostingTab` — do not reintroduce either. (2) **A manual money line offers a way back** — `useCosting` exposes `lastSaved` (`openingRef` run back through `formFromCosting` — captured **once**, when this job's pricing first loads, and deliberately never moved again by a successful save: comparing against the last save made the control vanish about a second after it appeared, because the sheet autosaves on every edit. The name is a leftover and is now misleading — it holds the opening figure, not the last-saved one — and is kept only because renaming it reaches `JobCardModal.jsx`), and `CostingTab` renders an "opened at $X · put it back" control (`revertControl`, `.ledger-field-opening`/`.ledger-field-revert`/`btn-link` — **not** `.tier-foot-edited`/`.tier-dot`, whose dot means "hand-typed, not stored" and would be a lie on a figure that is stored) beside materials cost and margin, subcontractor cost and margin, and the special-labour hours and rate whenever the current value differs from it. Those six are the only fields with no "reset to auto" of their own; the tier hours and multipliers are deliberately left out, because "Reset all to auto" already covers them. (3) **The invoice confirm shows the total being committed** — and *committed* is the operative word, so which figure backs the `Total: $X` line depends on whether pricing is dirty. `JobCardModal` passes `grandTotal={canSeePricing && costingLoaded ? calculateCostingTotals().grandTotal : null}` **and** `canSeeTotal={canSeePricing && isEdit}` to `JobIdentityStrip`. When `costingDirty`, the prompt shows `grandTotal` — the on-screen figure, which is exactly what the confirm goes on to save and bill — and does **not** fetch: the stored total is the pre-edit number, and showing it under a message promising the unsaved edits will be billed archived jobs at a figure the dialog never named. Otherwise nothing is about to change, so it fetches the stored total (`fetchStoredTotal`, a plain `getCosting` that touches nothing on screen) because the on-screen figure can lag work someone else logged since the job opened. A failed fetch falls back to the plain message — never show a total that might be stale. `canSeeTotal`, not `typeof grandTotal === 'number'`, is the gate: pricing is only fetched once the Costing tab is opened (see below), so the old proxy would have silenced the total on every job where nobody opened the tab. A manager gets no total line and no fetch either way — they never see pricing at all. (4) **Pricing is fetched only once the Costing tab has actually been opened** — the fetch walks every logged minute, and most job opens never touch pricing. `useJobCardCosting`'s load effect gates on `costingOpened`, which is **derived** (`activeTab === 'costing' || costingOpenedThisOpening`) rather than purely stored: `resetCosting` clears the stored flag on every open, and an admin arriving straight onto Costing from the activity list twice in a row never changes `activeTab`, so the effect that sets it never re-fires and the opening would silently skip its refresh. The same derived value gates `JobCardModal`'s `reloadTimeEntriesAndCosting`. **All of the job screen's costing wiring lives in `useJobCardCosting.js`**, not in `JobCardModal` — the on-open `GET` and its `costingLoadFailed` flag (set in the catch, cleared on a successful load and by `resetCosting`), the `confirmInvoicedEdit` dialog, the `updateCosting` operation, and the two flush-on-the-way-out effects (leaving the tab, and closing the job — a backstop, see `flushCosting` above). A save refused with the closed-job 409 (`JOB_CLOSED` — the job was invoiced from another PC while this sheet was open) calls the job screen's shared `handleJobClosedWrite` (passed in as `onJobClosed`) instead of the ordinary failure toast, and drops the unstored figures (`dropUnsavedCosting`: the sheet goes back to what the server last handed back, and closing won't ask about them); the reload then locks the tab. It wraps `useCosting` and re-exports its whole API plus `costingLoaded` / `costingLoadFailed` / `retryLoadCosting`, so the modal holds no costing state of its own and stays a manageable length. **There is no "change an invoiced job?" question on the pricing sheet** — a billed job's figures save themselves exactly like any other job's. There used to be one, asked once per opening and remembered in an `invoicedAck` ref. It was removed (2026-09-20) because with no Save button it had nowhere to hang except the 1 s autosave countdown, so it spoke a beat *after* the typing stopped with nobody having clicked anything — and a question raised by a timer could land on top of another question the user was already reading (the close confirm), which is what forced `useConfirmDialog` to start queueing. It was also a speed bump rather than a gate: the sheet is admin-only, `PUT /:id/costing` accepts the change regardless, and every figure is recorded in the activity trail with its old and new value. With it went `confirmInvoicedEdit`, `invoicedAck`, `declinedAtSeq`, the `'declined'` return, `runSave`'s `skipConfirm`, `flushCosting`'s `withoutPrompt` / `'needs-confirm'`, and `useCosting`'s `isInvoiced` option. **The manual time-entry form's own "change an invoiced job?" question is gone too** (2026-09-26) — the server refuses an invoiced job's time outright (see "A filed-away (invoiced/archived) job's time is locked" below), so asking first only delayed a refusal that was always coming. `useTimeEntries.js` now checks `isInvoiced` itself before opening the add/edit form, before saving, and before deleting, and just says "Reopen the job to change its time" (a stable-id toast) instead of asking; `useJobCardTimerActions.js`'s `handleStartItemTimer` carries the same check and message for Start, since a live per-part Start/Stop button has no confirm dialog of its own to remove. Nothing on the buttons themselves is greyed out yet — that lives in `ItemsTab.jsx`/`DetailsTab.jsx`, which don't read `isInvoiced` for this — so the buttons stay clickable and the refusal is what a click now produces, same as Costing's own no-lock-but-no-confirm choice above. **The `PUT` hands the stored figures back instead of the screen re-fetching them**: `PUT /:id/costing` responds `{ success, costing: buildCostingResponse(jobId, computed) }` (it already has `computed` — no second recompute), `updateCosting` in `useJobCardCosting` returns that mapped through `mapCostingResponseToForm`, and `runSave` moves `loadedRef` to it on every successful reply for the same job and opening (see above), and adopts it into `costingForm` under **two** guards: the edit counter is unchanged (nothing was typed while the request was in flight) **and** `jobCardIdRef.current` still equals the job the save was started for — a save fired as a job is closed can resolve after the next job has opened, and without the id check its figures would be adopted onto that other job. The three free-text notes are **not** taken from the reply: the server trims them for storage, so swapping the trimmed copy back into a box mid-sentence would eat the space just typed before the next word (`Weekend ` → `Weekendshift`); `runSave` carries the on-screen note text through instead (`TEXT_FIELDS`). That's what keeps the sticky grand total equal to the billed one: the server re-tallies labour hours from time entries on every `PUT`, so a worker finishing a run while an admin has the Costing tab open would otherwise leave the on-screen total permanently below the stored one (`refreshCosting` only fires on time-entry actions taken in *this* modal, and the timer poll's `onExternalStop` reloads time entries, not costing). A separate `GET` after the `PUT` is still avoided — that would spend a full costing recompute (a walk over every logged minute) per save. Regular labour hours are auto-calculated server-side from completed time entries (`getHoursByJobcard`), but the admin can **override** that figure by typing their own hours in the Costing tab's Hours box: the auto-tally is always kept in `labour_hours` (returned as `labourHoursCalculated`) while an optional `labour_hours_override` on `job_costings` holds the hand-typed number (NULL = use the live tally). The labour total uses the override when set, otherwise the tally. A reference line under the field shows the logged-time figure with a "Reset to logged" link that clears the override (**emptying any override box does the same** — `commitBox` in `useCostingDrafts.js` treats a box left blank as "drop the hand-edit", not as a typed 0, so it commits the calculated/logged figure and drops the override flag; a typed 0 is still a real 0, and gets committed and sent as one), and a manual entry survives a timer refresh (a timer tick only re-fills the box when no override is in place). **A blank box is never ambiguous — see the drafts paragraph above.** The old `NUMERIC_HOLD_FIELDS` / `blankRestoreRef` machinery (remember-what-it-held-before-clearing, restore-on-blur, restore-again-in-runSave-if-still-blank) is gone: with a draft holding the raw text until `commitBox` judges it, there is nothing left to remember and restore — a plain box left blank simply commits to 0, on purpose, and a box that still holds the figure it opened with was never blanked at all. The 2026-09-27 change that made a blank hold field save its restored figure instead of refusing outright is superseded by the same commit: there is no more "blank sitting there" state by the time a save can be asked for. Special hours are **not** derived from time entries — time blocks can no longer be marked "special". A one-time startup conversion (`init.js`, guarded by the `special_labour_manual_reset_at` settings flag) zeroes any special hours that were previously auto-tallied so the manual line starts clean; the seed scripts stamp that flag so freshly-seeded manual figures aren't wiped. **Overtime labour tiers**: Logged time is split by *when* each minute was worked into four tiers — normal, Overtime 1, Overtime 2, and public holiday — against the admin's weekly schedule + public-holiday list (the Labour Rates & Overtime settings above; every block start must land on the hour — `validateSchedule` in `settings-overtime.js` refuses a sub-hour minute outright, and restoring a backup snaps whatever schedule it carries to whole hours with the same `scheduleToWholeHours` helper the one-time startup conversion uses, so a sub-hour boundary can never come back in through a restore). The split is done a minute at a time — along the clock's whole minutes, so a block starting mid-minute bills its first partial minute on its own and a step never straddles a tier change — in local wall-clock (via `Intl`, so DST and midnight-spanning blocks fall out naturally) by `splitHours` (`server/src/utils/overtimeSplit.js`; each day is a cycle — a minute before the day's earliest block takes the last block's tier, so a late block carries over past midnight); all costing values are then worked out in **one place** — `computeLiveCosting` (`server/src/utils/costingCompute.js`), used by the costing GET/PUT routes. The company's overtime configuration (schedule, holidays, timezone, default rate, tier multipliers) is read through one place, `readOvertimeSettings` (`server/src/utils/overtimeSettings.js`) — `costingCompute.js` and the Workshop Statistics routes both read the company rules through it, so a malformed stored schedule/holidays value falls back the same way everywhere instead of erroring one page and not another. The "this job's own captured rules, else those live settings" fallback itself is also one function, `jobOvertimeBaseline` (`costingCompute.js`) — `computeLiveCosting` calls it for the full baseline (rules + base multipliers), and the Workshop Statistics route calls it per job (fed by `getJobCostingOvertimeRowsByJobcardIds` in `server/src/db/database.js`) for just the schedule/holidays/timezone piece it needs to split a worker's logged hours by the right rules. The app's starting pricing figures themselves (the default rate and the three tier multipliers, plus the materials/subcontractor markup defaults) are the one frozen list `COSTING_DEFAULTS` in `server/src/utils/costingDefaults.js` — every seed row, schema column default and settings fallback reads from it instead of carrying its own copy of the numbers. Every hand-written `Math.round(x * 10^k) / 10^k` and local `round2`/`round3` on the server is now `roundTo(n, places)` from `server/src/shared/round.js` — used by `costingCompute.js` and the statistics routes, each keeping its own number of decimals. `splitHours` itself returns its tier hours **unrounded** (normal hours reconciled from the unrounded total) — each caller rounds once, at the point it shows or stores a figure: 2 places in costing, and in statistics only after adding up across jobs. It used to round to 3 places inside the split as well, so a 1.2347 h run became 1.235 and then 1.24 instead of 1.23. It decides "was this figure sent?" **per key** (`has(key)` = own-property check on the body), never per request: a save that omits a figure keeps the stored value for it, so a partial body can't zero the figures it doesn't mention — and the screen now relies on that, sending only the figures it changed (see above). A figure that was sent but isn't a real, finite number (junk text, or a pasted 400-digit figure that reads as Infinity) is treated as not sent — the stored value stands — rather than read as 0 or, for an override, as "use the automatic figure". Every money line (each tier, special labour, materials, subcontractor) is rounded to whole cents where it is worked out, and the grand total adds up those rounded lines — plain multiplication used to store and audit figures like 51.74999999999999. Each tier charges `hours × base labourRate × that tier's multiplier` (multipliers come from settings — normal is always ×1). **Per-job overtime multipliers**: the two overtime tiers' multipliers are hand-overridable per job exactly like the hours — on the Costing tab each OT row's ×N chip is a small editable box; typing marks it hand-edited (amber cue + row dot) and saves to `labour_ot1_multiplier_override` / `labour_ot2_multiplier_override` on `job_costings` (NULL = follow this job's own captured baseline multiplier; values are floored at 1 server-side), with a "standard ×N" snap-back link under the box and the footer's reset-all covering multipliers too. The effective multiplier (override ?? this job's captured baseline) is what's stored in `labour_*_multiplier` and used for the tier's charge; a job that never touched its multipliers keeps following its own captured baseline (see Per-job rule ownership below), so recomputing always reproduces the billed figure. The holiday multiplier is settings-only (not per-job). Overrides are tracked in the audit trail. **Base rate default (new-jobs-only)**: the base labour rate has a company-wide default (`labour_default_rate` in settings, a number ≥ 0, set on the Labour Rates & Overtime page). The default **only seeds new jobs**: when a job card is created, its costing row is seeded with `labour_rate` = the current company default (`persistCosting(computeLiveCosting(id, { labourRate: default }))` in the create route, inside the create transaction). From then on the job **owns** its rate — changing the company default later never moves any already-created job. The base rate is editable per job on the Costing tab (a "use company default ($X)" convenience link fills it with the current default, but it's a plain value set — nothing "follows" the default afterwards). A job with no costing row yet (only old pre-feature jobs, since new jobs are seeded at creation) falls back to the current default as a starting suggestion until first saved. `labour_rate` is owned per job, so it never moves once the job is created. Each tier's auto-split hours are hand-**overridable** exactly like normal labour: `labour_ot1_override` / `labour_ot2_override` / `labour_holiday_override` on `job_costings` (NULL = use the auto split), with `labour_*_hours` holding the tally and `labour_*_total` the charge; the tier multipliers are also copied onto the row (`labour_*_multiplier`) so the exact rate each tier was charged at is recorded. On the Costing tab each tier shows a "From logged time" reference with a "Reset to logged" link. **An invoiced (archived) job's sheet is read-only until unarchived**: `GET /:id/costing` still recomputes on the spot (a view of a filed-away job's price is always live, never frozen), but `PUT /:id/costing` is a write like any other on the job and is refused by the shared `closedJobGuard` (see "One lock for a closed job" in `docs/notes/jobs-and-status.md`) with 409 `{ error: 'This job is invoiced and closed. Unarchive it to make changes.', code: 'JOB_CLOSED' }` — a manager must unarchive the job to correct a figure. It recalculates from the job's own rules — see Per-job rule ownership below. **Per-job rule ownership (no invoice-time freeze)**: every job captures its own copy of the overtime rules (schedule, holidays, timezone, base multipliers) into `job_costings` — `labour_schedule` / `labour_public_holidays` / `labour_timezone` / `labour_base_ot1_multiplier` / `labour_base_ot2_multiplier` / `labour_base_holiday_multiplier` — the first time its costing is computed (seeded at creation), exactly how `labour_rate` is already owned per job. `computeLiveCosting` reads the overtime rules from that captured copy (live settings only as the fallback for a not-yet-captured row) and writes them back, so the rules are **write-once** and a later change to the company overtime rules never moves an already-created job. Invoicing therefore takes **no** costing snapshot: recomputing an invoiced job always reproduces the billed number, and `GET /:id/costing` recomputes on the spot for open **and** invoiced jobs alike. Editing it (`PUT /:id/costing`) is refused once the job is archived, the same as every other write on it — see the paragraph above. The Workshop Statistics customer table's Invoiced Total follows the same rule: for each invoiced job in range it recomputes that job's live costing (`computeLiveCosting(jobId, null)`, read-only — nothing is persisted) rather than reading `job_costings.grand_total` directly, since that column is only refreshed by a pricing-sheet save and goes stale the moment logged time changes afterwards. A job whose recompute throws counts as $0 toward the total and is logged, rather than failing the whole statistics page. For jobs created *before* this feature (whose rules were never recorded), a one-time startup conversion (`init.js`, guarded by the `overtime_ownership_at` flag) stamps every un-captured costing row with today's rules as its own copy — best available, since the originals are unrecoverable — so from then on they too own their rules and recalculate like any other job. The client still flushes any unsaved pricing edits **before** invoicing so nothing is lost when the job is filed away. A one-time startup conversion (`init.js`, guarded by the `labour_hours_override_reset_at` settings flag) clears stale whole-job labour-hours overrides on non-invoiced jobs (the override now means *normal-tier only*, so an old whole-job override would double-count once overtime windows exist); the seed scripts stamp that flag. Hand-entered time blocks longer than ~31 days are rejected at entry (`checkEntryDuration`; an open block with no finish is measured from its start to now, so a start typed a year back can't become a running timer) and the minute-walk is safety-capped at 60 days so a bad legacy row can't stall a costing read. On the edit route this check only runs when the request is actually changing the start or finish time — a worker filling in pieces on a long-running stopped timer, with its own start/finish left untouched, must not be blocked by a span that was never theirs to fix. **A filed-away (invoiced/archived) job is closed to every write, time included**: timer start, manual add, edit (`PUT`, which also covers resuming/clearing a finish time) and delete on `jobcard-time-entries.js` are all refused before any write with 409 `{ error: 'This job is invoiced and closed. Unarchive it to make changes.', code: 'JOB_CLOSED' }` when the job's `archived === 1` — checked once, ahead of every job route, by the shared `closedJobGuard` middleware (`server/src/middleware/closedJob.js`; see "One lock for a closed job" in `docs/notes/jobs-and-status.md`) rather than a check pasted into each time route. **Stop is the one exception, allow-listed through** — a running timer must always be stoppable even if the job somehow got archived with one still going (invoicing itself refuses while any timer is running — see `docs/notes/jobs-and-status.md` — so this is a backstop, not the normal path). The Costing tab is locked the same way on an invoiced job (see "read-only until unarchived" above) — pricing, like everything else on a filed-away job, now needs an unarchive to correct. **Active timer protection**: Server blocks DELETE on entries with no `end_time` (returns 400). The per-item Progress section shows only a Stop button for active entries (no Edit/Delete until stopped). `useTimer` polls every 5s while a timer is active; if an admin stops it externally, the employee sees a toast notification and the time entries list refreshes automatically. **Stop timer form** (`StopTimerForm.jsx`): When a worker stops their timer, a focused card appears for the single item that was being worked on, asking for good pieces completed, scrap (binned + recycled), machines used, and description — plus the four-item Critical inspection sign-off when the job is on the Critical quality level. Good/scrap counts use a stepper (−/+ buttons either side of a typeable number; the buttons are skipped by Tab so keyboard flows field-to-field), a live scrap rate shows once any piece is entered, the description offers one-tap preset chips, and a long equipment list gets a filter box and a capped scrolling area (picked machines pinned on top). The header shows how long the run logged (start → end clock times). Submitting fills those fields on the existing time entry (the row created at start); a description is always required, and on a Critical job all four inspection answers are required too (good pieces, both scrap counts, and machines stay optional). Clicking X resumes the timer by clearing `end_time` on the original entry (preserves the original `startTime` and its `itemId`). **A non-management worker can only resume the run they just stopped**: the edit route (`PUT /:id/time-entries/:entryId`) refuses clearing `end_time` with 403 `{ error: "Only the run you just stopped can be resumed." }` unless all three hold — it's the worker's own most recently *started* block anywhere (no other block by that `user_id`, on any job, has a later `start_time`), its `end_time` is within the last 12 hours, and the worker has no other timer running right now. Without this, a worker could reopen any old stopped block of their own days later. Management is exempt (they can correct any block's times, including reopening an old one). A run under 15 seconds never reaches this form — the stop route discards it (see Timer endpoints) and the worker just sees a "Timer discarded — under 15 seconds" toast. On a finished entry's card (`TimeEntryCard.jsx`) the Critical inspection answers are collapsed behind a one-line "passed / flagged" summary that expands to the full Yes/No chips.
