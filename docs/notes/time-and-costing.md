# Time tracking, overtime and job costing

> Detail split out of CLAUDE.md. This is the largest and most trap-laden area in the app — read it before touching timers, logged work, overtime tiers or pricing.

## Timer endpoints

Timer endpoints: `GET /jobcards/active-timer` (authenticated), `POST /jobcards/:id/time-entries/start` (authenticated, body: `{ itemNumber, workerId? }` — `itemNumber` required, must match an existing line item; auto-assigns the timer's worker to the job if they aren't already an assignee, recorded as `self_assign`. Optional `workerId` lets **management start the timer for another worker** (e.g. setting someone up at a machine): management-only (everyone else gets 403), the worker is validated via `resolveWorkerId`; **both** start paths assign through the one `autoAssignWorker` helper, which takes the history action to record (`self_assign` for your own timer, `assign` for one set up for someone else), the running timer belongs to that worker (history names them under `worker`), and the client does **not** adopt it as the caller's own active timer), `POST /jobcards/:id/time-entries/:entryId/stop` (authenticated — **a run shorter than 15 seconds is treated as an accidental start/stop tap**: the block is deleted instead of logged, history records a `discard_timer` action, and the route returns `{ discarded: true }` so the client skips the stop form. **The discard also undoes what the Start did** — `server/src/utils/startTimerUndo.js` puts back the status move and the auto-assignment that Start made, so an accidental tap can't leave the job reading In Progress with the worker assigned and no work to show for it. **Nothing is remembered between the two taps**: both facts are read back out of the database, so a restart in between changes nothing and no second copy of them exists. The status move comes from the Start's own `start_timer` history entry, found by the block's start time (`historyQueries.getStartTimer`, a `json_extract(changes,'$.timer.to')` match — Start writes that same value into the block and into the entry), and the auto-assignment from `job_assignees.assigned_at` being no older than the block (anyone assigned before it was already meant to be there, so they stay). The status is only put back if nothing else moved it since; the reply carries `unassignedUserId` so an open job screen unticks that worker too, or the next Save would re-assign them. It deliberately does **not** call `syncStatusToWork` — that would just re-assert In Progress. Pinned by `server/scripts/check-startTimerUndo.js`, a standalone self-check against a throwaway database)

## Time entries, overtime tiers and the costing sheet

**Time entries**: Core fields only — item#, machine#, qty, scrap (bin + recycle), description, start/end time. A block stores **only** the part's permanent `item_id` (resolved when the block is created — inline in the timer-start route, via `resolveItemId` in the manual add/edit routes). There is **no** `item_number` column on `time_entries`: the displayed number is derived at read time by joining the part's **current** position (`LEFT JOIN job_items` in `getByJobcard` / `getById` / `getActiveByUser`). The API returns both (`itemId` / `itemNumber`), and anything matching a block back to a part must key off `itemId` — the number only says where the part currently sits on screen. **Blocks logged before 2026-06-10** (when work switched from position number to stable id, commit `26dc957`) have `item_id` NULL and were never backfilled; a database upgraded across that change still carries the old `item_number` column, so those blocks show up in the "What this job used" panel under "Work on a deleted part". A fresh or re-seeded database has neither the column nor any such rows. **Good pieces are whole numbers**: `qty` on a work block is stored as a whole number or NULL — `wholeQty` in `timeEntryHelpers.js` coerces it on both the add and edit/stop routes (`"2.5"` → 2, blank → NULL), and both entry boxes (the stop-timer stepper and the admin manual form via `handleTimeEntryChange`) accept digits only. This is what keeps the three readers in step: `syncStatusToWork` and statistics sum with `parseInt`, the part's progress bar with `parseFloat` — a fractional count made the part read Done while the job stayed In Progress. A one-time startup conversion in `runMigrations` folds any fractional text already stored down to its whole number (idempotent, no flag needed). **Scrap pieces**: Scrap is split into two destinations — `scrap_bin_qty` and `scrap_recycle_qty` (both integers, default 0) recording pieces binned vs sent to recycling; the line's total scrap and scrap rate sum the two. They are entered by the worker in the stop-timer form (two number fields) and by admins in the manual time-entry form (which carries both Scrap — Bin and Scrap — Recycle for adding and editing). The server clamps each to ≥ 0, treating blank/garbage as 0, and preserves the existing value if an update omits a field. **Critical-job inspection checklist**: Job cards on the **Critical** quality level (the job's `quality_level` label is `'CRITICAL'`) ask the worker an extra inspection checklist when they finish, stored on the time entry: `first_off_inspection`, `in_process_validation`, `measuring_equipment_verification`, `equipment_checks` (each 1 = yes / 0 = no / NULL = not applicable, i.e. the job wasn't Critical) plus a free-text `equipment_checks_comments`. On a Critical job all four Yes/No answers are **required before a finished block can be saved** — enforced client-side (the stop-timer Submit button stays disabled until all four are answered) and server-side in `checkCriticalInspection` (`jobcard-time-entries.js`) on both the add and edit routes, which 400s a completed block missing any answer. Non-Critical jobs never show the checklist and store NULLs. The admin manual time-entry form also shows the checklist when the job is Critical (so an admin can record/correct the answers), and each finished entry's card displays the answers as Yes/No chips with the equipment comment. (The schema's legacy-drop list deliberately excludes `first_off_inspection` / `in_process_validation` — they are live again for this feature.) **Crediting work**: The admin manual time-entry form requires picking the worker who actually did the work (a `workerId` select), so hours land under that person, not the admin filling in the form. The server validates the chosen worker is a real, active account, auto-assigns them to the job (mirroring what a self-started timer does), and records the worker in history. On edit, only an admin can re-credit a block to a *different* worker (a regular worker editing their own block keeps it under themselves); leaving the owner unchanged is always allowed, so an old block owned by a since-deactivated worker can still have its other fields corrected. The machines field on a time entry is a multi-select (`CheckboxDropdown`) stored as one comma-joined string (e.g. `"5, 9"`), matching the stop-timer form. The per-item Progress section shows scrap total + scrap rate (scrap / every piece made, i.e. good + scrap — the same formula the stop-timer form and the statistics page use, so it can never exceed 100%; hidden until any piece is recorded). **Per-item timers**: Each line item has its own Start/Stop button (`LineItemTimerButton.jsx`); starting a timer requires picking an item, and the active timer is bound to that `itemNumber` (server validates the item exists on the job card, returns 409 if a timer is already running on another job/item with the conflicting timer's `jobcardId` + `itemNumber` for "stop & switch" prompts). **Special labour**: Special labour is a **manually-entered costing line**, not a per-time-entry flag. An admin types the special-labour hours and rate directly on the Costing tab (`labour_special_hours` / `labour_special_rate` on `job_costings`); the special total is `hours × rate`. **Cost-line notes**: each of the three manual cost lines (special labour, materials, subcontractor) carries a free-text note saying what the cost covers — `labour_special_description` / `materials_description` / `subcontractor_description` on `job_costings`, trimmed and capped at 300 characters server-side and stored NULL when blank. It renders as a "What this covers" box on its own row under that line's figures on the Costing tab (auto-capitalised on blur like every other text field), is tracked in the audit trail as text, and is exported in the Excel Costing sheet. **"What this job used" info panel**: an info icon beside the "Job costing" title in the sticky header toggles a read-only panel (`tabs/CostingBreakdown.jsx`, `.cost-brief` / `.cb-*` styles) that folds out between the header and the Labour block. It is the supporting evidence for the pricing boxes below it, and it is **one table**, read left to right: **part · material · treatment & supplier · machine · who · hours**. A part's item cell, material and treatment cells are `rowSpan`-merged down its machine rows, so however many runs a part took it still reads as one horizontal band and nothing about it is looked up in two places (an earlier split into two tables — hours and bought-in — was rejected for exactly that reason). Deliberately **six columns, not eight**: the supplier is stacked under its treatment (one fact — who is doing what to this part) and the part's own total sits under its name rather than in a column of its own; both were costing width that every other column paid for as an ellipsis. Each hours cell shows the decimal (the form the Hours boxes take) with the h/m reading under it, right-aligned in tabular mono; the job total closes the column in the `tfoot`. Machine **codes only** (`CNC-01`, `CNC-01 + MILL-01`) — carrying the make and model as well truncated the material and the worker's name to pay for it — and a treatment with no supplier is called out in the caution colour because it can't be priced. It is built entirely from data the job screen already holds (`formHook.lineItems` + `timeEntries`, passed as props — it needs no machines list), so it adds **no** new route and no saving; option names come from the shared cached tag lists (`useTags`), the same ones the job screen already loads. Only **finished** blocks are counted (running timers are called out in a note but excluded, matching how costing tallies hours); a block logged on several machines at once is kept as one combined row rather than split, since its span can't be divided between them without inventing figures; and blocks are matched to a part by the part's **permanent id** (`itemId` on the time entry — `item_id` is emitted by `toCamelCase` in `server/src/utils/timeEntryHelpers.js` and carried through `mapTimeEntryFromApi`), never by `itemNumber` — the number is only a display position that shifts as parts are added or removed — with blocks whose part has since been deleted falling into a "Work on a deleted part" group so the totals still add up. Tag values are named via each category's `rawTags` (not `useTags`'s `labelOf`, whose identity changes every render and would rebuild the table on the job screen's one-second timer re-render). The table **never wraps** — a wrapping table narrows itself by stacking words, which pushed the hours off the right edge instead of scrolling to them; cells ellipsis and `.cb-scroll` scrolls sideways below its `min-width`. **Grand total placement**: the grand total lives in the Costing tab's header bar, which sticks to the top of the scrolling panel (`position: sticky` — hence no `overflow` clipping on `.costing-sheet`), so the figure stays readable while the sheet is scrolled; there is no second grand-total block at the bottom. **The Costing tab saves itself — there is no Save button.** Every edit calls `markEdited` (bumps an edit counter, sets `costingDirty`, shows `pending`) and re-arms a 1 s countdown in `useCosting`; the countdown effect keys off `[costingForm, costingDirty, savingCosting, autoSavePaused]` only — never a per-render function identity, or the job screen's one-second timer re-render would restart it forever — and fires through a `saveNowRef`. So a burst of typing (or tabbing across boxes) lands as **one** save and one audit entry. `flushCosting()` saves immediately and is called on Enter anywhere in the sheet, on switching away from the Costing tab, and on closing the job; `handleSaveCosting()` is `saveNow({ skipConfirm: true })` and stays for **`JobIdentityStrip` only**, which runs its own "this will archive the job / your unsaved costing will be billed" prompt before calling it. `handleSubmit`'s pre-invoice flush uses plain **`flushCosting()`**, *not* `handleSaveCosting` — that path is reached when the job is **already** invoiced (the strip applies the status change itself), so skipping the confirm there would let the job form's Save quietly restate a billed total without ever asking "change an invoiced job?". It aborts only on an outright **`=== false`** (the save failed), *not* on any non-`true`: declining the invoiced-job question returns `'declined'`, which means the billed figures were put back and nothing is left pending — so the rest of the job save (dates, parts, notes, which have nothing to do with pricing) carries on instead of the Update button silently doing nothing. A `costingSaveState` of `idle | pending | saving | saved | error` drives the status line that replaced the button (the `error` state offers "try again"). Four guards make auto-save safe. (1) Saves are **serialised, not deduplicated**: `saveNow` chains a second caller *behind* the in-flight save (`inFlight.current.then(runNext, runNext)`, with `runNext` reading a `runSaveRef` so the queued attempt sends the figures as they are when it finally runs) rather than handing back the in-flight promise — that promise is bound to `costingForm` as it was when it started, so returning it would tell an invoicing or closing caller "saved" about keystrokes that were never sent, and file the job away billing the older number. (2) A save only clears `costingDirty` when the **edit counter is unchanged**, so typing during an in-flight save isn't marked saved (and re-arms the countdown when it finishes). (3) A failed save sets `autoSavePaused` so a down server gets one attempt per typing burst, not one per second. (4) **A save is refused while `loadedRef` is null** — i.e. the job's stored costing never arrived, because the `GET` failed or hasn't finished. The form would still be `getDefaultCostingForm()` (every figure 0, every note blank) and `computeLiveCosting` takes every field from `incoming` when `incoming` is truthy, so one keystroke on that empty sheet would otherwise write zeros over the job's real rate, tier overrides, materials, subcontractor figures and notes. The Costing tab never shows that sheet either: `CostingTab` takes `loaded` / `loadFailed` / `onRetryLoad` and renders a plain "Loading pricing…" or "couldn't be loaded" placeholder (`.costing-placeholder`) with a Try again button instead — the `multEditing` `useState` sits **above** that early return so the hook order is stable. **The lazy `GET` is guarded the same way**: `useJobCardCosting` keeps a `loadSeq` counter, bumped in an effect **cleanup** keyed on `[isOpen, jobCardId]` (i.e. on close and on job switch — **not** in `resetCosting`, whose call from the modal's open effect lands *after* the load effect has already fired for a tab left on Costing, so a bump there discarded the new job's own reply and stuck the tab on "Loading pricing…"), and `loadCosting` drops a reply whose counter has moved — the fetch walks every logged minute, so a reply for a job closed seconds ago can land after the next job has opened and would otherwise paint (and, on the next keystroke, save) that job's figures onto the new one. `resetCosting` in `useCosting` also bumps `editSeq`, so a close-time save that resolves after the same job is reopened fails the "nothing typed since" check instead of being adopted onto the freshly blanked form. **All of the job screen's costing wiring lives in `useJobCardCosting.js`**, not in `JobCardModal` — the lazy `GET` and its `costingLoadFailed` flag (set in the catch, cleared on a successful load and by `resetCosting`), the `confirmInvoicedEdit` dialog, the `updateCosting` operation, and the two flush-on-the-way-out effects (leaving the tab, closing the job). It wraps `useCosting` and re-exports its whole API plus `costingLoaded` / `costingLoadFailed` / `retryLoadCosting`, so the modal holds no costing state of its own and stays under the 600-line limit. **The invoiced-job confirm is asked once per opening**, not per save: `useCosting` takes `isInvoiced` + `confirmInvoicedEdit` and remembers the answer in `invoicedAck` (reset when the costing loads / `resetCosting`); declining snaps the form back to the loaded figures via `formFromCosting`, toasts that the change wasn't kept (the figures visibly revert, so it can't pass unnoticed), returns `'declined'` rather than `false`, **and stamps `declinedAtSeq` with the current edit counter**, so a save queued behind the declined one is dropped rather than asking the same question again — the next real keystroke bumps the counter and the question can be asked afresh. On close no dialog can render (the modal returns `null`), so `flushCosting({ withoutPrompt: true })` returns `'needs-confirm'` and the hook toasts that the change wasn't kept. **The `PUT` hands the stored figures back instead of the screen re-fetching them**: `PUT /:id/costing` responds `{ success, costing: buildCostingResponse(jobId, computed) }` (it already has `computed` — no second recompute), `updateCosting` in `useJobCardCosting` returns that mapped through `mapCostingResponseToData`, and `runSave` adopts it into `costingForm` + `loadedRef` under **two** guards: the edit counter is unchanged (nothing was typed while the request was in flight) **and** `jobCardIdRef.current` still equals the job the save was started for — a save fired as a job is closed can resolve after the next job has opened, and without the id check its figures would be adopted onto that other job. The three free-text notes are **not** taken from the reply: the server trims them for storage, so swapping the trimmed copy back into a box mid-sentence would eat the space just typed before the next word (`Weekend ` → `Weekendshift`); `runSave` carries the on-screen note text through instead (`TEXT_FIELDS`). That's what keeps the sticky grand total equal to the billed one: the server re-tallies labour hours from time entries on every `PUT`, so a worker finishing a run while an admin has the Costing tab open would otherwise leave the on-screen total permanently below the stored one (`refreshCosting` only fires on time-entry actions taken in *this* modal, and the timer poll's `onExternalStop` reloads time entries, not costing). A separate `GET` after the `PUT` is still avoided — that would spend a full costing recompute (a walk over every logged minute) per save. Regular labour hours are auto-calculated server-side from completed time entries (`getHoursByJobcard`), but the admin can **override** that figure by typing their own hours in the Costing tab's Hours box: the auto-tally is always kept in `labour_hours` (returned as `labourHoursCalculated`) while an optional `labour_hours_override` on `job_costings` holds the hand-typed number (NULL = use the live tally). The labour total uses the override when set, otherwise the tally. A reference line under the field shows the logged-time figure with a "Reset to logged" link that clears the override (**emptying any override box does the same** — `handleCostingChange` in `useCosting.js` treats a cleared hours/multiplier box as "drop the hand-edit", not as a typed 0, so the save sends no override and the reply refills the box with the logged / company figure; a typed 0 is still a real 0), and a manual entry survives a timer refresh (a timer tick only re-fills the box when no override is in place). The override is tracked in the audit trail (the auto-tally itself is not, so an automatic recalculation isn't attributed to whoever saved). Special hours are **not** derived from time entries — time blocks can no longer be marked "special". A one-time startup conversion (`init.js`, guarded by the `special_labour_manual_reset_at` settings flag) zeroes any special hours that were previously auto-tallied so the manual line starts clean; the seed scripts stamp that flag so freshly-seeded manual figures aren't wiped. **Overtime labour tiers**: Logged time is split by *when* each minute was worked into four tiers — normal, Overtime 1, Overtime 2, and public holiday — against the admin's weekly schedule + public-holiday list (the Labour Rates & Overtime settings above). The split is done a minute at a time in local wall-clock (via `Intl`, so DST and midnight-spanning blocks fall out naturally) by `splitHours` (`server/src/utils/overtimeSplit.js`; each day is a cycle — a minute before the day's earliest block takes the last block's tier, so a late block carries over past midnight); all costing values are then worked out in **one place** — `computeLiveCosting` (`server/src/utils/costingCompute.js`), used by the costing GET/PUT routes. It decides "was this figure sent?" **per key** (`has(key)` = own-property check on the body), never per request: a save that omits a figure keeps the stored value for it, so a partial body (a hand-made request, or a future partial save) can't zero the figures it doesn't mention. The screen always sends every box, so the client is unaffected. Each tier charges `hours × base labourRate × that tier's multiplier` (multipliers come from settings — normal is always ×1). **Per-job overtime multipliers**: the two overtime tiers' multipliers are hand-overridable per job exactly like the hours — on the Costing tab each OT row's ×N chip is a small editable box; typing marks it hand-edited (amber cue + row dot) and saves to `labour_ot1_multiplier_override` / `labour_ot2_multiplier_override` on `job_costings` (NULL = follow this job's own captured baseline multiplier; values are floored at 1 server-side), with a "standard ×N" snap-back link under the box and the footer's reset-all covering multipliers too. The effective multiplier (override ?? this job's captured baseline) is what's stored in `labour_*_multiplier` and used for the tier's charge; a job that never touched its multipliers keeps following its own captured baseline (see Per-job rule ownership below), so recomputing always reproduces the billed figure. The holiday multiplier is settings-only (not per-job). Overrides are tracked in the audit trail. **Base rate default (new-jobs-only)**: the base labour rate has a company-wide default (`labour_default_rate` in settings, a number ≥ 0, set on the Labour Rates & Overtime page). The default **only seeds new jobs**: when a job card is created, its costing row is seeded with `labour_rate` = the current company default (`persistCosting(computeLiveCosting(id, { labourRate: default }))` in the create route, inside the create transaction). From then on the job **owns** its rate — changing the company default later never moves any already-created job. The base rate is editable per job on the Costing tab (a "use company default ($X)" convenience link fills it with the current default, but it's a plain value set — nothing "follows" the default afterwards). A job with no costing row yet (only old pre-feature jobs, since new jobs are seeded at creation) falls back to the current default as a starting suggestion until first saved. `labour_rate` is owned per job, so it never moves once the job is created. Each tier's auto-split hours are hand-**overridable** exactly like normal labour: `labour_ot1_override` / `labour_ot2_override` / `labour_holiday_override` on `job_costings` (NULL = use the auto split), with `labour_*_hours` holding the tally and `labour_*_total` the charge; the tier multipliers are also copied onto the row (`labour_*_multiplier`) so the exact rate each tier was charged at is recorded. On the Costing tab each tier shows a "From logged time" reference with a "Reset to logged" link. An invoiced job's sheet stays **fully editable** — there is no locked/frozen state; saving just asks for an on-screen confirm first, then recalculates from the job's own rules — see Per-job rule ownership below. **Per-job rule ownership (no invoice-time freeze)**: every job captures its own copy of the overtime rules (schedule, holidays, timezone, base multipliers) into `job_costings` — `labour_schedule` / `labour_public_holidays` / `labour_timezone` / `labour_base_ot1_multiplier` / `labour_base_ot2_multiplier` / `labour_base_holiday_multiplier` — the first time its costing is computed (seeded at creation), exactly how `labour_rate` is already owned per job. `computeLiveCosting` reads the overtime rules from that captured copy (live settings only as the fallback for a not-yet-captured row) and writes them back, so the rules are **write-once** and a later change to the company overtime rules never moves an already-created job. Invoicing therefore takes **no** costing snapshot and there is **no lock**: recomputing an invoiced job always reproduces the billed number, and `GET /:id/costing` recomputes on the spot for open **and** invoiced jobs (every job's PUT is allowed, gated only by an on-screen "change an invoiced job?" confirm on the client). For jobs created *before* this feature (whose rules were never recorded), a one-time startup conversion (`init.js`, guarded by the `overtime_ownership_at` flag) stamps every un-captured costing row with today's rules as its own copy — best available, since the originals are unrecoverable — so from then on they too own their rules and recalculate like any other job. The client still flushes any unsaved pricing edits **before** invoicing so nothing is lost when the job is filed away. A one-time startup conversion (`init.js`, guarded by the `labour_hours_override_reset_at` settings flag) clears stale whole-job labour-hours overrides on non-invoiced jobs (the override now means *normal-tier only*, so an old whole-job override would double-count once overtime windows exist); the seed scripts stamp that flag. Hand-entered time blocks longer than ~31 days are rejected at entry (`checkEntryDuration`) and the minute-walk is safety-capped at 60 days so a bad legacy row can't stall a costing read. **Active timer protection**: Server blocks DELETE on entries with no `end_time` (returns 400). The per-item Progress section shows only a Stop button for active entries (no Edit/Delete until stopped). `useTimer` polls every 5s while a timer is active; if an admin stops it externally, the employee sees a toast notification and the time entries list refreshes automatically. **Stop timer form** (`StopTimerForm.jsx`): When a worker stops their timer, a focused card appears for the single item that was being worked on, asking for good pieces completed, scrap (binned + recycled), machines used, and description — plus the four-item Critical inspection sign-off when the job is on the Critical quality level. Good/scrap counts use a stepper (−/+ buttons either side of a typeable number; the buttons are skipped by Tab so keyboard flows field-to-field), a live scrap rate shows once any piece is entered, the description offers one-tap preset chips, and a long equipment list gets a filter box and a capped scrolling area (picked machines pinned on top). The header shows how long the run logged (start → end clock times). Submitting fills those fields on the existing time entry (the row created at start); a description is always required, and on a Critical job all four inspection answers are required too (good pieces, both scrap counts, and machines stay optional). Clicking X resumes the timer by clearing `end_time` on the original entry (preserves original `startTime` and `itemNumber`). A run under 15 seconds never reaches this form — the stop route discards it (see Timer endpoints) and the worker just sees a "Timer discarded — under 15 seconds" toast. On a finished entry's card (`TimeEntryCard.jsx`) the Critical inspection answers are collapsed behind a one-line "passed / flagged" summary that expands to the full Yes/No chips.
