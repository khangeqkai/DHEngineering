# Client-side patterns and traps

> Detail split out of CLAUDE.md. Read before touching the job screen, the sign-in screen, error handling in the shared sender, or the activity trail colours.

## Talking to the server

- **"The server isn't answering" is one shared error, and only reads re-ask.** The server can be missing for a second or two — it is still finishing start-up, or (in dev, where `npm start` runs it as a separate process with `node --watch-path`) it restarted itself after a saved file. `_send` in `api.js` turns both shapes of that into a single `Error` carrying `code: 'SERVER_UNREACHABLE'` and one plain-English message: a `fetch` that rejects outright (nothing listening), **and** a `5xx` whose content-type isn't JSON — the Vite dev proxy answers `500 text/plain` with an empty body when its target is down, which is the same situation wearing a status code. That heuristic is safe because every real 5xx the app produces is `res.status(...).json(...)` (the catch-all handler in `server/index.js`, the restore-in-progress 503); the only non-JSON 5xx lives in `setup-trust.js`, outside `/api`. `request()` then wraps `_send` in a retry that applies **to reads only** — no `options.method`, or `GET` — 3 extra attempts 1.5 s apart. **A write is never re-sent**: it may have landed just before the server went away, and sending it twice would create two of whatever was being saved. This is why every non-GET goes through `_post`/`_put`/`_patch`/`_del` (which always set `method`) rather than calling `request()` bare — a body-carrying call with no method would be classified as a read and retried. Note `POST /jobcards/attachment-warnings` is read-shaped but sent as a write, so it deliberately gets no retry.

- **The login screen waits for the server before offering the form.** `api.isServerReady()` calls `/health` (outside `/api`, no sign-in needed, proxied in dev by `vite.config.js`, and it never throws — it returns false). `Login.jsx` holds it in `serverReady`: `null` = not asked yet (form works as normal), `true` = answering, `false` = not answering. Only `false` holds anything back — an amber `.login-notice` appears and the button reads "Waiting for the server...". While `false` it re-asks every 2 s until it answers. A sign-in that fails with `SERVER_UNREACHABLE` is **not** shown as a sign-in error (nothing the person typed was wrong): it flips `serverReady` to `false` and bumps `readyCheckKey` to restart the watcher. In the packaged app this rarely fires — Electron already polls `/health` before showing the window — so it mostly covers dev, where the window opens as soon as Vite is ready.

## The activity trail's one shared list of actions

- **One list names every history action.** `client/src/utils/activityColors.js` holds `ACTION_COLORS` — every action name passed to `recordHistory` and nothing else — plus `ACTION_NAMES` (its keys, in display order) and `actionColor(action)`. The global Activity Log, the per-job Activity tab and the search page's **activity** filter chips all read it; the three used to carry their own copies, which drifted (a new action was tinted on one screen and left muted grey on the others, and four actions the server records were missing from the search filter entirely while two of its options matched nothing). Adding a `recordHistory` action means adding it here. Colour convention: `--accent-ready` for something added, `--accent-caution` for something taken away, `--primary-accent` for something changed. Note the server does **not** validate the search `action` param against a list — it binds the values straight into an `IN (...)`, so a name missing here is simply unfilterable, not an error.

## The job screen

- **JobCardModal**: Modular tab-based UI with custom hooks for each tab's logic (`useJobCardCosting.js` → wraps `useCosting.js`, `useTimeEntries.js`, `useTimer.js`, `useJobNotes.js`, `useCamera.js`, `useJobCardForm.js`, `useJobCardSave.js`, `useUnsavedGuard.js`, `useContactSearch.js`, `useJobFiles.js`, `useActivityLog.js`). The Save flow itself — validation, resolving the customer on a new job, the pre-invoice pricing flush, the "files still missing" 409 retry — lives in `useJobCardSave.js`, not in the modal, which keeps `JobCardModal.jsx` under the 600-line limit. Everything about work that would be lost if the screen went away — the close question, the refresh guard, the inactivity registration and the spoken status — lives in `useUnsavedGuard.js` for the same reason.

- **A screen that closes must not clear which record it was showing in the same render.** The job screen saves pending pricing edits on the way out, and that save needs the job id; a caller wiring `isOpen={!!id}` and `onClose={() => setId(null)}` off one state variable silently drops the save (`runSave` returns early on a null id). Track open/closed separately from the id — `JobCardList` (`isModalOpen` + `editingCardId`) and `SearchPage` (`modalOpen` + `modalJobId`) both do.

- **A refresh mid-edit must merge, never replace, unsaved form state.** Starting a part timer re-reads the job (the server may have auto-assigned the timer's worker and moved the status); `handleStartItemTimer` in `JobCardModal.jsx` folds in only that one worker and the status, because replacing the whole assignee list from the server silently undid any ticks/unticks made before pressing Start. Stop-timer and the 5 s poll reload time entries / status only.

- **A save that leaves the screen open must adopt the stored ids back — without disturbing the rows themselves.** A line item added on the job screen carries a client-side placeholder id until it is saved; the save reply carries the real `item:` ids, plus the server's renumbered `item_number` (parts are renumbered 1..N by their position in the payload). `handleSubmit` (in `useJobCardSave.js`) therefore calls `markSaved(result.items, sent)` (in `useJobCardForm.js`) after an update, because the job stays open — without it every part on screen keeps its placeholder id, and work logged from then on is matched against an id no stored part has, so the "What this job used" panel files those hours under "Work on a deleted part". `markSaved` does **not** replace the on-screen rows with the reply: it matches each on-screen row to its reply row by the id that was actually sent for it, not by position; a row with no server id yet (a part added this same save) has nothing to match on, so it falls back to claiming the leftover reply rows in order. **A sent row whose stored id does not come back at all** (while the reply carried rows) means someone else deleted that part server-side while this job was open — `jobcard-mutations.js` then recreates it under a fresh id, which would fall through to the leftover matching and be handed to the wrong row, sticking every hour and file logged afterwards to the wrong part permanently. `markSaved` detects that, applies **nothing** (no ids, no baseline) and returns `{ conflict: true }`; `useJobCardSave.js` says so plainly and reloads the job from the save reply itself (`setFormDataFromJobCard(result)` — `formatJobcard`, the same shape the GET returns, so no extra fetch). That reload does replace anything typed mid-save, which is the deliberate trade: a guessed match is silent and permanent. Either way the row keeps its own on-screen content — a part whose description was edited while the save was in flight keeps that edit — and adopts back both the stored id and the stored item number from its matched reply row, not the id alone: because the server renumbers every part 1..N by its position in the payload, a part deleted (or reordered) on screen would otherwise leave the on-screen numbers out of step with what's actually stored, which matters because a part timer picks its part by that number.

- **The job window frames itself when there are edits no Save has sent.** Everything else on that screen reports itself — the timer counts, the costing sheet says "Saved", the file dots fill in — but the details, parts, assignees, description, priority and due date all wait for Update, and the window said nothing. `useJobCardForm.js` keeps a snapshot of the job as last loaded or saved and exposes `isDirty`; `JobCardModal.jsx` passes it (OR'd with a customer-fields check — see below) to `BottomSheet` as `unsaved`, which adds the `modal-unsaved` class (an amber ring drawn outside the border in `App.css`, so nothing shifts) around the whole job window, and the footer button reads "Save changes" instead of "Update" so the signal isn't carried by colour alone. A brand-new card is measured against a pristine, empty-form baseline (not `null`) from the moment it opens, so a half-filled new card is known to be unsaved even though nothing has reached the server yet — a `null` baseline could never turn dirty before the first Save, which is exactly the case this guard exists for. That dirtiness deliberately does **not** reach the amber frame: `JobCardModal.jsx` passes `unsaved={isEdit && isDirty}` to `BottomSheet`, so the ring is gated to an existing job only, and a brand-new card never turns amber no matter what is typed into it — flagging every new card for the whole of an ordinary fill-in-and-save task would just train people to stop looking at the colour. The close question is not gated the same way: `useUnsavedGuard.js` reads `hasUnsavedWork`, which starts from `isDirty` with no `isEdit` in front of it, so closing a half-filled new card still asks first ("Discard changes" / "Keep editing") — the same pristine baseline that keeps the frame clean is exactly what makes that confirm fire. Three things the snapshot deliberately does *not* count, because none of them is waiting on a Save: **status** (choosing one sends itself, and the server nudges it when work starts or finishes — so it is stripped from the form snapshot); **a worker the server added or removed on its own** (a started timer credits its worker, a discarded tap takes them back off — `creditAssignee`/`dropAssignee` move the snapshot with the list — but only until the next Save lands, because a job save hands over a whole `assigneeIds` list and `jobcard-mutations.js` deletes the stored list and rebuilds it from what was sent, so a credit made *while a save was in flight* is undone the moment that save arrives. `markSaved` therefore takes the assignee baseline straight from `sent.assignees` and folds in nothing: the credited worker is still on screen, so the card correctly reads unsaved and the next Save puts them back. Replaying those server-side ops into the new baseline was tried and is wrong — it showed the worker assigned, reported no unsaved edits, and the server no longer had them on the job at all); and **part ids specifically** (a part added on screen carries a placeholder id until saved, so the stored id coming back would read as an edit — the rest of the part is very much counted, see above). One thing it can't count at all: on a brand-new job the customer is picked through `useContactSearch`, a separate hook whose state `useJobCardForm` never sees, so `JobCardModal.jsx` folds in its own check of `contactHook.contactFormData` (non-empty on a new job only — existing jobs freeze the customer fields read-only) rather than reaching into `useJobCardForm` for it. The snapshot taken at Update time is the one that went out for the form fields and assignees (`captureSent`) — nothing on screen is locked during a save, so anything typed mid-flight stays marked unsaved until it is actually sent. Parts follow the same rule: their baseline is the rows that were **sent**, with each matched reply row's id and item number folded in — never the rows on screen when the reply lands. Taking it from the screen was tried and is wrong: it adopted a part description typed *during* the save as already saved, clearing the amber ring and silencing the close question on an edit that had never been sent. What made it tempting was the blank new-part row, which `validateJobCardForm` drops before the payload is built, so the reply can never account for it and a sent-rows baseline held a row the two sides could never agree on — leaving a perfectly saved job flagged unsaved for as long as it stayed open. That belongs in the comparison, not the baseline: `snapshotItems` now drops any row with an empty description, the same rule the payload applies, so a blank row reaches neither the server nor either side of the dirty check. The blank row itself is left where the user put it rather than swept off the screen: typing a description into it marks the card unsaved again, and the next save drops it the same way. **Closing a job card with unsaved edits now asks first**: `JobCardModal.jsx`'s `handleRequestClose` is wired as `BottomSheet`'s `onClose`, covering Escape and the header X in one place; it closes straight away when nothing is dirty, and otherwise confirms ("Discard changes" / "Keep editing") before calling the real `onClose`. A save already in flight does **not** block the close or get cancelled by it — the confirm (if anything is dirty) runs the same as any other close, and the request keeps going in the background, landing its own toast/`onSuccess` when it resolves. **Questions queue rather than overwrite each other.** `useConfirmDialog` used to hold a single `resolveRef`, so a second question asked while one was up replaced it and the first promise never settled. Escape can't cause that — `ConfirmDialog` and `BottomSheet` both gate on `isTopModal`, so while a question is up Escape only answers *it* and never reaches the screen underneath. What could was a question raised by a **timer**: the pricing sheet's old "change an invoiced job?" came off the 1 s autosave countdown, so on an invoiced job with both a job edit and a pricing edit waiting, Escape put up "close and lose them?" and the invoiced question reworded it mid-read a second later; the close `await` never resolved and the card silently refused to shut. That question has since been removed outright (see `time-and-costing.md`), so nothing in the app currently asks without a click — the queue stays as the structural guarantee, and still covers the two things that bite regardless: a double-click answering one question and stranding the next, and a question left outstanding when the screen goes away. Questions sit in a FIFO queue — one on screen, the rest waiting — with a 250 ms gap between them so the click answering one cannot land on the next and the box visibly goes and comes back. `JobCardModal.jsx` calls the hook's `cancelConfirms` when `isOpen` goes false, answering anything outstanding `false`: past that point nothing renders the box, so a question left on the queue would never settle and would park every later question behind it for the rest of the session. Pinned by `client/scripts/check-confirmQueue.mjs`. The question is asked about `hasUnsavedWork`, deliberately wider than `isDirty`: it also counts **a comment typed into the Comments tab but never posted** (`jobNotes.newNote`) and **the details form of a run that was just stopped** (`timer.showEntryForm` — the run itself is recorded, but the machine, quantities and checks about to be recorded against it are not). Those two are kept out of `isDirty` on purpose, because `isDirty` drives the amber ring and the footer button's wording and both of those mean *edits waiting on Save* — neither of these is, and the stop form is already a panel in its own right, so framing the whole window amber for it would dilute the signal. Two doors that used to bypass the question entirely are now covered as well. **A browser refresh or tab close** (`beforeunload`, registered while `hasWorkToLose`) stops and asks — the browser only ever shows its own fixed wording there, so it cannot carry the message above, but Ctrl+R no longer empties a half-filled card in silence. `hasWorkToLose` is `hasUnsavedWork` **plus** `costingDirty`, and that addition is the point: closing the job flushes pricing to the server (`useJobCardCosting`'s effect on `isOpen`), but a refresh and the inactivity sign-out never run that flush, so a money figure typed inside the 1 s autosave window — or any time after a failed save, when autosave is paused — went without a word. `costingDirty` stays out of `hasUnsavedWork` itself, so the amber ring and the close confirm are unchanged. **The packaged app needs its own handler for this**: Electron never shows Chromium's "Leave site?" dialog — it fires `will-prevent-unload` on the webContents, and with nothing listening its default is to cancel the close silently, so the desktop app simply refused to close and looked frozen. `client/electron/main.js` registers that handler and shows a real `showMessageBoxSync` ("Leave Without Saving" / "Keep Editing", the safe choice as both `defaultId` and `cancelId`); `event.preventDefault()` there means *proceed* with the close, so it is called only on the leave branch. **The inactivity sign-out** is told what is at stake: `useUnsavedGuard.js` calls `registerUnsavedWork('job card')` from `AuthContext` while there is something to lose, and `InactivityWarningModal` reads that label once when it appears and adds "You have an unsaved job card. It will be lost unless you continue." to a countdown that previously ran in silence while a manager was away from their desk (admins are exempt from the inactivity timer; managers and employees are not). It is the read-only companion to `registerBeforeLogout`, which `useTimer.js` already uses to put a half-stopped run back on the clock before the pass is torn up. Finally, the unsaved state is now **said as well as shown**: a visually hidden `role="status"` line beside the footer button reads "This job card has unsaved changes." / "All changes saved." — the same approach `CostingTab.jsx`'s own status line already takes. It stays empty until the card has actually been edited, so a card nobody has touched announces nothing on arrival.
