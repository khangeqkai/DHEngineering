# Client-side patterns and traps

> Detail split out of CLAUDE.md. Read before touching the job screen, the sign-in screen, error handling in the shared sender, or the activity trail colours.

## Talking to the server

- **"The server isn't answering" is one shared error, and only reads re-ask.** The server can be missing for a second or two — it is still finishing start-up, or (in dev, where `npm start` runs it as a separate process with `node --watch-path`) it restarted itself after a saved file. `_send` in `api.js` turns both shapes of that into a single `Error` carrying `code: 'SERVER_UNREACHABLE'` and one plain-English message: a `fetch` that rejects outright (nothing listening), **and** a `5xx` whose content-type isn't JSON — the Vite dev proxy answers `500 text/plain` with an empty body when its target is down, which is the same situation wearing a status code. That heuristic is safe because every real 5xx the app produces is `res.status(...).json(...)` (the catch-all handler in `server/index.js`, the restore-in-progress 503); the only non-JSON 5xx lives in `setup-trust.js`, outside `/api`. `request()` then wraps `_send` in a retry that applies **to reads only** — no `options.method`, or `GET` — 3 extra attempts 1.5 s apart. **A write is never re-sent**: it may have landed just before the server went away, and sending it twice would create two of whatever was being saved. This is why every non-GET goes through `_post`/`_put`/`_patch`/`_del` (which always set `method`) rather than calling `request()` bare — a body-carrying call with no method would be classified as a read and retried. Note `POST /jobcards/attachment-warnings` is read-shaped but sent as a write, so it deliberately gets no retry.

- **The login screen waits for the server before offering the form.** `api.isServerReady()` calls `/health` (outside `/api`, no sign-in needed, proxied in dev by `vite.config.js`, and it never throws — it returns false). `Login.jsx` holds it in `serverReady`: `null` = not asked yet (form works as normal), `true` = answering, `false` = not answering. Only `false` holds anything back — an amber `.login-notice` appears and the button reads "Waiting for the server...". While `false` it re-asks every 2 s until it answers. A sign-in that fails with `SERVER_UNREACHABLE` is **not** shown as a sign-in error (nothing the person typed was wrong): it flips `serverReady` to `false` and bumps `readyCheckKey` to restart the watcher. In the packaged app this rarely fires — Electron already polls `/health` before showing the window — so it mostly covers dev, where the window opens as soon as Vite is ready.

- **A screen that reloads when a choice changes shows only the newest request's answer.** A slower older reply can land last, so the Activity Log's "Last 25" showed 200 rows. `hooks/useLatestRequest.js` gives `startRequest()` → `isLatest()`: call it before the fetch, check it before touching the screen (rows, spinner, error pop-up). The list pages (`useManagedListPage`'s `runLoad`), the job list, statistics, search, tags/equipment and `useSearch` each carry the same idea with their own counter; a new reload-on-change screen takes the hook instead of writing another. Reads only — it decides whose answer is shown, it never re-sends anything.

## The activity trail's one shared list of actions

- **One list names every history action.** `client/src/utils/activityColors.js` holds `ACTION_COLORS` — every action name passed to `recordHistory` and nothing else — plus `ACTION_NAMES` (its keys, in display order) and `actionColor(action)`. The global Activity Log, the per-job History window and the search page's **activity** filter chips all read it; the three used to carry their own copies, which drifted (a new action was tinted on one screen and left muted grey on the others, and four actions the server records were missing from the search filter entirely while two of its options matched nothing). Adding a `recordHistory` action means adding it here. The same goes for the search page's other two hand-kept copies: a new recorded change key goes in `ACTIVITY_FIELDS` (`components/searchFields.js`) and a new entity type in `ENTITY_TYPES` (`SearchPage.jsx`). Trail values are shown through one formatter, `formatHistoryValue` (`utils/formatters.js`) — the Activity screens, the per-job History window, the search page and the Activity Excel export all use it — which reads a stored UTC moment on the local clock and a bare calendar day as an Australian date. Colour convention: `--accent-ready` for something added, `--accent-caution` for something taken away, `--primary-accent` for something changed. Note the server does **not** validate the search `action` param against a list — it binds the values straight into an `IN (...)`, so a name missing here is simply unfilterable, not an error.

## The job screen

- **The job History window writes one plain sentence per change.** The History window (`jobcard/JobHistoryPanel.jsx`, admin-only like the rest of the trail) is a side window built like the comments window: a round bubble hangs off the job window's left edge directly under the comments bubble, and pressing it slides the window out beside the job (a Refresh button sits beside its close button). Only one side window is open at a time — each hides the other's bubble. Which one is open is **one value owned by the job window** (`sideWindow`: nothing, comments or history); both panels are controlled by it (`open` + `onOpenChange`, with `otherOpen` derived from the same value), so there is never a redraw where the job window and a panel disagree. The comments' automatic opening (unread comments, or a comment the job was opened at) is still decided once per opening by the comments panel, which asks the job window to open it; a "yes" made while History is open waits and is honoured the moment History closes, unless the person has pressed the comments bubble themselves meanwhile. History opens itself for **every** job opened from an activity search result, whichever tab that result lands on (pricing results land on Costing, everything else on Details) — the search page passes `initialHistoryOpen`, separate from the tab. The history is read when the window opens and read again, while it stays open, after anything that writes a trail entry lands on the job: a field, part, worker or price save, a clock or logged-work change, a comment posted or deleted, a status change, a file added, moved or deleted, or a job card / attachments print or packet save. It does this from **one signal**: `api.js` announces `onJobChanged(jobId, fn)` after every write the server accepted whose path is `/jobcards/:id` or anything under it (failed writes and reads never announce), and the job window subscribes for its own job while History is open. Changes that did not come through this PC's own writes — an external clock stop the job window notices, and a finish-time question that went away because another screen changed or removed that clock — announce through the same signal with `api.noteJobChanged(jobId)`. An accepted answer to the question needs nothing extra (its own save already announced), and every full reload of the job in this window after its first load (a job found closed from another PC, a finish question, an external stop, invoicing) announces through the same signal from the one place the job loader finishes. So History reads on exactly three occasions: when it opens (after the job's first load), on that signal, and after each later full reload. A trigger is never removed to avoid a second read; reads coalesce (a read asked for while one is in flight runs once more when it settles, never two at once — `utils/coalesceRuns.js`). A plain status or comments reload on its own does not announce. No feature tells the window by hand — there are no change counters or `onTrailWritten`-style callbacks, so a new feature that writes under the job's path shows up in History without any wiring (a trail-writing route outside `/jobcards/:id` would need adding to that announcement). Newest load wins, and the window waits for the job's first load, so a window opened with History already open reads once, not once per piece of data arriving. When closing History hands over to a comments window that was waiting, focus goes into the comments window (as a normal opening does) rather than onto a bubble that is about to go inert — that hand-over lives in the comments panel only. "Nothing has happened on this job yet" shows only after a load has finished for this job (`historyLoaded`); before that the window shows its loading look. Only the first load replaces the list with "Loading…"; a reload (automatic or Refresh) swaps the list in place, so opened "Show N more" sections and the scroll position stay put. It no longer prints raw action names and from/to rows. `utils/historySentences.js` is the one place that builds the wording: `describeEntry(entry)` returns `{ kind, ring, headline, details }`, where each line is `{ parts: [{ text, strong? }], was? }` (the window prints `was …` after it in small grey). The names, part and new value are bold; the person who did it is named in the sentence, never in a column. Nine kinds (`KINDS`) colour the dot on the timeline — job details, status, people, work & time, quality & scrap, pricing, files, comments, and "needs a look" (a hollow red ring: deletions, clocks that stopped themselves or were thrown away) — through the `--history-dot-*` fill tokens in `index.css` (both themes); the header's filter chips are real toggle buttons that hide and show a kind. Days are headed Today / Yesterday / the date on the local calendar. A line's extra detail sits behind "Show N more" (an entry with exactly one detail shows it straight away). Worker, part and quantity for the work sentences come from the entry's `snapshot` (`workerId`, `workerName`, `partDescription`, `partQty`). "Their own clock" is decided only by account — the snapshot's `workerId` against the entry's acting user — never by comparing names, so two staff with the same name are never mixed up. An entry that never recorded its worker or part is worded neutrally ("the work", "stopped a clock on …", "the part"), never credited to whoever pressed the button — see the "Intended, not findings" entry in `time-and-costing.md`. **A part is worded from plain fields, never from the one-line summary:** part add/remove/edit entries keep the summary in `changes` (the global Activity Log shows it) and carry the part itself in the snapshot — `part` (the part after the change; the removed part for a removal), `partBefore` (an edit) or `parts` keyed by change name (a job's creation) — each `{ qty, description, jobType, material, treatments: [{ name, supplier }], drawingsType, customerProperty }`. A startup conversion gave older entries `{ qty, description }` with the rest of the summary verbatim as the description (old summaries can't be split reliably). Before that, the old whole-job Save wrote part changes under `item …` keys (`item #3 added` at creation, `item <description> added` / `item <description>` / `item <description> removed`); the startup conversion renames them to the `part …` keys, then splits an old entry holding several part changes into one entry per part (the original keeps the first and every non-part change; the rest copy its job, person and moment), and only then does the fold run. "removed the part X" / "changed the part X" name X from the entry's own snapshot (`part` / `partBefore` description); with no stored description the sentence says "a part", so an old position-numbered key never reads as today's part 3. All the trail conversions (rename, split, fold, the part name a time-block entry already recorded in its own `item` change, an auto-stop's worker from the entry's own account, and the one person an old worker entry added or removed when its stored lists give a single exact answer — they only reshape what was recorded, nothing is traced or guessed) are one pure rule, `convertTrailEntry` in `server/src/db/trailEntries.js` (no database in it, tested under `server/test/` and, through the wording, `client/test/trailConversion.test.js`), applied once to every job trail row behind the `history_trails_converted_at` settings flag; a restored older backup lacks the flag and is converted again. Every History and search read parses a row through the same file's `readTrailEntry`, so a damaged entry is skipped and counted in the log in both places, never shown and never a failure. An old file-upload entry that never recorded its part's name reads "to a part" (as does one whose part has since been deleted), and only one with no part id reads "to the job". A moved file's destination is read from the raw `part` change, and "the whole job" appears only when the snapshot has no `itemId`. Keys only older trails carry have their own sentences too (`jobCardPreviewed` "opened the job card preview", `packetBuilt` "built a print packet", the old Save button's `assignees` with a "Now on the job" detail, `photos`, `qaLevelId`, `companyId`/`contactId`), because they are stored data the window has to read. An older part or time entry that carries a status move (from before status became hand-set only) words the move as a plain follow-up under its line. A new recorded action or change key means adding its sentence in `historySentences.js` — an unknown key still shows as a plain "Field: value" line, and an unknown action as "made a change".
- **JobCardModal**: Modular tab-based UI with custom hooks for each tab's logic (`useJobCardCosting.js` → wraps `useCosting.js`, `useTimeEntries.js`, `useTimer.js`, `useJobNotes.js`, `useCamera.js`, `useJobCardForm.js`, `useJobCardInstantSaves.js`, `useJobCardSave.js`, `useJobCardCloseGuard.js` → `useUnsavedGuard.js` + `closeReasons.js` (on an existing job, closing by Escape or the X first *leaves* the focused box so its blur save fires, waits a frame and for `saveQueue.whenSettled()` — for at most 3 seconds, since a save stuck on a dead network never settles and an unbounded wait left the window impossible to close; past that the question names whatever hasn't finished saving — then asks the close question against the fresh state through a ref — closing is a way of leaving a box, so it keeps the value rather than offering to discard it; only a failed save or a blank required box is still asked about, 2026-09-27), `useContactSearch.js`, `useJobFiles.js`, `useActivityLog.js`). `useJobCardSave.js` is create-only (see the instant-save note below) — validation, resolving/creating the customer, one `POST /jobcards`. Everything about work that would be lost if the screen went away — the close question, the refresh guard, the inactivity registration and the spoken status — lives in `useUnsavedGuard.js`, wired up against `closeReasons.js`'s "which box, what failed" by `useJobCardCloseGuard.js`; both are pulled out of the modal for the same length reason `useJobCardSave.js` is.

- **A screen that closes must not clear which record it was showing in the same render.** The job screen saves pending pricing edits on the way out, and that save needs the job id; a caller wiring `isOpen={!!id}` and `onClose={() => setId(null)}` off one state variable silently drops the save (`runSave` returns early on a null id). Track open/closed separately from the id — `JobCardList` (`isModalOpen` + `editingCardId`) and `SearchPage` (`modalOpen` + `modalJobId`) both do.

- **A refresh mid-edit must merge, never replace, unsaved form state.** Starting a part timer may auto-assign the timer's worker; `handleStartItemTimer` in `useJobCardTimerActions.js` reloads the time entries and credits only that one worker (`creditAssignee`), because replacing the whole assignee list from the server silently undid any ticks/unticks made before pressing Start. It never touches the status — work never moves it (`jobs-and-status.md`). Stop-timer and the 5 s poll reload time entries only.


- **A part is matched to logged work by its own permanent id, never by its position.** A line item added on an existing job carries a client-side placeholder id until its description is committed (`createItemFromRow` in `useInstantItems.js`), at which point the create reply's real `item:` id and `item_number` replace it on that one row, and the placeholder is kept as the row's `rowKey`. An edit that arrives after that swap but still names the placeholder (a supplier or service created on the spot, a pick whose reply lands after the create) is resolved by that `rowKey` to the real part — in `updateLineItem` and in `useInstantItems.js` alike — rather than silently going nowhere. A part write's reply is merged **field by field**: a field untouched since the write left (still what it sent, or for an unsent field still what was stored) takes the server's stored copy — so a value the server rewrites on save, such as a supplier's current name, lands and matches the baseline — while a field changed since keeps what is on screen. On a create this keeps anything typed while it travelled; afterwards only the fields *committed* meanwhile (a pick made, a box left) are sent, and a box still being typed in saves on its own leave. Removing a part (`DELETE /jobcards/:id/items/:itemId`) never renumbers the survivors — `item_number` is a sort order the server owns and gaps are expected once a part is deleted (see `docs/notes/jobs-and-status.md`) — so a part's on-screen position (`position`, stated by the server on every part it returns) can shift for every surviving part after just one deletion, and a timer picking a part by that position still needs the *permanent* id underneath to survive the shuffle — `workMatch.mjs` is what time entries and the "Progress" list actually match against, never the position, for exactly this reason (see `ItemsTab.jsx`'s `entriesForItem`).

- **One status-change flow, shared by the job screen and the list.** `components/jobcard/changeJobStatus.js` exports `changeJobStatus(opts)` — used by both `JobIdentityStrip.jsx`'s own status control and `JobCardList.jsx`'s `handleQuickStatusChange` (a row's status badge) — so the billing confirm-then-send order (a confirm on first reaching billing and on archiving), the soft-checkpoint 409s (files, sign-off, PO number — each confirmed once, resent with every answered flag), the closed-job hand-off, and the one success wording ("Status updated to `<label>`") live in exactly one place instead of two copies that used to drift (different success wording, one missing the closed-job handling). Each caller supplies its own hooks: `prepareBilling` (only the job screen has costing access, so only it refuses a red pricing box, flushes unsaved pricing first and fetches a fresh total — the list passes none, so billing there asks the plain question with no total); `beforeSend` (the job screen waits for every save still on its way — `useSaveQueue.whenSettled` — so a PO number typed a moment ago is stored before the move is judged); `onApplied` (what "the write landed" means for that screen — the job screen updates its own form field, the list patches the row in place, or reloads when the job was archived); `onJobClosed`/`onFailed` (both reload the list; the job screen's `onJobClosed` shows the shared closed-job sentence and reloads the job). A second call for a job whose change is still running is ignored inside the module itself, on top of whatever busy-state a caller keeps for its own UI (the job screen still disables its status picker with `statusBusy` while a change is in flight). **The job list's own status badge reloads the whole list on any failed status change or a job closed elsewhere, rather than tracking one closed row** — a list row carries no per-field save state the way the job screen does, so there's nothing to reconcile in place; the simplest fix for a row gone stale (most commonly: another PC already invoiced/archived this job, so the write comes back refused by `closedJobGuard`'s 409) is to re-fetch and let the row disappear or update along with everything else. **The two also share one drop-down.** The job screen's status pill is a real button that opens the same `.status-popover` the list's status column opens (the rules live in `App.css`, not in either screen's own stylesheet): one row per status the person may set from here (`offeredStatusValues`), grouped under non-focusable headings by `statusMenuModel` and drawn by one shared `common/StatusPopover.jsx` (keyboard on the current status when it opens, Up/Down/Home/End over the status rows only, opens upward when there's no room below) (with a "Put back to …" row on top for a job on Action Required), each row carrying that status's badge, a tick on the current one, closed by a press outside, Escape (focus back on the pill) or focus leaving it through the shared `hooks/useDismissableMenu.js`. A status the person can't change (a worker on an office status, a paid and archived job) is a plain pill with a title saying why, not a disabled picker.
- **The job window frames itself when something on it hasn't reached the job.** Everything else on that screen reports itself — the timer counts, the costing sheet says "Saved", the file dots fill in — and the details, parts and assignees now do too (see the instant-save note below). `useJobCardForm.js` keeps a baseline of what the job last confirmed storing and exposes `isDirty`; `JobCardModal.jsx` folds it together with unsaved pricing as `waitingOnSave` and passes that to `BottomSheet` as `unsaved`, which adds the `modal-unsaved` class (an amber ring drawn outside the border in `App.css`, so nothing shifts) around the whole job window. **The same frame answers in green once the last of it lands** — `modal-saved`, the identical three layers in `--success-*`, held for 1.8s by `useSavedFlash.js` and then let go so the window's own border/shadow transition fades it back. **Green is fired by a write the server confirmed, never by unsaved work going away** — `useSaveQueue.js` counts confirmed landings (`landedCount`) alongside its outstanding-key map, `useCosting.js` keeps the same tally for the pricing sheet (`costingLandedCount`, since pricing saves on its own path rather than through the queue), and `JobCardModal.jsx` hands `useSavedFlash.js` the two added together. The two are not the same fact: the screen also stops having anything outstanding when an edit is *abandoned* — a half-typed part deleted before it was ever sent (`useInstantItems.js`'s `removeItem` on a not-yet-real row), or a box typed back to exactly what was already stored (`useInstantSave.js` returns before enqueueing) — and answering those with green told people their work had saved at the moment it was thrown away. A landing while other work is still outstanding *arms* the flash and waits, so the green always means all of it. **A refused create or remove is not a landing either**, even though it did reach the server and `run()` resolves rather than rejects — a part whose create or delete came back refused (400/409, logged work against it, the job's last line, …) already reports itself with its own toast (`useInstantItems.js`'s `createItemFromRow`/`removeItem` catches) and must stay off the count, or the green frame would flash for a part that was never actually created or removed. Rejecting instead isn't right either — that's `'failed'`, which flags the key and waits for the user to retry, and neither of these wants that (there's nothing stored to retry against on a refused create; a refused remove just leaves the row exactly as it was). `useSaveQueue.js` exports a sentinel, `NOT_LANDED`, for exactly this: a catch that already told the user returns it instead of the normal result, and the queue's landing handler clears the key (so it stops reading as outstanding) without bumping `landedCount`. The half it waits on is `waitingOnSave` — `isEdit && (isDirty || costingOutstanding)` — and **the amber ring is asked that exact same question**, so a price behaves like every other box: amber while it travels, green when it lands. The two halves must cover the same work or the frame contradicts itself; pricing was once in green's question and not in amber's, and a visit that only touched money got a green it had never announced — and, before `costingLandedCount` existed, no green at all. An unposted comment and an open stop-timer form are in **neither**: they are drafts the person is holding, not saves in flight, and letting either veto the flash would mean a job with a stray half-typed comment never confirmed a save again. `useSavedFlash.js` returns `flashing && !waiting` rather than leaving the answer to CSS ordering — its effect only runs after paint, so a fresh edit would otherwise get one frame of green before amber took over. Nothing gates on "has this card been edited yet" any more: a landing cannot happen on a card nobody has touched, and both counts belong to one window and start at zero in each (`JobCardModal.jsx` mounts a fresh `JobCardWindow` per opening), so the total is always this opening's. **Each opening is a fresh window.** `JobCardModal` is a thin shell: closed it renders nothing, open it renders `<JobCardWindow key={jobCardId ?? 'new'}>`, so closing unmounts everything and reopening — even the same job — mounts new state, a new save queue, new "decide once" flags and a new set of in-flight replies. The window used to stay mounted behind the list and hand-wipe each piece of per-opening state (`resetForm`, `reset*` on a dozen hooks, "opening" counters, a `useLayoutEffect` reset); the wiping ran after the first commit, so the reopened window briefly showed the previous opening's data and every new piece of state was one more thing to forget. Nothing changes the job id while the window is open (Create closes the window and the list holds the id), so the key only ever separates openings. What used to run "when `isOpen` became true" runs on mount (the job load, the supplier/worker/machine lists, the handed-in stop form — showing the same form twice is a no-op, so strict mode's second mount cannot stack a copy); what ran "when it became false" runs as an unmount cleanup (the confirm queue answers outstanding questions "no", and the pricing sheet's last flush — the one write-on-close that matters, `useCostingSave.js`'s `flushOnUnmount`; `useJobCardCosting.js` only commits the box being typed in on the way out, because a send scheduled from there would land one render too late on an unmounted window). **A late reply after the window is gone follows one rule, made of two questions.** *May this reply change the window's own screen?* (marks, row updates, reloads, closing the window) — only while `isWindowUp()` (`hooks/useStillMounted.js`, one ref set false in an unmount cleanup, created once in `JobCardWindow` and handed down); a reply that only sets the window's own state needs no guard at all, since React drops state set on an unmounted component. *Must the person hear that their own write failed or was refused?* — **always, whether or not the window is still up**: they typed it, closed the window while it travelled, and it never arrived, so staying silent would lose their work without a word. That covers the queue's generic failure toast, a refused part create, remove or edit, a failed comment post or delete, and the closed-job sentence (`handleJobClosedWrite` always toasts and reloads only if the window is up). Because such a message can appear while a different job is on screen, **every one of them names its job** ("Job 1234: …") and carries a per-job toast id, through the one helper `jobWriteFailure.js`'s `toastJobWriteFailure` (the save queue hands it to its callers as `saveQueue.reportFailure`) — never a hand-written prefix, so a new failure message cannot forget it. The pricing sheet's own failure messages name their job the same way in `useCostingSave.js`. Asking the window: the job load's failure (else it would toast, or `onClose()` the *next* job opened), the comment-thread load failure, the supplier/worker/machine load failure, the job-folder file listing's failure (`useJobFiles.js` asks its own `useStillMounted`), a create's success reply (else it would close the next job), and the timer-action replies that reload the screen. Failures of *reads*, and messages that instruct the person about the window itself, stay gated — nobody needs them after close. Naming: the callbacks into the list behind — `onNotesChange(jobId, latestNote)` and `onCommentsRead(jobId, unreadNotes)` — carry their job and still fire after the window closed, because the server has already stored the change and the list row should catch up; `onTimerChange` and `onSuccess` name no job but patch nothing in particular (they reload). **A landing's screen work runs only while its window is up**: `useSaveQueue.js` is handed `isWindowUp` and hands `run` the same function (named `isWindowUp` there too), and every caller — a field's "Saved" mark, a part's reply, a create's reconcile, a remove, a worker tick — returns early on `!isWindowUp()` for its *success* work; a failure is still told (second question above). The queue itself bumps `landedCount` and clears the key on every landing without asking — those are the window's own state, which React simply drops once the window is gone, so nothing reads a landing that arrives after close. A job-id-only check let a field edited just before closing show "Saved" on the reopened screen, and let a part created just before closing be deleted as "no longer on screen" by the fresh opening; a fresh window per opening makes that impossible. **The one thing that deliberately outlives a window is the per-field write order**: the chain of promises that makes a save wait for an earlier save of the same box lives at module level (keyed job + box, each tail tagged with the window that asked for it), because a write still travelling from the window just closed must stay ahead of the next write of that box in the reopened one, or the older save could land last and overwrite the newer; a tail from an earlier window is waited for at most 20s. The pricing half has its own: `editSeq`, which `runSave` uses to drop a reply whose snapshot no longer matches. Because the window starts from its first frame as a spinner (`loading` is true from the first render of an existing job) and carries no stale state, nothing needs to run before paint any more. The green is a flash rather than a state on purpose: a frame that stayed green would stop reading as *that just saved*. It is deliberately not a CSS keyframe — `.modal-popup` already carries `animation: modalSlide` for its opening, and a class that comes and goes would replay that slide every time it cleared. The pair is now the **only** general answer to "did that save?" on an existing job: the identity strip's old `Saving… / Saved` line is gone (see the instant-save note below). A brand-new card is measured against a pristine, empty-form baseline (not `null`) from the moment it opens, so a half-filled new card is known to be unsaved even though nothing has reached the server yet. That dirtiness deliberately does **not** reach the amber frame on a brand-new card — the ring is gated to an existing job only (`isEdit &&`), so flagging every new card for the whole of an ordinary fill-in-and-create task wouldn't mean anything. The close question is not gated the same way: `useUnsavedGuard.js`'s `hasUnsavedWork` starts from `isDirty` with no `isEdit` in front of it, so closing a half-filled new card still asks first. Three things the baseline deliberately does *not* count, because none of them is a write waiting to happen: **status** (it's already instant, and the server also nudges it on its own — stripped from the form snapshot); **the people list, in full** — `toggleAssignee` writes the one worker it's about the moment the tile is tapped (`PUT`/`DELETE /jobcards/:id/assignees/:userId`, idempotent), moving the baseline with the list on success and leaving both alone on failure, so a failed tick stays flagged until retried; `creditAssignee`/`dropAssignee` do the same, unconditionally, for what the server did on its own (a started timer credits its worker, a discarded tap takes them back off); and **a part not yet real** — a placeholder id would otherwise read as an edit the moment the create reply swaps it for the stored one. On a brand-new job the customer, picked through `useContactSearch`, is a separate hook whose state `useJobCardForm` never sees, so `JobCardModal.jsx` folds in its own check of `contactHook.contactFormData` (non-empty on a new job only) rather than reaching into `useJobCardForm` for it.

- **Closing a job card with something unsaved now asks first, and says the right thing about it.** `JobCardModal.jsx`'s `handleRequestClose` is wired as `BottomSheet`'s `onClose`, covering Escape and the header X in one place. A save already in flight (the create path only — see the instant-save note) does **not** block the close or get cancelled by it: the confirm, if there's something to lose, runs the same as any other close, and the request keeps going in the background, landing its own toast/`onSuccess` when it resolves. **On an existing job the question is no longer one sentence for every situation** — see the instant-save note's closing bullet for the split, and `closeReasons.js` for how it's built. A brand-new job asks one plain question — "Discard this new job card?" / "Nothing has been created yet…" with **Discard job card** / **Keep editing** (and, while Create is still on its way, "still being created") — since none of the per-field/per-row machinery below applies until a job exists to write to. **Questions queue rather than overwrite each other.** `useConfirmDialog` used to hold a single `resolveRef`, so a second question asked while one was up replaced it and the first promise never settled. Escape can't cause that — `ConfirmDialog` and `BottomSheet` both gate on `isTopModal`, so while a question is up Escape only answers *it* and never reaches the screen underneath. What could was a question raised by a **timer**: the pricing sheet's old "change an invoiced job?" came off the 1 s autosave countdown, so on an invoiced job with both a job edit and a pricing edit waiting, Escape put up "close and lose them?" and the invoiced question reworded it mid-read a second later; the close `await` never resolved and the card silently refused to shut. That question has since been removed outright (see `time-and-costing.md`), so nothing in the app currently asks without a click — the queue stays as the structural guarantee, and still covers the two things that bite regardless: a double-click answering one question and stranding the next, and a question left outstanding when the screen goes away. Questions sit in a FIFO queue — one on screen, the rest waiting — with a 250 ms gap between them so the click answering one cannot land on the next and the box visibly goes and comes back. `useConfirmDialog` answers anything outstanding `false` when the screen that owns it unmounts (`cancelConfirms` runs as the hook's unmount cleanup, so the job window closing triggers it): past that point nothing renders the box, so a question left on the queue would never settle and would park every later question behind it for the rest of the session. Pinned by `client/scripts/check-confirmQueue.mjs`. The question is asked about `hasUnsavedWork`, deliberately wider than `isDirty`: it also counts **a comment typed into the comments window but never posted** (`jobNotes.newNote`) and **the details form of a run that was just stopped** (`timer.showEntryForm` — the run itself is recorded, but the machine, quantities and checks about to be recorded against it are not) and **a part's half-filled New supplier form** (`supplierDraftOpen` — the form keeps its typing only inside itself, so each open one reports up through `onSupplierDraftChange` to `JobCardModal.jsx`; leaving the Details tab while one holds typing asks first too, since the form goes with the tab). Those are kept out of `isDirty` on purpose, because `isDirty` drives the amber ring and both of those mean *a write waiting to happen*, and the stop form is already a panel in its own right, so framing the whole window amber for it would dilute the signal. Two doors that used to bypass the question entirely are now covered as well. **A browser refresh or tab close** (`beforeunload`, registered while `hasWorkToLose`) stops and asks — the browser only ever shows its own fixed wording there, so it cannot carry the message above, but Ctrl+R no longer empties a half-filled card in silence. `hasWorkToLose` is `hasUnsavedWork` **plus** `costingDirty` **plus** `costingUnsettled`, and that addition is the point: closing the job saves pricing first and waits for it (`useJobCardCloseGuard.js` — a failed pricing save is then named in the close question), but a refresh and the inactivity sign-out never run that save, so a committed figure typed and not yet saved — the cursor still in its box, or any time after a failed save, when autosave is paused — went without a word. `costingUnsettled` (`useCosting.js`'s `costingHasDraft`) is the same idea for a box that hasn't even reached a committed figure yet: a draft still being typed, or one sitting red and refused — see `time-and-costing.md`'s draft-then-commit pattern — since neither of those is `costingDirty` either. Both stay out of `hasUnsavedWork` itself, so the amber ring and the close confirm are unchanged. **The packaged app needs its own handler for this**: Electron never shows Chromium's "Leave site?" dialog — it fires `will-prevent-unload` on the webContents, and with nothing listening its default is to cancel the close silently, so the desktop app simply refused to close and looked frozen. `client/electron/main.js` registers that handler and shows a real `showMessageBoxSync` ("Leave Without Saving" / "Keep Editing", the safe choice as both `defaultId` and `cancelId`); `event.preventDefault()` there means *proceed* with the close, so it is called only on the leave branch. **The inactivity sign-out** is told what is at stake: `useUnsavedGuard.js` calls `registerUnsavedWork('job card')` from `AuthContext` while there is something to lose, and `InactivityWarningModal` reads that label once when it appears and adds "You have an unsaved job card. It will be lost unless you continue." to a countdown that previously ran in silence while a manager was away from their desk (admins are exempt from the inactivity timer; managers and employees are not). It is the read-only companion to `registerBeforeLogout`, which `useTimer.js` already uses to put a half-stopped run back on the clock before the pass is torn up — only the signed-in person's own run; another worker's block a manager stopped into the same form stays stopped. Finally, the unsaved state is now **said as well as shown**: on an existing job (management only) a visually hidden `role="status"` line reads "This job card has unsaved changes." / "All changes saved." — the same approach `CostingTab.jsx`'s own status line already takes. It is the spoken twin of the window frame and is held to the same standard: the first half is the frame's own `waiting` (pricing included), and the second only speaks once `saveQueue.landedCount > 0`, so a card nobody has changed announces nothing on arrival and an abandoned edit is never announced as a save. There is no footer at all to sit beside any more on an existing job — see the instant-save note.
- **An inner box that handles Escape itself marks it handled, and the window stays open.** `BottomSheet` closes on Escape only when nothing inside already dealt with the key (`e.defaultPrevented`). A small box or list inside a window that closes on Escape calls `e.preventDefault()` (the Suppliers page's "+ Other" service box; `CheckboxDropdown`, which listens on the capture pass so the mark is there before the window looks) — otherwise one Escape closed the box *and* the whole supplier form, throwing away everything typed. Layers that register with the modal stack (`pushModal`/`isTopModal`) or stop the key outright keep working as before.

- **A closed (invoiced/archived) job is locked by wrapping, not by threading a prop
  through every field.** See `jobs-and-status.md`'s "Invoicing and archiving" for the
  policy and the one client rule (`jobLock.js`'s `isJobClosed`); the pattern worth
  keeping here is `.jc-lock-fieldset` — a plain `<fieldset disabled={jobClosed}>`
  around a whole tab's JSX. A disabled `fieldset` refuses interaction with every
  input/select/textarea/button nested inside it, however deeply, which is what makes
  it possible to lock the Details tab's editable fields/parts/workers and the Costing
  tab's sheet body in one wrap each, rather than adding a `readOnly`/`disabled` prop to every box the two
  tabs already own. `display: contents` on the class keeps it from becoming a layout
  box of its own, so it can't disturb the grid/flex it's dropped into. Reach for this
  before threading a lock flag through a subtree that already has more than a couple
  of interactive children — but wrap only the editable part: it disables view-only
  buttons too (an info toggle, a Try again), so those belong outside the wrap.

- **A field-error mark belongs to the text it was raised against, not to the field's
  name (`hooks/useFieldErrors.js`).** Every caller passes `useFieldErrors(valueOf)`,
  where `valueOf(name)` reads what the named box holds right now — a per-part mark's
  name is `fieldErrorKey(itemId, field)` (`fieldRules.mjs`), so its `valueOf`
  splits the key back apart and looks the row up; the pricing sheet's `valueOf`
  reads a box's draft if one exists, else its committed figure. `setFieldErrors`
  records, per name, the message plus the value the box held (or was explicitly
  raised against, via the optional second argument — `commitBox` in `useCostingDrafts.js`
  raises a pricing mark against the raw draft text, since the row/committed state it
  would otherwise read hasn't caught up with that same keystroke yet). A mark is
  live — shown, counted, announced — only while `valueOf(name)` still equals the
  value it was raised against; once the box's content changes, however it changed
  (typed over, a pick filling it in, a server reply reconciling it, a row being
  removed), the mark simply isn't surfaced any more. There is no hand-written
  per-box clearing call any more (`clearFieldError` was deleted from the hook and
  every caller) — a value changing is what clears its own mark. `clearAll()` still
  exists, called by hand only for a new form session (opened, switched to another
  record, reset to blank) or right after a successful submit.

- **A picked customer's phone/email are not re-validated on typing any more — a
  failed Create marks the box instead.** Last round's client-side format check
  (regexes mirroring the server's, run in `JobCardModal.jsx`'s submit handler) is
  gone; see `time-and-costing.md`'s sibling note in this file's history if chasing
  why. Now: `handleValidationErrors` (server, S4) puts `fields: [{ field, message }]`
  on every 400, and `useJobCardSave.js`'s catch maps `contactName`/`contactPhone`/
  `contactEmail` (the job route) or `contactName`/`phone`/`email` (the contact routes
  `jobCardContact.jsx` calls first, for "Update contact" / "Add as new contact") onto
  the same three boxes via `JobCardModal.jsx`'s own `useFieldErrors` instance (and
  the new-customer step's `name` onto the Company box) —
  `CONTACT_FIELD_TO_BOX` in `useJobCardSave.js` is the one place that knows both
  spellings, handed to the shared `fieldErrorsFromRefusal` in `hooks/useFieldErrors.js`
  — the same step the Users, Suppliers, Customers (company and person) and Tags &
  Equipment forms use through its `showSaveRefusal` wrapper, each with its own
  field→box map and `noValidate` on the form so the app's own marks report an empty
  required box instead of the browser's bubble. Any other failure (a network error, a non-validation 500) still falls
  through to a toast. `buildJobcardPayload` (`mappers.js`) only sends a picked
  person's phone/email/name when it was actually edited for this job
  (`detailChanges` off `useContactSearch.js`) — the server copies the rest from the
  saved contact (S3) — so this mapping is really only ever reached by what was typed
  fresh, either on a brand-new contact or on the one field someone changed. A mark
  raised this way clears itself the moment the box's content stops matching the text
  that was refused — `JobCardModal.jsx`'s `useFieldErrors` instance is given a
  `valueOf` that reads `contactHook.contactFormData`, so picking a saved person
  (which fills the phone/email in from that record) drops a stale mark without
  `JobCardModal.jsx` having to clear it by hand; see the general rule below.

## Every change saves itself — the job screen has no Save button for an existing job

`tasks/instant-save-job-card.md` is the frozen spec; this is the short version of why.

A Save button is a **gap** between deciding something and sending it, and the old job save was
**wide** — it handed over the whole job, so the gap flattened whatever else had changed since the
payload was built (a timer crediting its worker, another person editing the same job). The people
list is where it bit first, because the timers write to that same list. The rule replacing it is
**narrow and immediate**: send only the thing that changed, at the moment it changes. An autosave
that still posted a whole-job payload on a timer would reproduce the same bug with a shorter fuse.

- **Single-value fields** (priority, due date, description, the customer's PO/quote/previous-job
  number, quality level, previous job) write one field through `PUT /jobcards/:id`, which already
  treats an absent field as *leave it alone* (the `jobcardQueries.update.run` call in `jobcard-mutations.js`). Dropdowns, dates and
  toggles write on change; text boxes write on **blur only**, after `capitalizeFirst`/`toTitleCase`
  has run, so the tidy-up and the write are one action and the tidied value is what is sent.
  `useInstantSave.js` chains per field — a fast second edit to the same field queues behind the
  first and settles on its value, and different fields never block each other — and
  `markFieldSaved` moves that one key of the form baseline on success. **An unchanged field on blur
  writes nothing**, so tabbing through a form produces no writes and no trail entries.
- **Status** was already instant and is untouched. **Pricing** has always saved itself — see the
  draft-then-commit pattern below, which is now what "leaving a box" means on that sheet too.
- **A box that saves on leave holds its typed text as a draft; leaving is the one moment it is
  judged and committed; a server reply never touches a draft.** The costing sheet (`useCosting.js`, composed from `useCostingDrafts.js` and `useCostingSave.js`)
  is the pattern's fullest example, because it's the one screen where "leave it blank" and "type a
  bad value" both have to mean something specific rather than just falling back to whatever was
  there. A **committed** value (a plain number, a flag) is the only thing ever sent; a parallel
  **drafts** map holds exactly the text in any box currently being typed in, keyed by field name,
  and what the sheet renders is the draft if one exists, else the committed value — so a half-typed
  "1-" or a box cleared mid-edit is never coerced into a number just because a keystroke landed.
  `commitBox` is the single place a draft becomes a figure: called on blur (Tab, click-away,
  Escape-then-close, switching away) and on Enter — the same function either way, so there is
  exactly one moment a box is judged, not one per firing mechanism. A blank box and a bad one are
  different outcomes: blank commits to a sensible default (0, or "follow the calculated/logged
  figure" for a box with an auto fallback) and saves; text that isn't a valid number, or a number
  under the field's floor, **keeps the draft**, marks the field with `hooks/useFieldErrors.js` /
  `common/FieldError.jsx`, and sends nothing — the box still shows exactly what was typed, not a
  reformatted or reverted figure, because reformatting an invalid "abc" or "-1" the moment it loses
  focus would hide the very text the red mark exists to explain. Live totals read the committed
  figures overlaid with every current draft (parsed per the same blank/invalid rules, but never
  sent) so the running numbers update on every keystroke without a request going out — the payload
  a save actually sends is built from the committed form alone. A reply from the server is only
  ever merged into the committed form, and only for fields with no draft sitting on top of it right
  now — a reply landing mid-keystroke must never overwrite what's still being typed underneath it.
- **A pick from an autocomplete does its own write.** `onMouseDown` fires before the input blurs and
  the blur still reads the DOM's *old* text, so the Previous Job Reference suggestion writes the job
  number itself and arms the pick guard in `useComboboxNav.js`, which makes the blur behind it stand aside. Without that
  the half-typed reference is written over the job number just chosen.
- **A reply that lands after the window closed is dropped** — every save reply checks `isWindowUp()`
  before touching any state. The window is mounted fresh per job and shows one job for its whole
  life (no id yet, then the job's id once created), so there is no "different job" a late reply
  could land on and no job-id comparison is needed.
- **A failed write keeps what the user typed**, flags the field, and is **never re-sent
  automatically**; the retry is the user editing again. Messages take a stable id per field so a
  repeat replaces rather than stacks.
- **The save-status line is one per area**, not one per field — `role="status" aria-live="polite"`,
  the same shape `CostingTab.jsx` uses. Eight live regions would be unusable read aloud.
  Each opening mounts a fresh job window, so the line starts empty by construction and can never
  greet the next job with the previous one's "Saved".
- **In the identity strip that line no longer shows its words**, only its failures. The header bar
  already carries the job number, priority pill, description box, status pill and due date, and a
  sixth item in it — a small `Saving… / Saved` that spent almost all its life saying nothing new —
  stopped being read. The amber/green window frame above says the same thing at a size that cannot
  be missed, so `JobIdentityStrip.jsx` renders `instant-save-status` **only** for `failed`, and it
  names the field ("Due date not saved", "Priority not saved", "Job description not saved") with a
  **Retry** button that resends that one field's value (a person's own action, never automatic). The
  mark stays until a retry lands or the field is edited again. The frame staying amber says *not
  there yet*, which on its own doesn't say anything went wrong, and that is the one state worth
  words. The full wording is still announced from a `sr-only` live region beside it, because a
  colour says nothing to a screen reader.
- **A part whose write failed carries a persistent "Not saved · Retry" chip on its card**, as well as
  the toast. A saved part's failure is read from the save queue; a new part whose create failed is
  tracked by `useInstantItems.js` (`createFailedIds`). Retry (`retryItem`) re-creates a still-local
  part, or resends every box of a saved part that differs from what the job last confirmed storing.
- The strip is one line — job number, priority, description, status, due date and the window
  controls — so the Files and close buttons sit level with the rest of it. (A second line of
  customer, assignee avatars and a Critical pill was tried and reverted: it pushed the right-hand
  controls off the line.) The Order Details card (PO number, quality level, previous job) sits straight under the customer, above Parts.
- **Removing a part that has anything filled in asks first** (`requestRemoveItem` in
  `JobCardModal.jsx`): title names the part number and description; "Keep part" (focused) / "Remove
  part" (danger). A blank part goes without asking. A part with logged time is still refused by the
  server and that message still shows.
- **Parts: required stars, Duplicate, and Add time in place.** Qty, Description, Job Type, Drawings
  and Customer Property all carry the red star (the five boxes a part cannot be saved without). A
  part card's "Duplicate part" copies everything except quantity and puts the cursor in the new
  part's Qty box; the copy is an ordinary local part and is created through the same path as Add
  part once complete. "+ Add time" in a part's progress row opens the New Time Entry form inside
  that part's card (only one form open at a time); editing an existing entry still opens it at the
  top of the Parts section.
- **Start Timer is a split button for management**: the main part starts the timer for the
  signed-in user at once; the caret ("Start for someone else") opens the people list. Workers keep
  the plain button.
  `DetailsTab.jsx`'s copy of the line is unchanged — its grey section title bar has room for it.
- **The parts list saves row by row, in `useInstantItems.js`.** A row added by "Add part" stays
  purely local — every field on it just edits screen state — until its description is filled in and
  left (`commitItemFieldBlur`): that's the one moment it becomes real, sending the whole row as one
  create (`POST /jobcards/:id/items`) and swapping the placeholder id for the stored one. From there,
  every further edit on that row writes itself: dropdowns/tags/toggles on change, text/number on
  blur, each through `PATCH /jobcards/:id/items/:itemId` — absent-means-unchanged, so only the one
  field travels. Removing a row calls `DELETE /jobcards/:id/items/:itemId` for an already-real row
  (a still-local row is just dropped, nothing was ever sent); a refusal (time logged against it, or
  it's the job's last line) leaves the row on screen with the server's own wording shown, never a
  silent drop. **A required box on an already-real row that's emptied is marked and never sent** —
  same rule as the details fields, using `hooks/useFieldErrors.js` — so a cleared box can't destroy
  a stored value; a still-local row's boxes are never marked this way, since starting blank is normal
  for a fresh row. This also closed a latent bug: the per-part timer button used to render on
  never-saved rows, so starting a timer there sent a part number the server didn't know about — it's
  now gated on the row actually being real (`isPersisted` in `ItemsTab.jsx`).
- **An existing job has no Save button at all — `useJobCardSave.js` is create-only now.** Every
  field, row and worker already writes itself the moment it changes, so there's nothing left for a
  whole-payload submit to do; a stray Enter inside the form is stopped from reaching it by an
  unconditional `if (isEdit) return;` at the top of `handleSubmit`, not just a role check. Creating a
  new job: one `validateJobCardForm` pass, resolve/create the customer, one
  `POST /jobcards` carrying the whole form, items and assignees in one shot. The button reads
  **Create job card** ("Creating…" while it works) and Ctrl+Enter presses it (the box in use is left
  first, so its tidy-up lands; an Enter a suggestion list used for a pick stays a pick). On success
  the window **reopens as the new job** — the list's `onCreated` sets the job's id, the window re-keys
  on it — with "Job N created. You can now attach its files.", because files can't be attached
  before the job exists (the Parts heading says so on a new job). A window closed while Create was
  travelling just gets "Job N created." A failed create says what was entered is still on screen.
  That pass returns
  **marks, not a message list**: the customer box, the description box and each part's own boxes
  (keyed `fieldErrorKey(item.id, field)`, the same marks a saved part's instant save raises) are
  marked and the first is scrolled into view. A card with no part filled in marks its first part's
  description "Describe at least one part"; only what has no box — a supplier picked with no
  service — is still a pop-up. Each mark says what to do ("Choose a job type", "Enter a quantity"),
  worded once in `fieldRules.mjs`. Blurring an empty description marks it on a new
  job too, so the one mistake is only ever signalled one way.
- **The close question now says *why*, not just *that*.** With no Save button, "this job card has
  changes that haven't been saved yet" stopped being one true sentence for every situation — an
  emptied required box has nothing to lose (the stored value stands, nothing was ever sent), while a
  failed write genuinely does. `closeReasons.js` turns `isDirty`'s ingredients (the details fields'
  `fieldStates`, the parts list's required-box marks and each row's own saved-vs-screen comparison,
  the people list's baseline mismatch) into two lists — `safe` (an empty required box, nothing at
  risk) and `atRisk` (a failed write, a part row that was never sent at all, a team assignment that
  hasn't landed, an unposted comment, an open stop-timer form) — and `useUnsavedGuard.js` picks the
  framing: `atRisk` alone or alongside `safe` gets the original "close and lose them?" wording naming
  what's at risk, with any `safe` items folded in as a second, calmer line; `safe` alone gets a
  different question entirely — "Close anyway" / "Fix it", `confirmVariant: 'warning'` not `'danger'`
  — and **Fix it moves the cursor into the offending box** (`scrollFieldIntoView`, reused from
  `hooks/useFieldErrors.js` rather than rewritten) instead of just dismissing the dialog. A local part
  row with anything typed into it counts as `atRisk` even though `hasIncompleteItem`-style marking
  never touches it — an untouched blank row is normal and never counts. None of this replaces
  `isDirty` itself, which stays exactly the single screen-vs-stored comparison it already was; the
  close question just describes it more specifically. See `tasks/instant-save-job-card.md`, Stage 4b.

## Intended, not findings

Each of these was decided (2026-10-14); a review or bug hunt does not raise it.

- **Start Timer stays where it is on the part card (an outlined button under the part's details), and a running clock is shown inside that part's card only — no running-clock band at the top of the job window and no filled Start button at the top of each card.** Decided 2026-10-15 when the UI review proposed both; the owner chose to leave the part card as it is.
- **History may read twice in a row after a write that also reloads the job (e.g. invoicing).** The second read is queued behind the first, never concurrent, and is accepted. Do not raise "History loaded twice".
- **`api.js` has two announcers on purpose:** `onDataWritten` (every accepted write, with its path, for screens holding cached lists) and `onJobChanged` (one job's trail may have a new entry). They are not one filtered over the other, because `noteJobChanged` announces changes that were *not* writes from this PC (an external clock stop, a reload that found the job closed), and those must not look like a data write to the list screens. Do not raise "merge the two announcers".

- **History keeps sentences for event kinds that no longer happen.** `jobCardPreviewed`, `packetBuilt`, `photos` and `qaLevelId` are past events no route records any more; there is nothing current to convert them into, so their old entries keep their sentences rather than being rewritten.
- **The older reload-on-change screens keep their own request counters.** The job list, statistics, search (`useSearch`), tags/equipment and the list pages (`useManagedListPage`'s `runLoad`) each guard "newest answer wins" with a hand-written counter. They work and are deliberately not moved onto `hooks/useLatestRequest.js`; only new screens take the hook.
- **Searching logged time by part number matches that exact part only.** "3" finds part 3, never 13 or 30, so the total hours at the top are that part's; "03" or "part 3" find nothing by part number. Every other field in that box still matches partial text.
- **The job list keeps the running-timer pin and labels it.** The job with the signed-in person's running clock sits at the top whatever the sort, under a thin band reading "Your timer is running on this job". It is always shown while the pin is active, even when the sort would have put the job there anyway.
- **Unarchive is one click; delete is confirmed.** Restoring an archived job from the list needs no question (it is easily reversed by invoicing again); deleting still asks, because it cannot be taken back. There is no Undo on the restore, since no job-archive call exists apart from invoicing.

- **A control looks like what it is.** Every single-choice drop-down shows the same drawn chevron (one app-wide rule in `App.css`, `:root select:not([multiple]):not([size])`, both themes), and every type-to-search box with a suggestion list shows the same chevron (`.autocomplete-caret`, rotating while the list is open) plus a hint that says what to do ("Type or choose a customer…", "Type or choose a job…") — never a sample value, which reads as already filled in (the previous-job box's "DH-00001", the PIN box's "····" and the stop form's "0" were all removed for that). A suggestion row that shows more than one thing uses the two-line layout (`.suggestion-two-line`: the choice in bold, a grey note beside it, a smaller grey detail under them, each cut short with "…"), because the plain row spreads its pieces across the width until they wrap mid-word. A yes/no setting in a form is the app's switch row (`.toggle-label` with `.toggle-input`/`.toggle-switch`/`.toggle-content`), never a bare tick box inside `.form-group`, which stretches it to the full width. A drop-down hanging off a control is a `common/PlacedPopover.jsx`, which opens upward when there's no room below.
