# Client-side patterns and traps

> Detail split out of CLAUDE.md. Read before touching the job screen, the sign-in screen, error handling in the shared sender, or the activity trail colours.

## Talking to the server

- **"The server isn't answering" is one shared error, and only reads re-ask.** The server can be missing for a second or two — it is still finishing start-up, or (in dev, where `npm start` runs it as a separate process with `node --watch-path`) it restarted itself after a saved file. `_send` in `api.js` turns both shapes of that into a single `Error` carrying `code: 'SERVER_UNREACHABLE'` and one plain-English message: a `fetch` that rejects outright (nothing listening), **and** a `5xx` whose content-type isn't JSON — the Vite dev proxy answers `500 text/plain` with an empty body when its target is down, which is the same situation wearing a status code. That heuristic is safe because every real 5xx the app produces is `res.status(...).json(...)` (the catch-all handler in `server/index.js`, the restore-in-progress 503); the only non-JSON 5xx lives in `setup-trust.js`, outside `/api`. `request()` then wraps `_send` in a retry that applies **to reads only** — no `options.method`, or `GET` — 3 extra attempts 1.5 s apart. **A write is never re-sent**: it may have landed just before the server went away, and sending it twice would create two of whatever was being saved. This is why every non-GET goes through `_post`/`_put`/`_patch`/`_del` (which always set `method`) rather than calling `request()` bare — a body-carrying call with no method would be classified as a read and retried. Note `POST /jobcards/attachment-warnings` is read-shaped but sent as a write, so it deliberately gets no retry.

- **The login screen waits for the server before offering the form.** `api.isServerReady()` calls `/health` (outside `/api`, no sign-in needed, proxied in dev by `vite.config.js`, and it never throws — it returns false). `Login.jsx` holds it in `serverReady`: `null` = not asked yet (form works as normal), `true` = answering, `false` = not answering. Only `false` holds anything back — an amber `.login-notice` appears and the button reads "Waiting for the server...". While `false` it re-asks every 2 s until it answers. A sign-in that fails with `SERVER_UNREACHABLE` is **not** shown as a sign-in error (nothing the person typed was wrong): it flips `serverReady` to `false` and bumps `readyCheckKey` to restart the watcher. In the packaged app this rarely fires — Electron already polls `/health` before showing the window — so it mostly covers dev, where the window opens as soon as Vite is ready.

## The activity trail's one shared list of actions

- **One list names every history action.** `client/src/utils/activityColors.js` holds `ACTION_COLORS` — every action name passed to `recordHistory` and nothing else — plus `ACTION_NAMES` (its keys, in display order) and `actionColor(action)`. The global Activity Log, the per-job Activity tab and the search page's **activity** filter chips all read it; the three used to carry their own copies, which drifted (a new action was tinted on one screen and left muted grey on the others, and four actions the server records were missing from the search filter entirely while two of its options matched nothing). Adding a `recordHistory` action means adding it here. Colour convention: `--accent-ready` for something added, `--accent-caution` for something taken away, `--primary-accent` for something changed. Note the server does **not** validate the search `action` param against a list — it binds the values straight into an `IN (...)`, so a name missing here is simply unfilterable, not an error.

## The job screen

- **JobCardModal**: Modular tab-based UI with custom hooks for each tab's logic (`useJobCardCosting.js` → wraps `useCosting.js`, `useTimeEntries.js`, `useTimer.js`, `useJobNotes.js`, `useCamera.js`, `useJobCardForm.js`, `useJobCardInstantSaves.js`, `useJobCardSave.js`, `useJobCardCloseGuard.js` → `useUnsavedGuard.js` + `closeReasons.js`, `useContactSearch.js`, `useJobFiles.js`, `useActivityLog.js`). `useJobCardSave.js` is create-only (see the instant-save note below) — validation, resolving/creating the customer, one `POST /jobcards`. Everything about work that would be lost if the screen went away — the close question, the refresh guard, the inactivity registration and the spoken status — lives in `useUnsavedGuard.js`, wired up against `closeReasons.js`'s "which box, what failed" by `useJobCardCloseGuard.js`; both are pulled out of the modal for the same length reason `useJobCardSave.js` is.

- **A screen that closes must not clear which record it was showing in the same render.** The job screen saves pending pricing edits on the way out, and that save needs the job id; a caller wiring `isOpen={!!id}` and `onClose={() => setId(null)}` off one state variable silently drops the save (`runSave` returns early on a null id). Track open/closed separately from the id — `JobCardList` (`isModalOpen` + `editingCardId`) and `SearchPage` (`modalOpen` + `modalJobId`) both do.

- **A refresh mid-edit must merge, never replace, unsaved form state.** Starting a part timer re-reads the job (the server may have auto-assigned the timer's worker and moved the status); `handleStartItemTimer` in `JobCardModal.jsx` folds in only that one worker and the status, because replacing the whole assignee list from the server silently undid any ticks/unticks made before pressing Start. Stop-timer and the 5 s poll reload time entries / status only.

- **A part create/update/delete can also auto-advance the job's status**, the same way logging time does (`jobs-and-status.md`), so it needs the same server-confirmed refresh — but without a second round trip: every part reply now carries the job's post-change status top-level (`jobStatus`, always present, not only when it changed). `useInstantItems.js`'s `applyItemReply` folds it straight into form state via `onJobStatusChange` (wired up in `useJobCardInstantSaves.js`, straight onto `formHook.setFormData`), the same landing point the timer refresh above uses — `status` is stripped from the isDirty baseline (`useJobCardForm.js`), so setting it this way can never mark the card dirty, arm the amber ring, or trigger a status write of its own. The delete route's older, `items`-less reply shape is handled the same way in `removeItem`'s own `.then`, since that branch skips `applyItemReply` entirely.

- **A part is matched to logged work by its own permanent id, never by its position.** A line item added on an existing job carries a client-side placeholder id until its description is committed (`createItemFromRow` in `useInstantItems.js`), at which point the create reply's real `item:` id and `item_number` replace it on that one row — the row's own content is left exactly as typed, not overwritten by the reply. Removing a part (`DELETE /jobcards/:id/items/:itemId`) never renumbers the survivors — `item_number` is a sort order the server owns and gaps are expected once a part is deleted (see `docs/notes/jobs-and-status.md`) — so a part's on-screen position (`position`, stated by the server on every part it returns) can shift for every surviving part after just one deletion, and a timer picking a part by that position still needs the *permanent* id underneath to survive the shuffle — `workMatch.mjs` is what time entries and the "Progress" list actually match against, never the position, for exactly this reason (see `ItemsTab.jsx`'s `entriesForItem`).

- **The job window frames itself when something on it hasn't reached the job.** Everything else on that screen reports itself — the timer counts, the costing sheet says "Saved", the file dots fill in — and the details, parts and assignees now do too (see the instant-save note below). `useJobCardForm.js` keeps a baseline of what the job last confirmed storing and exposes `isDirty`; `JobCardModal.jsx` folds it together with the pricing countdown as `waitingOnSave` and passes that to `BottomSheet` as `unsaved`, which adds the `modal-unsaved` class (an amber ring drawn outside the border in `App.css`, so nothing shifts) around the whole job window. **The same frame answers in green once the last of it lands** — `modal-saved`, the identical three layers in `--success-*`, held for 1.8s by `useSavedFlash.js` and then let go so the window's own border/shadow transition fades it back. **Green is fired by a write the server confirmed, never by unsaved work going away** — `useSaveQueue.js` counts confirmed landings (`landedCount`) alongside its outstanding-key map, `useCosting.js` keeps the same tally for the pricing sheet (`costingLandedCount`, since pricing saves on its own path rather than through the queue), and `JobCardModal.jsx` hands `useSavedFlash.js` the two added together. The two are not the same fact: the screen also stops having anything outstanding when an edit is *abandoned* — a half-typed part deleted before it was ever sent (`useInstantItems.js`'s `removeItem` on a not-yet-real row), or a box typed back to exactly what was already stored (`useInstantSave.js` returns before enqueueing) — and answering those with green told people their work had saved at the moment it was thrown away. A landing while other work is still outstanding *arms* the flash and waits, so the green always means all of it. **A refused create or remove is not a landing either**, even though it did reach the server and `run()` resolves rather than rejects — a part whose create or delete came back refused (400/409, logged work against it, the job's last line, …) already reports itself with its own toast (`useInstantItems.js`'s `createItemFromRow`/`removeItem` catches) and must stay off the count, or the green frame would flash for a part that was never actually created or removed. Rejecting instead isn't right either — that's `'failed'`, which flags the key and waits for the user to retry, and neither of these wants that (there's nothing stored to retry against on a refused create; a refused remove just leaves the row exactly as it was). `useSaveQueue.js` exports a sentinel, `NOT_LANDED`, for exactly this: a catch that already told the user returns it instead of the normal result, and the queue's landing handler clears the key (so it stops reading as outstanding) without bumping `landedCount`. The half it waits on is `waitingOnSave` — `isEdit && (isDirty || costingOutstanding)` — and **the amber ring is asked that exact same question**, so a price behaves like every other box: amber while it travels, green when it lands. The two halves must cover the same work or the frame contradicts itself; pricing was once in green's question and not in amber's, and a visit that only touched money got a green it had never announced — and, before `costingLandedCount` existed, no green at all. An unposted comment and an open stop-timer form are in **neither**: they are drafts the person is holding, not saves in flight, and letting either veto the flash would mean a job with a stray half-typed comment never confirmed a save again. `useSavedFlash.js` returns `flashing && !waiting` rather than leaving the answer to CSS ordering — its effect only runs after paint, so a fresh edit would otherwise get one frame of green before amber took over. Nothing gates on "has this card been edited yet" any more: a landing cannot happen on a card nobody has touched, and both counts are reset together on every open (`JobCardModal.jsx`'s `resetForm` clears the queue and calls `resetCosting`), so the total is always this job's. **Both signals are gated on `active` (`isOpen && isEdit`)**, which is what keeps one opening's news out of the next one: a field edited with the cursor still in the box is sent as the close button takes focus off it, so that write is normally still in the air when the window goes and lands while there is nothing on screen — without the gate the flash started against a closed window and the reopen (which resets the count) cancelled its timer without clearing it, so the next opening arrived green and stayed green. While the window is shut the hook absorbs whatever lands, arms nothing and holds nothing. **The queue itself counts a landing only for the opening that asked for it** — `useSaveQueue.js` captures an `openingRef` counter alongside the job id when a write is enqueued and checks both when the reply comes back; `reset()` bumps it. The job id on its own cannot tell a reply meant for the previous opening from one meant for this one when the SAME job is closed and immediately reopened, and that reply used to be counted against the fresh opening — an untouched job answering with the green frame and "all changes saved". The pricing half already had this, through `editSeq` (`resetCosting` bumps it, and `runSave` drops a reply whose snapshot no longer matches). **And the reset itself is a `useLayoutEffect`, not a `useEffect`** (`JobCardModal.jsx`): the modal returns null while closed rather than unmounting, so the commit that reopens it still holds the previous opening's form, baseline and queue. As a plain effect the reset landed one paint too late and that stale state was drawn — a job closed with an edit discarded came back wearing its amber frame, and the old form values flashed up before `loading` turned the body into a spinner. Running before paint means the reopened window is measured, framed and drawn as the new opening from its first frame. The green is a flash rather than a state on purpose: a frame that stayed green would stop reading as *that just saved*. It is deliberately not a CSS keyframe — `.modal-popup` already carries `animation: modalSlide` for its opening, and a class that comes and goes would replay that slide every time it cleared. The pair is now the **only** general answer to "did that save?" on an existing job: the identity strip's old `Saving… / Saved` line is gone (see the instant-save note below). A brand-new card is measured against a pristine, empty-form baseline (not `null`) from the moment it opens, so a half-filled new card is known to be unsaved even though nothing has reached the server yet. That dirtiness deliberately does **not** reach the amber frame on a brand-new card — the ring is gated to an existing job only (`isEdit &&`), so flagging every new card for the whole of an ordinary fill-in-and-create task wouldn't mean anything. The close question is not gated the same way: `useUnsavedGuard.js`'s `hasUnsavedWork` starts from `isDirty` with no `isEdit` in front of it, so closing a half-filled new card still asks first. Three things the baseline deliberately does *not* count, because none of them is a write waiting to happen: **status** (it's already instant, and the server also nudges it on its own — stripped from the form snapshot); **the people list, in full** — `toggleAssignee` writes the one worker it's about the moment the tile is tapped (`PUT`/`DELETE /jobcards/:id/assignees/:userId`, idempotent), moving the baseline with the list on success and leaving both alone on failure, so a failed tick stays flagged until retried; `creditAssignee`/`dropAssignee` do the same, unconditionally, for what the server did on its own (a started timer credits its worker, a discarded tap takes them back off); and **a part not yet real** — a placeholder id would otherwise read as an edit the moment the create reply swaps it for the stored one. On a brand-new job the customer, picked through `useContactSearch`, is a separate hook whose state `useJobCardForm` never sees, so `JobCardModal.jsx` folds in its own check of `contactHook.contactFormData` (non-empty on a new job only) rather than reaching into `useJobCardForm` for it.

- **Closing a job card with something unsaved now asks first, and says the right thing about it.** `JobCardModal.jsx`'s `handleRequestClose` is wired as `BottomSheet`'s `onClose`, covering Escape and the header X in one place. A save already in flight (the create path only — see the instant-save note) does **not** block the close or get cancelled by it: the confirm, if there's something to lose, runs the same as any other close, and the request keeps going in the background, landing its own toast/`onSuccess` when it resolves. **On an existing job the question is no longer one sentence for every situation** — see the instant-save note's closing bullet for the split, and `closeReasons.js` for how it's built. A brand-new job keeps the plain original wording ("Discard changes" / "Keep editing"), since none of the per-field/per-row machinery below applies until a job exists to write to. **Questions queue rather than overwrite each other.** `useConfirmDialog` used to hold a single `resolveRef`, so a second question asked while one was up replaced it and the first promise never settled. Escape can't cause that — `ConfirmDialog` and `BottomSheet` both gate on `isTopModal`, so while a question is up Escape only answers *it* and never reaches the screen underneath. What could was a question raised by a **timer**: the pricing sheet's old "change an invoiced job?" came off the 1 s autosave countdown, so on an invoiced job with both a job edit and a pricing edit waiting, Escape put up "close and lose them?" and the invoiced question reworded it mid-read a second later; the close `await` never resolved and the card silently refused to shut. That question has since been removed outright (see `time-and-costing.md`), so nothing in the app currently asks without a click — the queue stays as the structural guarantee, and still covers the two things that bite regardless: a double-click answering one question and stranding the next, and a question left outstanding when the screen goes away. Questions sit in a FIFO queue — one on screen, the rest waiting — with a 250 ms gap between them so the click answering one cannot land on the next and the box visibly goes and comes back. `JobCardModal.jsx` calls the hook's `cancelConfirms` when `isOpen` goes false, answering anything outstanding `false`: past that point nothing renders the box, so a question left on the queue would never settle and would park every later question behind it for the rest of the session. Pinned by `client/scripts/check-confirmQueue.mjs`. The question is asked about `hasUnsavedWork`, deliberately wider than `isDirty`: it also counts **a comment typed into the Comments tab but never posted** (`jobNotes.newNote`) and **the details form of a run that was just stopped** (`timer.showEntryForm` — the run itself is recorded, but the machine, quantities and checks about to be recorded against it are not). Those two are kept out of `isDirty` on purpose, because `isDirty` drives the amber ring and both of those mean *a write waiting to happen*, and the stop form is already a panel in its own right, so framing the whole window amber for it would dilute the signal. Two doors that used to bypass the question entirely are now covered as well. **A browser refresh or tab close** (`beforeunload`, registered while `hasWorkToLose`) stops and asks — the browser only ever shows its own fixed wording there, so it cannot carry the message above, but Ctrl+R no longer empties a half-filled card in silence. `hasWorkToLose` is `hasUnsavedWork` **plus** `costingDirty`, and that addition is the point: closing the job flushes pricing to the server (`useJobCardCosting`'s effect on `isOpen`), but a refresh and the inactivity sign-out never run that flush, so a money figure typed inside the 1 s autosave window — or any time after a failed save, when autosave is paused — went without a word. `costingDirty` stays out of `hasUnsavedWork` itself, so the amber ring and the close confirm are unchanged. **The packaged app needs its own handler for this**: Electron never shows Chromium's "Leave site?" dialog — it fires `will-prevent-unload` on the webContents, and with nothing listening its default is to cancel the close silently, so the desktop app simply refused to close and looked frozen. `client/electron/main.js` registers that handler and shows a real `showMessageBoxSync` ("Leave Without Saving" / "Keep Editing", the safe choice as both `defaultId` and `cancelId`); `event.preventDefault()` there means *proceed* with the close, so it is called only on the leave branch. **The inactivity sign-out** is told what is at stake: `useUnsavedGuard.js` calls `registerUnsavedWork('job card')` from `AuthContext` while there is something to lose, and `InactivityWarningModal` reads that label once when it appears and adds "You have an unsaved job card. It will be lost unless you continue." to a countdown that previously ran in silence while a manager was away from their desk (admins are exempt from the inactivity timer; managers and employees are not). It is the read-only companion to `registerBeforeLogout`, which `useTimer.js` already uses to put a half-stopped run back on the clock before the pass is torn up. Finally, the unsaved state is now **said as well as shown**: on an existing job (management only) a visually hidden `role="status"` line reads "This job card has unsaved changes." / "All changes saved." — the same approach `CostingTab.jsx`'s own status line already takes. It is the spoken twin of the window frame and is held to the same standard: the first half is the frame's own `waiting` (pricing included), and the second only speaks once `saveQueue.landedCount > 0`, so a card nobody has changed announces nothing on arrival and an abandoned edit is never announced as a save. There is no footer at all to sit beside any more on an existing job — see the instant-save note.

## Every change saves itself — the job screen has no Save button for an existing job

`tasks/instant-save-job-card.md` is the frozen spec; this is the short version of why.

A Save button is a **gap** between deciding something and sending it, and the old job save was
**wide** — it handed over the whole job, so the gap flattened whatever else had changed since the
payload was built (a timer crediting its worker, another person editing the same job). The people
list is where it bit first, because the timers write to that same list. The rule replacing it is
**narrow and immediate**: send only the thing that changed, at the moment it changes. An autosave
that still posted a whole-job payload on a timer would reproduce the same bug with a shorter fuse.

- **Single-value fields** (priority, due date, description, the customer's PO/quote/previous-job
  references, quality level, repeat job) write one field through `PUT /jobcards/:id`, which already
  treats an absent field as *leave it alone* (the `jobcardQueries.update.run` call in `jobcard-mutations.js`). Dropdowns, dates and
  toggles write on change; text boxes write on **blur only**, after `capitalizeFirst`/`toTitleCase`
  has run, so the tidy-up and the write are one action and the tidied value is what is sent.
  `useInstantSave.js` chains per field — a fast second edit to the same field queues behind the
  first and settles on its value, and different fields never block each other — and
  `markFieldSaved` moves that one key of the form baseline on success. **An unchanged field on blur
  writes nothing**, so tabbing through a form produces no writes and no trail entries.
- **Status** was already instant and is untouched. **Pricing** has always saved itself (and still
  debounces, which these fields deliberately do not — the caller here already knows exactly when).
- **A pick from an autocomplete does its own write.** `onMouseDown` fires before the input blurs and
  the blur still reads the DOM's *old* text, so the Previous Job Reference suggestion writes the job
  number itself and sets `justPickedRef`, which makes the blur behind it stand aside. Without that
  the half-typed reference is written over the job number just chosen.
- **A reply that lands after the user moved to another job is dropped** — `useInstantSave` and
  `toggleAssignee` both compare a captured job id against a live ref before touching any state, so a
  late reply can never mark a different job's field as saved.
- **A failed write keeps what the user typed**, flags the field, and is **never re-sent
  automatically**; the retry is the user editing again. Messages take a stable id per field so a
  repeat replaces rather than stacks.
- **The save-status line is one per area**, not one per field — `role="status" aria-live="polite"`,
  the same shape `CostingTab.jsx` uses. Eight live regions would be unusable read aloud.
  `resetFieldStates` clears it whenever the window opens, because `JobCardModal` returns null when
  closed rather than unmounting, so its state outlives a close and would otherwise greet the next
  job with the previous one's "Saved".
- **In the identity strip that line no longer shows its words**, only its failures. The header bar
  already carries the job number, priority pill, description box, status pill and due date, and a
  sixth item in it — a small `Saving… / Saved` that spent almost all its life saying nothing new —
  stopped being read. The amber/green window frame above says the same thing at a size that cannot
  be missed, so `JobIdentityStrip.jsx` renders `instant-save-status` **only** for `failed` ("Not
  saved"): the frame staying amber says *not there yet*, which on its own doesn't say anything went
  wrong, and that is the one state worth words. The full wording is still announced from a
  `sr-only` live region beside it, because a colour says nothing to a screen reader.
  `DetailsTab.jsx`'s copy of the line is unchanged — its grey section title bar has room for it.
- **The parts list saves row by row, in `useInstantItems.js`.** A row added by "Add Part" stays
  purely local — every field on it just edits screen state — until its description is filled in and
  left (`commitItemFieldBlur`): that's the one moment it becomes real, sending the whole row as one
  create (`POST /jobcards/:id/items`) and swapping the placeholder id for the stored one. From there,
  every further edit on that row writes itself: dropdowns/tags/toggles on change, text/number on
  blur, each through `PATCH /jobcards/:id/items/:itemId` — absent-means-unchanged, so only the one
  field travels. Removing a row calls `DELETE /jobcards/:id/items/:itemId` for an already-real row
  (a still-local row is just dropped, nothing was ever sent); a refusal (time logged against it, or
  it's the job's last line) leaves the row on screen with the server's own wording shown, never a
  silent drop. **A required box on an already-real row that's emptied is marked and never sent** —
  same rule as the details fields, using `hooks/useFieldErrors.js` — so a cleared box can't destroy
  a stored value; a still-local row's boxes are never marked this way, since starting blank is normal
  for a fresh row. This also closed a latent bug: the per-part timer button used to render on
  never-saved rows, so starting a timer there sent a part number the server didn't know about — it's
  now gated on the row actually being real (`isPersisted` in `ItemsTab.jsx`).
- **An existing job has no Save button at all — `useJobCardSave.js` is create-only now.** Every
  field, row and worker already writes itself the moment it changes, so there's nothing left for a
  whole-payload submit to do; a stray Enter inside the form is stopped from reaching it by an
  unconditional `if (isEdit) return;` at the top of `handleSubmit`, not just a role check. Creating a
  new job is unchanged: one `validateJobCardForm` pass, resolve/create the customer, one
  `POST /jobcards` carrying the whole form, items and assignees in one shot.
- **The close question now says *why*, not just *that*.** With no Save button, "this job card has
  changes that haven't been saved yet" stopped being one true sentence for every situation — an
  emptied required box has nothing to lose (the stored value stands, nothing was ever sent), while a
  failed write genuinely does. `closeReasons.js` turns `isDirty`'s ingredients (the details fields'
  `fieldStates`, the parts list's required-box marks and each row's own saved-vs-screen comparison,
  the people list's baseline mismatch) into two lists — `safe` (an empty required box, nothing at
  risk) and `atRisk` (a failed write, a part row that was never sent at all, a team assignment that
  hasn't landed, an unposted comment, an open stop-timer form) — and `useUnsavedGuard.js` picks the
  framing: `atRisk` alone or alongside `safe` gets the original "close and lose them?" wording naming
  what's at risk, with any `safe` items folded in as a second, calmer line; `safe` alone gets a
  different question entirely — "Close anyway" / "Fix it", `confirmVariant: 'warning'` not `'danger'`
  — and **Fix it moves the cursor into the offending box** (`scrollFieldIntoView`, reused from
  `hooks/useFieldErrors.js` rather than rewritten) instead of just dismissing the dialog. A local part
  row with anything typed into it counts as `atRisk` even though `hasIncompleteItem`-style marking
  never touches it — an untouched blank row is normal and never counts. None of this replaces
  `isDirty` itself, which stays exactly the single screen-vs-stored comparison it already was; the
  close question just describes it more specifically. See `tasks/instant-save-job-card.md`, Stage 4b.
