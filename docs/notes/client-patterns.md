# Client-side patterns and traps

> Detail split out of CLAUDE.md. Read before touching the job screen, the sign-in screen, error handling in the shared sender, or the activity trail colours.

## Talking to the server

- **"The server isn't answering" is one shared error, and only reads re-ask.** The server can be missing for a second or two — it is still finishing start-up, or (in dev, where `npm start` runs it as a separate process with `node --watch-path`) it restarted itself after a saved file. `_send` in `api.js` turns both shapes of that into a single `Error` carrying `code: 'SERVER_UNREACHABLE'` and one plain-English message: a `fetch` that rejects outright (nothing listening), **and** a `5xx` whose content-type isn't JSON — the Vite dev proxy answers `500 text/plain` with an empty body when its target is down, which is the same situation wearing a status code. That heuristic is safe because every real 5xx the app produces is `res.status(...).json(...)` (the catch-all handler in `server/index.js`, the restore-in-progress 503); the only non-JSON 5xx lives in `setup-trust.js`, outside `/api`. `request()` then wraps `_send` in a retry that applies **to reads only** — no `options.method`, or `GET` — 3 extra attempts 1.5 s apart. **A write is never re-sent**: it may have landed just before the server went away, and sending it twice would create two of whatever was being saved. This is why every non-GET goes through `_post`/`_put`/`_patch`/`_del` (which always set `method`) rather than calling `request()` bare — a body-carrying call with no method would be classified as a read and retried. Note `POST /jobcards/attachment-warnings` is read-shaped but sent as a write, so it deliberately gets no retry.

- **The login screen waits for the server before offering the form.** `api.isServerReady()` calls `/health` (outside `/api`, no sign-in needed, proxied in dev by `vite.config.js`, and it never throws — it returns false). `Login.jsx` holds it in `serverReady`: `null` = not asked yet (form works as normal), `true` = answering, `false` = not answering. Only `false` holds anything back — an amber `.login-notice` appears and the button reads "Waiting for the server...". While `false` it re-asks every 2 s until it answers. A sign-in that fails with `SERVER_UNREACHABLE` is **not** shown as a sign-in error (nothing the person typed was wrong): it flips `serverReady` to `false` and bumps `readyCheckKey` to restart the watcher. In the packaged app this rarely fires — Electron already polls `/health` before showing the window — so it mostly covers dev, where the window opens as soon as Vite is ready.

## The activity trail's one shared list of actions

- **One list names every history action.** `client/src/utils/activityColors.js` holds `ACTION_COLORS` — every action name passed to `recordHistory` and nothing else — plus `ACTION_NAMES` (its keys, in display order) and `actionColor(action)`. The global Activity Log, the per-job Activity tab and the search page's **activity** filter chips all read it; the three used to carry their own copies, which drifted (a new action was tinted on one screen and left muted grey on the others, and four actions the server records were missing from the search filter entirely while two of its options matched nothing). Adding a `recordHistory` action means adding it here. Colour convention: `--accent-ready` for something added, `--accent-caution` for something taken away, `--primary-accent` for something changed. Note the server does **not** validate the search `action` param against a list — it binds the values straight into an `IN (...)`, so a name missing here is simply unfilterable, not an error.

## The job screen

- **JobCardModal**: Modular tab-based UI with custom hooks for each tab's logic (`useJobCardCosting.js` → wraps `useCosting.js`, `useTimeEntries.js`, `useTimer.js`, `useJobNotes.js`, `useCamera.js`, `useJobCardForm.js`, `useJobCardSave.js`, `useContactSearch.js`, `useJobFiles.js`, `useActivityLog.js`). The Save flow itself — validation, resolving the customer on a new job, the pre-invoice pricing flush, the "files still missing" 409 retry — lives in `useJobCardSave.js`, not in the modal, which keeps `JobCardModal.jsx` under the 600-line limit.

- **A screen that closes must not clear which record it was showing in the same render.** The job screen saves pending pricing edits on the way out, and that save needs the job id; a caller wiring `isOpen={!!id}` and `onClose={() => setId(null)}` off one state variable silently drops the save (`runSave` returns early on a null id). Track open/closed separately from the id — `JobCardList` (`isModalOpen` + `editingCardId`) and `SearchPage` (`modalOpen` + `modalJobId`) both do.

- **A refresh mid-edit must merge, never replace, unsaved form state.** Starting a part timer re-reads the job (the server may have auto-assigned the timer's worker and moved the status); `handleStartItemTimer` in `JobCardModal.jsx` folds in only that one worker and the status, because replacing the whole assignee list from the server silently undid any ticks/unticks made before pressing Start. Stop-timer and the 5 s poll reload time entries / status only.

- **A save that leaves the screen open must adopt the stored ids back — without disturbing the rows themselves.** A line item added on the job screen carries a client-side placeholder id until it is saved; the save reply carries the real `item:` ids. `handleSubmit` (in `useJobCardSave.js`) therefore calls `markSaved(result.items, sent)` (in `useJobCardForm.js`) after an update, because the job stays open — without it every part on screen keeps its placeholder id, and work logged from then on is matched against an id no stored part has, so the "What this job used" panel files those hours under "Work on a deleted part". `markSaved` does **not** replace the on-screen rows with the reply: it merges just the stored id onto each row already on screen, matched to the reply by position (safe because the reply comes back ordered by `item_number` and the on-screen array is already in that order). A part whose description was edited while the save was in flight keeps that edit. If the row count on screen doesn't match the reply — a blank new row that never reached the server, or a row added/removed mid-save — there's no safe position to trust, so it falls back to taking the reply as-is.

- **The job window frames itself when there are edits no Save has sent.** Everything else on that screen reports itself — the timer counts, the costing sheet says "Saved", the file dots fill in — but the details, parts, assignees, description, priority and due date all wait for Update, and the window said nothing. `useJobCardForm.js` keeps a snapshot of the job as last loaded or saved and exposes `isDirty`; `JobCardModal.jsx` passes it (OR'd with a customer-fields check — see below) to `BottomSheet` as `unsaved`, which adds the `modal-unsaved` class (an amber ring drawn outside the border in `App.css`, so nothing shifts) around the whole job window, and the footer button reads "Save changes" instead of "Update" so the signal isn't carried by colour alone. A brand-new card is measured against a pristine, empty-form baseline (not `null`) from the moment it opens, so an untouched new card reports clean but typing into it turns the frame amber right away, the same as an edit to a loaded job would — a `null` baseline could never turn dirty before the first Save, which is exactly the half-filled-new-card case this guard exists for. Three things the snapshot deliberately does *not* count, because none of them is waiting on a Save: **status** (choosing one sends itself, and the server nudges it when work starts or finishes — so it is stripped from the form snapshot); **a worker the server added or removed on its own** (a started timer credits its worker, a discarded tap takes them back off — `creditAssignee`/`dropAssignee` move the snapshot with the list); and **part ids specifically** (a part added on screen carries a placeholder id until saved, so the stored id coming back would read as an edit — the rest of the part is very much counted, see above). One thing it can't count at all: on a brand-new job the customer is picked through `useContactSearch`, a separate hook whose state `useJobCardForm` never sees, so `JobCardModal.jsx` folds in its own check of `contactHook.contactFormData` (non-empty on a new job only — existing jobs freeze the customer fields read-only) rather than reaching into `useJobCardForm` for it. The snapshot taken at Update time is the one that went out (`captureSent`, which now covers the parts too), not the one that comes back — nothing on screen is locked during a save, so anything typed mid-flight, parts included, stays marked unsaved until it is actually sent. **Closing a job card with unsaved edits now asks first**: `JobCardModal.jsx`'s `handleRequestClose` is wired as `BottomSheet`'s `onClose`, covering Escape and the header X in one place; it closes straight away when nothing is dirty, and otherwise confirms ("Discard changes" / "Keep editing") before calling the real `onClose`. A save already in flight does **not** block the close or get cancelled by it — the confirm (if anything is dirty) runs the same as any other close, and the request keeps going in the background, landing its own toast/`onSuccess` when it resolves.
